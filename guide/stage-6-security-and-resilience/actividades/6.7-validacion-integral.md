## Por que esta actividad

Has completado 6 actividades de seguridad y resiliencia, cada una enfocada en un aspecto especifico. Pero la seguridad real no funciona en silos — un atacante no va a probar solo XSS o solo CSRF. Va a probar todo. Esta actividad te obliga a verificar que **todas las capas de proteccion funcionan juntas**: que tu CSP no rompio tu auth, que tu validacion cubre tanto cliente como servidor, que tus error states aparecen cuando el retry se agota, y que no dejaste ningun hueco entre actividades. Es tu auditoria final de la etapa.

## Antes de empezar

Necesitas tener completadas **todas las actividades de la Etapa 6** (6.1 a 6.6). Esta actividad no introduce conceptos nuevos — es una verificacion integral de todo lo que implementaste.

Ten a mano:

- DevTools abierto
- La terminal lista para ejecutar comandos

### Paso 1 — XSS y sanitizacion (6.1)

Verifica que tu app es resistente a XSS:

1. Abre tu app y navega a cada formulario o campo de entrada
2. En cada input, ingresa el siguiente payload:
   ```text
   <img src=x onerror=alert('XSS')>
   ```
3. Envia el formulario o haz que el valor se renderice en la pagina
4. **Resultado esperado:** Cero alerts. El texto se muestra escapado como texto plano, no como HTML

5. Busca en tu codigo usos peligrosos:
   ```bash
   grep -r "innerHTML\|bypassSecurityTrust\|DomSanitizer" src/app/
   ```
6. Si hay resultados, verifica que cada uso esta justificado y sanitizado con DOMPurify

- [ ] Cero XSS alerts con payload de prueba
- [ ] Cero usos injustificados de `innerHTML` o `bypassSecurityTrust`

### Paso 2 — Error states (6.2)

Verifica que toda vista con data fetching maneja los 4 estados:

1. Identifica todas las vistas que hacen peticiones HTTP
2. Para cada vista, verifica:

   **Loading:** Aplica Slow 3G en DevTools → Network → Throttling
   - [ ] Se muestra skeleton o indicador de carga (no pantalla en blanco)

   **Error:** Bloquea la API en Network → Block request URL
   - [ ] Se muestra mensaje de error con boton de retry
   - [ ] El boton de retry funciona (vuelve a hacer la peticion)

   **Empty:** Asegurate de que la API devuelva un array vacio
   - [ ] Se muestra empty state con orientacion al usuario (no solo "No hay datos")

   **Success:** Con datos normales
   - [ ] Los datos se renderizan correctamente

### Paso 3 — Auth segura (6.3)

Verifica que los tokens estan almacenados de forma segura:

1. Abre DevTools → Application → Local Storage y Session Storage
   - [ ] Cero tokens de autenticacion visibles (no `access_token`, no `jwt`, no `auth`)

2. Verifica que el refresh token esta en una cookie HttpOnly:
   - Abre DevTools → Application → Cookies
   - [ ] La cookie de refresh tiene HttpOnly activado
   - [ ] La cookie tiene Secure activado

3. Verifica renovacion automatica:
   - Espera a que el access token expire (o forzalo cambiando el tiempo en el servidor)
   - [ ] La app renueva el token automaticamente sin que el usuario tenga que re-autenticarse

### Paso 4 — Validacion doble (6.4)

Verifica que la validacion funciona en ambos lados:

1. Intenta enviar datos invalidos desde el formulario:
   - [ ] El cliente muestra errores de validacion claros antes de enviar

2. Salta la validacion del cliente enviando datos directamente desde Console:
   ```javascript
   fetch('/api/usuarios', {
     method: 'POST',
     headers: { 'Content-Type': 'application/json' },
     body: JSON.stringify({ nombre: '', email: 'invalido', edad: -1 }),
   }).then(r => console.log(r.status, r.statusText));
   ```
   - [ ] El servidor responde con 400 (no con 200)

3. Verifica que no hay secretos en el bundle:
   ```bash
   ng build && grep -r "sk_\|api_key\|secret\|password\|PRIVATE" dist/
   ```
   - [ ] Cero resultados reales (sin secretos expuestos)

### Paso 5 — CSP y CSRF (6.5)

Verifica los headers de seguridad:

1. Abre DevTools → Network → click en el documento principal → Response Headers
   - [ ] `Content-Security-Policy` esta presente (o meta tag en desarrollo)
   - [ ] No contiene `*` en ninguna directiva
   - [ ] No contiene `'unsafe-inline'` en `script-src`

2. Prueba que CSP bloquea scripts externos:
   ```javascript
   const s = document.createElement('script');
   s.src = 'https://evil.com/malware.js';
   document.head.appendChild(s);
   ```
   - [ ] La Console muestra `Refused to load the script...`

3. Abre DevTools → Application → Cookies
   - [ ] Las cookies de sesion tienen `SameSite=Strict` o `SameSite=Lax`

### Paso 6 — Optimistic updates y retry (6.6)

Verifica el comportamiento de resiliencia:

1. Haz click en el boton de like con la API funcionando:
   - [ ] El like aparece inmediatamente (optimistic)

2. Bloquea la API y haz click en like:
   - [ ] El like aparece y luego se revierte (rollback)
   - [ ] Aparece un toast de error

3. Observa los reintentos en DevTools → Network:
   - [ ] Los intervalos entre reintentos son crecientes (~1s, ~2s, ~4s)

4. Desbloquea la API y verifica que todo vuelve a funcionar normalmente

## Que puede salir mal

- **"Algunos criterios no aplican a mi app"** → Si tu app no tiene auth (por ejemplo, es una app publica sin login), los criterios de auth no aplican. Documenta en la columna "Notas" por que no aplica. Pero no lo uses como excusa para saltarte criterios que si aplican.
- **"Todo pasaba antes pero ahora algo falla"** → Las actividades pueden interferir entre si. Por ejemplo, un CSP restrictivo puede bloquear un script de analytics que antes funcionaba. Ajusta tu CSP para incluir las fuentes necesarias sin usar `*`.
- **"No tengo servidor para verificar validacion del servidor"** → Documenta el requerimiento como pendiente. La validacion del cliente debe funcionar independientemente.
