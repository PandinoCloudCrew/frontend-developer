## Por que esta actividad

La validación en el frontend es para **UX** (mostrar errores rápido al usuario). La validación en el servidor es para **seguridad** (nunca confiar en datos del cliente). Un usuario puede desactivar tu validación frontend en 5 segundos: abre DevTools, elimina el atributo `required` de un input, y envia el formulario. Si tu servidor acepta todo lo que recibe sin validar, tu base de datos se llena de basura — o peor, un atacante explota la falta de validación para inyectar datos maliciosos.

## Antes de empezar

Necesitas tener completada la **Actividad 6.3** y un formulario que envia datos a una API.

**Validación del cliente** es la que ocurre en el navegador antes de enviar datos al servidor. Es rápida (no requiere red) y mejora la experiencia del usuario (errores inmediatos). Pero **no es segura** porque el usuario puede saltarsela.

**Validación del servidor** es la que ocurre en el backend cuando recibe datos. Es la única que puedes confiar porque el usuario no puede manipularla.

**Zod** es una libreria de validación para TypeScript que te permite definir un **schema** — una descripción de como deben verse los datos. Puedes usar el mismo schema en el cliente y en el servidor si ambos usan TypeScript.

Un **schema** es como un molde: defines que campos esperas, de que tipo, que restricciones tienen (longitud minima, formato de email, etc.). Si los datos no encajan en el molde, Zod te dice exactamente que esta mal.

### Paso 1 — Instalar Zod

1. Abre la terminal en VS Code en la carpeta de tu proyecto
2. Instala Zod:
   ```bash
   npm install zod
   ```

### Paso 2 — Definir el schema de validación

1. Crea un archivo para el schema: `src/app/schemas/usuario.schema.ts`
   ```typescript
   import { z } from 'zod';

   export const usuarioSchema = z.object({
     nombre: z.string()
       .min(2, 'El nombre debe tener al menos 2 caracteres')
       .max(50, 'El nombre no puede tener mas de 50 caracteres'),
     email: z.string()
       .email('El email no tiene un formato valido'),
     edad: z.number()
       .min(18, 'Debes ser mayor de edad')
       .max(120, 'Edad no valida'),
     sitioWeb: z.string()
       .url('La URL no es valida')
       .optional()
       .or(z.literal('')),
   });

   // TypeScript infiere el tipo automaticamente del schema
   export type UsuarioForm = z.infer<typeof usuarioSchema>;
   ```

> 💡 **Nota:** `z.infer<typeof usuarioSchema>` genera automáticamente un tipo TypeScript que coincide con el schema. No necesitas definir el tipo por separado — Zod lo hace por ti.

### Paso 3 — Validar en el cliente

1. Crea un componente de formulario:
   ```bash
   ng generate component formulario-usuario
   ```
2. En `src/app/formulario-usuario/formulario-usuario.component.ts`:
   ```typescript
   import { Component, signal, inject } from '@angular/core';
   import { FormsModule } from '@angular/forms';
   import { HttpClient } from '@angular/common/http';
   import { usuarioSchema, UsuarioForm } from '../schemas/usuario.schema';
   import { ZodError } from 'zod';

   @Component({
     selector: 'app-formulario-usuario',
     standalone: true,
     imports: [FormsModule],
     template: `
       <form (ngSubmit)="enviar()">
         <label>
           Nombre:
           <input type="text" [(ngModel)]="form.nombre" name="nombre" />
         </label>
         <label>
           Email:
           <input type="email" [(ngModel)]="form.email" name="email" />
         </label>
         <label>
           Edad:
           <input type="number" [(ngModel)]="form.edad" name="edad" />
         </label>
         <label>
           Sitio web (opcional):
           <input type="url" [(ngModel)]="form.sitioWeb" name="sitioWeb" />
         </label>

         @if (errores().length > 0) {
           <ul class="errores">
             @for (error of errores(); track $index) {
               <li>{{ error }}</li>
             }
           </ul>
         }

         @if (mensajeExito()) {
           <p class="exito">{{ mensajeExito() }}</p>
         }

         <button type="submit">Enviar</button>
       </form>
     `,
     styles: [`
       form { display: flex; flex-direction: column; gap: 1rem; max-width: 400px; }
       label { display: flex; flex-direction: column; gap: 0.25rem; }
       .errores { color: #e74c3c; list-style: none; padding: 0; }
       .exito { color: #27ae60; }
     `],
   })
   export class FormularioUsuarioComponent {
     private http = inject(HttpClient);

     form: UsuarioForm = {
       nombre: '',
       email: '',
       edad: 0,
       sitioWeb: '',
     };

     errores = signal<string[]>([]);
     mensajeExito = signal('');

     enviar() {
       this.errores.set([]);
       this.mensajeExito.set('');

       // Validar con Zod
       const resultado = usuarioSchema.safeParse(this.form);

       if (!resultado.success) {
         // Extraer mensajes de error legibles
         const mensajes = resultado.error.errors.map(e => e.message);
         this.errores.set(mensajes);
         return;
       }

       // Datos validados — enviar al servidor
       this.http.post('/api/usuarios', resultado.data).subscribe({
         next: () => {
           this.mensajeExito.set('Usuario creado exitosamente');
         },
         error: (err) => {
           if (err.status === 400 && err.error?.errors) {
             // El servidor tambien valido y rechazo
             this.errores.set(err.error.errors);
           } else {
             this.errores.set(['Error al enviar los datos. Intenta de nuevo.']);
           }
         },
       });
     }
   }
   ```

### Paso 4 — Probar saltando la validación del cliente

Esta es la prueba mas importante — demuestra por que necesitas validación en el servidor:

1. Abre tu formulario en Chrome
2. Abre DevTools → Console
3. Salta la validación del cliente enviando datos directamente con `fetch`:
   ```javascript
   // Esto es lo que un atacante haria — enviar datos sin pasar por tu formulario
   fetch('/api/usuarios', {
     method: 'POST',
     headers: { 'Content-Type': 'application/json' },
     body: JSON.stringify({
       nombre: '',           // vacio — deberia rechazarse
       email: 'no-es-email', // formato invalido
       edad: -5,             // negativo — invalido
     }),
   }).then(r => r.json()).then(console.log);
   ```
4. Verifica la respuesta:
   - Si el servidor responde con **400 Bad Request** y errores de validación → correcto
   - Si el servidor responde con **200 OK** y acepta los datos invalidos → tu servidor NO esta validando. Necesitas agregar validación en el backend
5. Documenta el resultado:
   - Si tienes control del backend, implementa validación con Zod (o la libreria que use tu servidor)
   - Si no tienes control del backend, documenta que la validación del servidor es un requerimiento pendiente

### Paso 5 — Verificar que no hay secretos en el bundle

Los secretos (API keys, contrasenas, tokens privados) nunca deben estar en el código frontend:

1. Haz el build de produccion:
   ```bash
   ng build
   ```
2. Busca secretos comunes en el bundle:
   ```bash
   grep -r "sk_\|api_key\|secret\|password\|PRIVATE" dist/
   ```
3. **El resultado debe ser vacio** — cero coincidencias
4. Si encuentras algo:
   - Mueve las claves al backend
   - Usa variables de entorno del servidor, no de Angular (las variables de `environment.ts` se incluyen en el bundle)

> 💡 **Nota:** Las variables en `environment.ts` de Angular NO son seguras — se incluyen en el bundle final y cualquiera puede verlas. Solo pon ahi valores publicos (URLs de APIs publicas, IDs de cliente para OAuth — no secrets).

## Que puede salir mal

- **"Zod me da error 'is not a function'"** → Verifica que tu `tsconfig.json` tiene `"moduleResolution": "bundler"` o `"node16"`. Las versiones antiguas de Angular pueden necesitar ajustes.
- **"No tengo un backend para probar la validación del servidor"** → Puedes usar [JSONPlaceholder](https://jsonplaceholder.typicode.com) como API de prueba (acepta todo — usa esto para entender el problema), o [Reqres](https://reqres.in) que rechaza datos invalidos.
- **"El grep encuentra 'password' en un archivo CSS que dice 'password-input'"** → Eso es un nombre de clase CSS, no un secreto. Busca patrones mas especificos: `sk_live_`, `sk_test_`, `AKIA` (AWS keys).

## Resultado esperado

Al terminar, tu formulario valida datos con un schema de Zod antes de enviarlos, el servidor rechaza datos invalidos independientemente de la validación del cliente, y no hay secretos expuestos en el bundle de produccion.

**Criterios de aceptacion:**
- [ ] Validación en el cliente con schema de Zod — mensajes de error claros en el formulario
- [ ] Servidor rechaza datos invalidos independientemente (verificado enviando datos directamente con fetch desde Console)
- [ ] `grep "sk_\|api_key\|secret\|password" dist/` devuelve cero resultados reales (sin secretos en el bundle)
