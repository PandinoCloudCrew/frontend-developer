## Por que esta actividad

Tu app ya tiene autenticacion — sabes **quien** es el usuario. Pero no todos los usuarios pueden hacer lo mismo: un admin puede borrar cuentas, un editor puede publicar contenido, un viewer solo puede leer. RBAC (Role-Based Access Control) organiza estos permisos. En el frontend, RBAC determina **que ve** y **que puede hacer** cada usuario en la interfaz. Pero hay una regla critica que muchos desarrolladores ignoran: **ocultar un boton no es seguridad**. Cualquier persona puede abrir DevTools y hacer un `fetch` directo a la API. El frontend RBAC es UX — la seguridad real esta en el servidor.

## Antes de empezar

Necesitas tener completada la **Actividad 6.8** (login con OIDC) y entender como funcionan signals, route guards y lazy loading en Angular.

**RBAC (Role-Based Access Control)** organiza la autorizacion en tres niveles: usuarios tienen **roles**, roles tienen **permisos**, y los permisos controlan **acciones**. Ejemplo: Juan tiene el rol `admin`, que incluye los permisos `users:read`, `users:write` y `users:delete`.

**Route guard** es una funcion que Angular ejecuta antes de navegar a una ruta. Si el guard retorna `false` (o un `UrlTree`), la navegacion se cancela. Los usaras para bloquear rutas segun el rol del usuario.

**Lazy loading** carga modulos o componentes solo cuando se necesitan. Combinado con RBAC, las rutas de admin no solo estan protegidas — su codigo ni siquiera se descarga para usuarios sin permiso.

### Paso 1 — Crear PermissionService

1. Genera el servicio:
   ```bash
   ng generate service services/permission
   ```
2. Implementa el servicio de permisos:

::: code-group

```typescript [Angular]
// src/app/services/permission.service.ts
import { Injectable, signal, computed, inject } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { firstValueFrom } from 'rxjs';

interface UserProfile {
  id: string;
  roles: string[];
  permissions: string[];
}

export const ROLES = {
  ADMIN: 'admin',
  EDITOR: 'editor',
  VIEWER: 'viewer',
} as const;

export const PERMISSIONS = {
  USERS_READ: 'users:read',
  USERS_WRITE: 'users:write',
  USERS_DELETE: 'users:delete',
  POSTS_READ: 'posts:read',
  POSTS_WRITE: 'posts:write',
  POSTS_PUBLISH: 'posts:publish',
} as const;

@Injectable({ providedIn: 'root' })
export class PermissionService {
  private http = inject(HttpClient);
  private profile = signal<UserProfile | null>(null);

  roles = computed(() => this.profile()?.roles ?? []);
  permissions = computed(() => this.profile()?.permissions ?? []);
  isLoaded = computed(() => this.profile() !== null);

  async cargarPermisos(): Promise<void> {
    const perfil = await firstValueFrom(
      this.http.get<UserProfile>('/api/me')
    );
    this.profile.set(perfil);
  }

  hasRole(role: string): boolean {
    return this.roles().includes(role);
  }

  hasPermission(permission: string): boolean {
    return this.permissions().includes(permission);
  }

  hasAnyPermission(...perms: string[]): boolean {
    return perms.some(p => this.permissions().includes(p));
  }

  limpiar(): void {
    this.profile.set(null);
  }
}
```

### Paso 2 — Implementar route guard basado en roles

1. Implementa la proteccion de rutas por roles:

::: code-group

```typescript [Angular]
// src/app/guards/role.guard.ts
import { inject } from '@angular/core';
import { CanActivateFn, Router } from '@angular/router';
import { PermissionService } from '../services/permission.service';

export function requireRole(...roles: string[]): CanActivateFn {
  return () => {
    const perms = inject(PermissionService);
    const router = inject(Router);

    const tieneRol = roles.some(r => perms.hasRole(r));
    return tieneRol ? true : router.createUrlTree(['/sin-permiso']);
  };
}

export function requirePermission(...permissions: string[]): CanActivateFn {
  return () => {
    const perms = inject(PermissionService);
    const router = inject(Router);

    const tienePermiso = permissions.every(p => perms.hasPermission(p));
    return tienePermiso ? true : router.createUrlTree(['/sin-permiso']);
  };
}
```

### Paso 3 — Condicionar el template con permisos

1. En cualquier componente que tenga acciones restringidas, inyecta el servicio y usa `@if`:
   ```typescript
   import { Component, inject } from '@angular/core';
   import { PermissionService, PERMISSIONS, ROLES } from '../services/permission.service';

   @Component({
     selector: 'app-dashboard',
     standalone: true,
     template: `
       <nav>
         <a routerLink="/posts">Posts</a>

         @if (perms.hasPermission(PERMISSIONS.POSTS_WRITE)) {
           <a routerLink="/posts/nuevo">Nuevo Post</a>
         }

         @if (perms.hasRole(ROLES.ADMIN)) {
           <a routerLink="/admin">Admin Panel</a>
         }
       </nav>

       <main>
         <h1>Dashboard</h1>

         @if (perms.hasPermission(PERMISSIONS.USERS_DELETE)) {
           <button (click)="eliminarUsuario()">Eliminar usuario</button>
         }
       </main>
     `,
   })
   export class DashboardComponent {
     perms = inject(PermissionService);
     PERMISSIONS = PERMISSIONS;
     ROLES = ROLES;

     eliminarUsuario() {
       // Logica de eliminacion...
     }
   }
   ```

> 💡 **Nota:** Usamos `@if` para **ocultar** elementos por permisos (el usuario no puede hacer esto nunca). Si quisieras mostrar un boton deshabilitado (el usuario puede pero ahora no), usarias `[disabled]` con una explicacion de por que esta deshabilitado.

### Paso 4 — Crear rutas admin con lazy loading

1. Crea la estructura de la seccion admin:
   ```bash
   ng generate component admin/admin-dashboard
   ng generate component admin/admin-usuarios
   ```
2. Crea el archivo de rutas `src/app/admin/admin.routes.ts`:
   ```typescript
   import { Routes } from '@angular/router';

   export const ADMIN_ROUTES: Routes = [
     {
       path: '',
       loadComponent: () =>
         import('./admin-dashboard/admin-dashboard.component').then(
           m => m.AdminDashboardComponent
         ),
     },
     {
       path: 'usuarios',
       loadComponent: () =>
         import('./admin-usuarios/admin-usuarios.component').then(
           m => m.AdminUsuariosComponent
         ),
     },
   ];
   ```
3. Configura la ruta admin con guard y lazy loading:

::: code-group

```typescript [Angular]
// src/app/app.routes.ts
import { requireRole } from './guards/role.guard';
import { ROLES } from './services/permission.service';

// Dentro del array de rutas:
{
  path: 'admin',
  canActivate: [requireRole(ROLES.ADMIN)],
  loadChildren: () =>
    import('./admin/admin.routes').then(m => m.ADMIN_ROUTES),
},
```

4. Verifica que funciona:

### Paso 5 — Demostrar que ocultar un boton no es seguridad

Este paso es intencionalmente destructivo — demuestra por que el frontend RBAC es UX, no seguridad.

1. Inicia sesion con un usuario que **no** tenga permiso `users:delete`
2. Verifica que el boton "Eliminar usuario" no aparece en la interfaz
3. Ahora abre DevTools → Console y ejecuta directamente:
   ```javascript
   fetch('/api/users/123', {
     method: 'DELETE',
     headers: { 'Content-Type': 'application/json' },
   }).then(r => console.log('Status:', r.status));
   ```
4. **Si tu API devuelve 200 o 204** → tu servidor no verifica permisos. Ocultar el boton no sirvio de nada. **El servidor DEBE verificar permisos y responder con 403 Forbidden.**
5. **Si tu API devuelve 403** → el servidor esta bien protegido. Ocultar el boton es una mejora de UX (no mostrar opciones que no funcionaran), no una medida de seguridad.
6. Documenta esta prueba: escribe un comentario en tu codigo o un archivo `docs/rbac-nota.md` con la conclusion:
   ```markdown
   El frontend RBAC oculta opciones para mejorar la UX.
   La seguridad REAL esta en el servidor — verificar permisos en cada endpoint.
   Verificado: DELETE /api/users/123 sin permiso devuelve 403.
   ```

## Que puede salir mal

- **"El guard siempre redirige a /sin-permiso"** → Verifica que `PermissionService.cargarPermisos()` se ejecuta antes de que el guard se evalúe. Puedes llamar a `cargarPermisos()` en un `APP_INITIALIZER` o en el `ngOnInit` del componente raiz, antes de que el router resuelva rutas.
- **"Las constantes de ROLES no aparecen en el template"** → Necesitas asignarlas a una propiedad publica del componente: `ROLES = ROLES;`. Angular templates solo pueden acceder a propiedades publicas de la clase.
- **"El lazy loading carga el chunk de admin para todos los usuarios"** → Verifica que el `canActivate` esta en la ruta con `loadChildren`, no dentro de las rutas hijas. El guard debe evaluar ANTES de que Angular descargue el chunk.

## Resultado esperado

Al terminar, tu app tiene un sistema de autorizacion basado en roles: un `PermissionService` centralizado con signals, rutas protegidas con guards, elementos visibles segun permisos, y una seccion admin que solo se carga para administradores. Ademas, tienes documentado por que el frontend RBAC es UX y no seguridad — verificado con una prueba directa desde Console.

**Criterios de aceptacion:**
- [ ] `PermissionService` funciona con signals — `hasRole()` y `hasPermission()` retornan valores correctos segun el usuario autenticado
- [ ] Navegar a `/admin` sin el rol `admin` redirige a `/sin-permiso` (verificado en el navegador)
- [ ] El chunk de admin solo se descarga para usuarios con rol `admin` (verificado en DevTools → Network)
- [ ] Un `fetch` directo desde Console a un endpoint protegido demuestra que la API verifica permisos (403 Forbidden) o esta documentado como requerimiento pendiente del backend
