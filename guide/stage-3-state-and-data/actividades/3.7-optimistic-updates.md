## Por qué esta actividad

Cuando un usuario hace click en "Like", espera que el corazón se llene inmediatamente, no 500ms después de que el servidor confirme. Si esperas la confirmación del servidor para actualizar la UI, la app se siente lenta — aunque el servidor responda rápido. Los **optimistic updates** actualizan la UI primero y asumen que el servidor dirá "ok". Pero si el servidor falla, necesitas **revertir** el cambio y avisar al usuario. Este patrón es estándar en apps como Twitter, Instagram y cualquier app que se sienta "instantánea".

## Antes de empezar

Necesitas tener completadas las **Actividades 3.1 y 3.4** — sabes consumir APIs, manejar los 4 estados de UI, y organizar estado en servicios.

Un **optimistic update** funciona así:
1. El usuario hace click en "Like"
2. **Inmediatamente** actualizas la UI (el corazón se llena, el contador sube)
3. **Mientras tanto** envías la petición al servidor
4. Si el servidor confirma → no haces nada más (la UI ya estaba correcta)
5. Si el servidor falla → **reviertes** la UI al estado anterior y muestras un error

El **backoff exponencial** es una estrategia de reintento donde cada intento espera más que el anterior: 1 segundo, 2 segundos, 4 segundos. Esto evita saturar un servidor que ya está teniendo problemas.

### Paso 1 — Crear el servicio de likes

1. En la terminal, ejecuta:
   ```bash
   ng generate service services/likes
   ```
2. Abre `src/app/services/likes.service.ts` y reemplaza:

```typescript
// src/app/services/likes.service.ts
import { Injectable, inject, signal } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { firstValueFrom } from 'rxjs';

export interface LikeState {
  [postId: number]: { liked: boolean; count: number };
}

@Injectable({ providedIn: 'root' })
export class LikesService {
  private http = inject(HttpClient);

  likes = signal<LikeState>({
    1: { liked: false, count: 12 },
    2: { liked: true, count: 7 },
    3: { liked: false, count: 23 },
  });

  toastMessage = signal('');

  async toggleLike(postId: number) {
    const current = this.likes()[postId];
    if (!current) return;

    // 1. Guardar estado anterior (para rollback)
    const previousState = { ...current };

    // 2. Optimistic update — actualizar la UI inmediatamente
    const newLiked = !current.liked;
    const newCount = newLiked ? current.count + 1 : current.count - 1;

    this.likes.update(state => ({
      ...state,
      [postId]: { liked: newLiked, count: newCount }
    }));

    // 3. Enviar al servidor
    try {
      await this.sendToServer(postId, newLiked);
      // Servidor confirmó — no hay nada que hacer
    } catch {
      // 4. Servidor falló — rollback
      this.likes.update(state => ({
        ...state,
        [postId]: previousState
      }));
      this.showToast('No se pudo guardar. Inténtalo de nuevo.');
    }
  }

  private async sendToServer(
    postId: number,
    liked: boolean
  ): Promise<void> {
    // Simular petición al servidor
    // En una app real: this.http.post(`/api/posts/${postId}/like`, { liked })
    await firstValueFrom(
      this.http.post('https://jsonplaceholder.typicode.com/posts', {
        postId,
        liked
      })
    );
  }

  private showToast(message: string) {
    this.toastMessage.set(message);
    setTimeout(() => this.toastMessage.set(''), 3000);
  }
}
```

### Paso 3 — Implementar optimistic update

La lógica ya está en `toggleLike()` del servicio. Repasemos el flujo:

1. `previousState` guarda una copia del estado actual
2. `this.likes.update(...)` actualiza la UI inmediatamente
3. `await this.sendToServer(...)` envía al servidor
4. Si todo va bien, la UI ya estaba correcta — no hay nada más que hacer

Para verificar que es realmente optimistic:
1. Abre DevTools → Network → Throttling → "Slow 3G"
2. Haz click en un botón de like
3. El corazón debe llenarse **inmediatamente**, sin esperar a que la petición termine

### Paso 4 — Implementar rollback

El rollback ya está en el `catch` de `toggleLike()`. Para probarlo:

1. Para forzar un error, cambia temporalmente la URL en `sendToServer` a una URL inválida:
   ```typescript
   // Temporal — para probar rollback
   await firstValueFrom(
     this.http.post('https://url-que-no-existe.com/fail', { postId, liked })
   );
   ```
2. Haz click en un like
3. Deberías ver: el corazón se llena instantáneamente → la petición falla → el corazón vuelve a su estado anterior → aparece el toast "No se pudo guardar"
4. **Revierte el cambio** después de probar — pon la URL original

### Paso 5 — Implementar retry con backoff

1. Agrega la lógica de retry en `likes.service.ts`. Reemplaza el método `sendToServer`:

```typescript
  private async sendToServer(
    postId: number,
    liked: boolean,
    retries = 3
  ): Promise<void> {
    for (let attempt = 0; attempt < retries; attempt++) {
      try {
        await firstValueFrom(
          this.http.post('https://jsonplaceholder.typicode.com/posts', {
            postId,
            liked
          })
        );
        return; // Éxito — salir
      } catch (error) {
        if (attempt < retries - 1) {
          // Backoff exponencial: 1s, 2s, 4s
          const delay = Math.pow(2, attempt) * 1000;
          console.log(
            `Retry ${attempt + 1}/${retries - 1} en ${delay}ms...`
          );
          await new Promise(r => setTimeout(r, delay));
        } else {
          throw error; // Último intento falló — propagar el error
        }
      }
    }
  }
```

2. Para verificar los intervalos, usa la URL inválida otra vez y observa la consola:
   ```
   Retry 1/2 en 1000ms...
   Retry 2/2 en 2000ms...
   ```
   Después del tercer intento (4 segundos), el error se propaga y se hace rollback.

### Paso 6 — Validar el comportamiento

1. **Optimistic:** Con Slow 3G, haz click en like. Debe aparecer instantáneamente.
2. **Rollback:** Bloquea la red (Offline en DevTools). Haz click en like. Debe llenarse, esperar los retries, y luego revertirse con un toast de error.
3. **Retry intervals:** En la consola, verifica que los intervalos son crecientes (~1s, ~2s, ~4s).
4. **UI consistente:** Después del rollback, verifica que el conteo y el estado liked/unliked son exactamente los que eran antes del click.

## Qué puede salir mal

- **"El like no se revierte cuando falla"** → Verifica que guardas `previousState` **antes** de hacer el optimistic update. Si lo guardas después, estás guardando el estado ya modificado.
- **"Veo el toast pero el corazón no vuelve"** → Verifica que el rollback usa `this.likes.update()` con el `previousState` guardado, no con un valor nuevo calculado.
- **"Los retries no esperan, se ejecutan todos inmediato"** → Verifica que usas `await new Promise(r => setTimeout(r, delay))` con `await`. Sin `await`, los retries se disparan todos a la vez.
- **"El usuario puede hacer click múltiples veces durante el retry"** → En una app de producción agregarías un estado `pending` por post. Para esta actividad, es un comportamiento aceptable.

## Resultado esperado

Tu sistema de likes responde instantáneamente al click, revierte el cambio visualmente si el servidor falla, muestra un toast de error, y reintenta con intervalos crecientes antes de rendirse.

**Criterios de aceptación:**
- [ ] El optimistic update aparece inmediatamente al hacer click (sin esperar al servidor)
- [ ] En fallo, el like se revierte visualmente y aparece un toast de error
- [ ] Los intervalos de retry son crecientes: ~1s, ~2s, ~4s (verificado en la consola)

**Pilares de diseño ejercitados:**
- **Resiliencia** — La app se recupera de fallos del servidor: reintenta y, si no puede, revierte limpiamente.
- **Usabilidad** — El usuario percibe respuesta instantánea. Si algo falla, recibe feedback claro.
- **Rendimiento** — La UI no espera al servidor para actualizarse.
