## Por qué esta actividad

En la Actividad 1.7 aprendiste a auditar accesibilidad manualmente — navegar con teclado, ejecutar Lighthouse. Pero las auditorías manuales tienen un problema: dependen de que alguien se acuerde de ejecutarlas. Con el tiempo, regresiones de accesibilidad se cuelan: alguien agrega un `<button>` sin texto accesible, otro pone una imagen sin `alt`, y nadie lo nota hasta que un usuario con discapacidad se queja.

Integrar **axe-core** en tu pipeline de CI automatiza la detección de problemas de accesibilidad. Cada vez que alguien sube código, el pipeline verifica automáticamente que no haya violaciones. Si un botón no tiene nombre accesible, el build falla — igual que falla si hay un error de lint.

> **Pilares de diseño:** Esta actividad ejercita **Mantenibilidad** (la accesibilidad se verifica automáticamente, no depende de la memoria humana) y **Observabilidad** (el pipeline te muestra exactamente qué violación de accesibilidad introdujiste).

## Antes de empezar

Necesitas haber completado la **Actividad 7.5** — un pipeline de CI funcionando en GitHub Actions.

Necesitas haber completado la **Actividad 1.7** — entiendes qué es accesibilidad, por qué importa, y qué son los roles ARIA.

**¿Qué es axe-core?** Es un motor de testing de accesibilidad creado por Deque Systems. Analiza el HTML renderizado y detecta violaciones de las guías WCAG (Web Content Accessibility Guidelines). Por ejemplo: detecta botones sin texto accesible, imágenes sin `alt`, contrastes de color insuficientes, y formularios sin labels. Puede detectar automáticamente alrededor del 57% de los problemas de accesibilidad — el resto requiere revisión manual, pero ese 57% automatizado es mucho mejor que cero.

**¿Qué es WCAG?** Son las "Web Content Accessibility Guidelines" — un estándar internacional que define cómo hacer contenido web accesible. Tiene tres niveles: A (básico), AA (recomendado, obligatorio por ley en la UE), y AAA (máximo).

### Paso 1 — Instalar axe-core

1. En la terminal de VS Code, ejecuta:
   ```bash
   npm install -D axe-core vitest-axe
   ```

   `vitest-axe` proporciona matchers como `toHaveNoViolations()` que puedes usar directamente en tus tests de Vitest.

2. En tu archivo de setup de tests (`src/setup-tests.ts`), agrega:
   ```typescript
   import 'vitest-axe/extend-expect';
   ```

### Paso 2 — Agregar test de accesibilidad a un componente

1. Abre un test existente (por ejemplo, `src/app/search-bar/search-bar.component.test.ts` de la Actividad 7.1)

2. Agrega un test de accesibilidad:
   ```typescript
   import { axe } from 'vitest-axe';
   import { render } from '@testing-library/angular';
   import { SearchBarComponent } from './search-bar.component';

   describe('SearchBarComponent — accesibilidad', () => {
     test('no tiene violaciones de accesibilidad', async () => {
       // Arrange — renderiza el componente
       const { container } = await render(SearchBarComponent);

       // Act — ejecuta el análisis de accesibilidad
       const results = await axe(container);

       // Assert — verifica cero violaciones
       expect(results).toHaveNoViolations();
     });
   });
   ```

3. Ejecuta el test:
   ```bash
   npx vitest run
   ```
   Debería pasar si tu componente tiene labels y roles correctos.

### Paso 3 — Verificar que detecta una violación

Para confirmar que axe-core realmente detecta problemas:

1. Modifica temporalmente tu componente para introducir una violación. Abre `search-bar.component.ts` y cambia el botón para que no tenga texto accesible:
   ```typescript
   // Cambia esto:
   //   <button type="submit">Buscar</button>
   // Por esto (violación intencional):
   //   <button type="submit"></button>
   ```

2. Ejecuta el test de nuevo:
   ```bash
   npx vitest run
   ```

3. El test debe **fallar** con un mensaje como:
   ```
   Expected the document to have no violations but received:
   - button element must have discernible text (button-name)
   ```

4. **Revierte el cambio** — pon el texto "Buscar" de vuelta en el botón

> 💡 **Nota:** Este es el mismo flujo del Paso 5 de la Actividad 1.6b — romper algo a propósito para confirmar que el test detecta el problema.

### Paso 4 — Integrar en el pipeline de CI

Tus tests con axe-core ya se ejecutan con `npx vitest run`, que ya está en tu pipeline de CI (Actividad 7.5). Pero para tener un job dedicado de accesibilidad:

1. Abre `.github/workflows/ci.yml` y agrega un job de accesibilidad después de `unit-tests`:
   ```yaml
     a11y:
       runs-on: ubuntu-latest
       needs: [lint]
       steps:
         - uses: actions/checkout@v4
         - uses: actions/setup-node@v4
           with:
             node-version: 20
             cache: 'npm'
         - run: npm ci
         - run: npx vitest run --reporter=verbose src/**/*a11y*.test.ts src/**/*accessibility*.test.ts
   ```

2. Actualiza el job `e2e` para que dependa también de `a11y`:
   ```yaml
     e2e:
       runs-on: ubuntu-latest
       needs: [unit-tests, a11y]
   ```

> 💡 **Nota:** Al separar los tests de accesibilidad en su propio job, puedes ver de un vistazo si el pipeline falló por un bug funcional o por un problema de accesibilidad.

### Paso 5 — Validar que CI falla ante violación

1. Crea un componente con una violación intencional:
   ```bash
   ng generate component test-a11y --standalone
   ```

2. En `src/app/test-a11y/test-a11y.component.ts`, agrega un botón sin texto:
   ```typescript
   @Component({
     selector: 'app-test-a11y',
     standalone: true,
     template: `<button type="button"></button>`,
   })
   export class TestA11yComponent {}
   ```

3. Crea el test `src/app/test-a11y/test-a11y.a11y.test.ts`:
   ```typescript
   import { axe } from 'vitest-axe';
   import { render } from '@testing-library/angular';
   import { TestA11yComponent } from './test-a11y.component';

   test('detecta botón sin nombre accesible', async () => {
     const { container } = await render(TestA11yComponent);
     const results = await axe(container);
     expect(results).toHaveNoViolations();
   });
   ```

4. Haz push y verifica en GitHub Actions que el pipeline falla:
   ```bash
   git add -A
   git commit -m "test: verify a11y CI catches accessibility violations"
   git push
   ```

5. Ve a GitHub → Actions y confirma que el job `a11y` (o `unit-tests`) falla con el mensaje de violación

6. Corrige el componente (agrega texto al botón) o elimínalo y haz push de nuevo

## Qué puede salir mal

- **"Cannot find module 'vitest-axe'"** → No instalaste el paquete. Ejecuta `npm install -D vitest-axe` en la carpeta de tu proyecto.
- **"toHaveNoViolations is not a function"** → Falta importar el matcher. Agrega `import 'vitest-axe/extend-expect'` en tu archivo de setup de tests.
- **"El test de accesibilidad pasa pero sé que hay problemas"** → axe-core detecta ~57% de los problemas automáticamente. No detecta problemas de contraste en imágenes, ni verifica que el orden de lectura sea lógico, ni que los textos alternativos sean descriptivos. La auditoría manual (Actividad 1.7) sigue siendo necesaria.
- **"El pipeline se volvió muy lento"** → Los tests de axe-core son rápidos (milisegundos por componente). Si el pipeline es lento, el cuello de botella probablemente está en la instalación de dependencias o en los tests E2E, no en axe-core.

## Resultado esperado

Tu pipeline de CI verifica automáticamente la accesibilidad de tus componentes. Si alguien sube un componente con un botón sin texto accesible, un input sin label, o un heading con nivel incorrecto, el build falla. La accesibilidad ya no depende de la buena voluntad del equipo — está automatizada.

**Criterios de aceptación:**
- [ ] axe-core integrado en al menos un test de componente que pasa
- [ ] Un botón sin nombre accesible falla el test (verificado manualmente)
- [ ] El pipeline de CI ejecuta los tests de accesibilidad automáticamente
- [ ] Los tests de accesibilidad están separados o identificables en el output del pipeline
