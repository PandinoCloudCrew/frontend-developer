## Por qué esta actividad

En la Actividad 1.6b escribiste tests unitarios para funciones puras con Vitest. Eso cubre la lógica, pero tu aplicación no es solo lógica — tiene componentes con botones, inputs y texto que el usuario ve e interactúa. ¿Cómo verificas que un botón realmente aparece, que un input acepta texto, que un formulario llama a la función correcta al hacer submit?

**Testing Library** te permite testear componentes de la misma forma que un usuario los usa: buscando por texto visible, por roles accesibles, por labels — no por clases CSS ni IDs internos. Esto hace que tus tests sobrevivan refactorizaciones y que detecten problemas reales de usabilidad.

> **Pilar de diseño:** Esta actividad ejercita **Mantenibilidad** — tests que verifican comportamiento (no implementación) sobreviven refactorizaciones sin romperse.

## Antes de empezar

Necesitas haber completado la **Actividad 1.6b** — entiendes qué es un test, el patrón AAA (Arrange-Act-Assert) y los principios FIRST.

Necesitas tener un proyecto Angular con al menos un componente interactivo (un `SearchBar` o similar con un input y un botón de submit). Si no lo tienes, puedes crear uno rápido en el Paso 1.

**¿Qué es Testing Library?** Es una familia de utilidades para testear componentes de UI. Su filosofía es: "cuanto más se parezcan tus tests a cómo el usuario usa tu software, más confianza te dan". En lugar de buscar elementos por `class` o `id` (detalles de implementación), buscas por `role` (botón, input, heading) o por texto visible — exactamente como lo haría un usuario real o un lector de pantalla.

**¿Qué es `userEvent`?** Es una librería que simula interacciones del usuario de forma realista (typing, clicks, tab). Es preferible a `fireEvent` porque reproduce el comportamiento real del navegador (por ejemplo, `userEvent.type` dispara `keydown`, `keypress`, `input` y `keyup` — como un usuario real tecleando).

### Paso 1 — Crear el componente SearchBar

Si ya tienes un componente interactivo, puedes usarlo. Si no, crea uno:

1. En la terminal de VS Code, ejecuta:
   ```bash
   ng generate component search-bar --standalone
   ```

2. Abre `src/app/search-bar/search-bar.component.ts` y reemplaza el contenido por:
   ```typescript
   import { Component, output } from '@angular/core';
   import { FormsModule } from '@angular/forms';

   @Component({
     selector: 'app-search-bar',
     standalone: true,
     imports: [FormsModule],
     template: `
       <form (ngSubmit)="handleSubmit()">
         <label for="search-input">Buscar</label>
         <input
           id="search-input"
           type="text"
           [(ngModel)]="query"
           name="query"
           placeholder="Escribe tu búsqueda..."
         />
         <button type="submit">Buscar</button>
         @if (errorMessage) {
           <p role="alert">{{ errorMessage }}</p>
         }
       </form>
     `,
   })
   export class SearchBarComponent {
     search = output<string>();
     query = '';
     errorMessage = '';

     handleSubmit(): void {
       if (this.query.trim() === '') {
         this.errorMessage = 'Escribe algo para buscar';
         return;
       }
       this.errorMessage = '';
       this.search.emit(this.query.trim());
     }
   }
   ```

### Paso 2 — Configurar el entorno de testing

1. Instala Testing Library para Angular:
   ```bash
   npm install -D @testing-library/angular @testing-library/jest-dom @testing-library/user-event
   ```

2. Si tu proyecto usa Vitest (recomendado), asegúrate de tener la configuración de Vitest con `jsdom`:
   ```bash
   npm install -D vitest @analogjs/vite-plugin-angular jsdom
   ```

3. En `vite.config.ts` (o créalo si no existe), verifica que tienes:
   ```typescript
   /// <reference types="vitest" />
   import { defineConfig } from 'vite';
   import angular from '@analogjs/vite-plugin-angular';

   export default defineConfig({
     plugins: [angular()],
     test: {
       globals: true,
       environment: 'jsdom',
       include: ['src/**/*.test.ts'],
     },
   });
   ```

### Paso 3 — Escribir el primer test

1. Crea el archivo `src/app/search-bar/search-bar.component.test.ts`
2. Escribe un test que verifica que el componente se renderiza correctamente:

```typescript
import { render, screen } from '@testing-library/angular';
import { SearchBarComponent } from './search-bar.component';

describe('SearchBarComponent', () => {
  test('renderiza el input y el botón de búsqueda', async () => {
    // Arrange — renderiza el componente
    await render(SearchBarComponent);

    // Assert — verifica que los elementos existen por su rol accesible
    expect(screen.getByRole('textbox', { name: /buscar/i })).toBeTruthy();
    expect(screen.getByRole('button', { name: /buscar/i })).toBeTruthy();
  });
});
```

> 💡 **Nota:** `getByRole('textbox', { name: /buscar/i })` busca un input cuyo label accesible contenga "buscar". Esto es exactamente lo que un lector de pantalla ve. Si tu label está mal asociado, el test falla — y descubres un bug de accesibilidad gratis.

### Paso 4 — Tests de interacción con userEvent

Agrega tests que simulan lo que un usuario realmente hace:

```typescript
import userEvent from '@testing-library/user-event';

// ... dentro del describe

  test('permite escribir en el input', async () => {
    // Arrange
    const user = userEvent.setup();
    await render(SearchBarComponent);
    const input = screen.getByRole('textbox', { name: /buscar/i });

    // Act — simula que el usuario escribe
    await user.type(input, 'angular testing');

    // Assert
    expect(input).toHaveValue('angular testing');
  });

  test('emite el evento search al hacer submit con texto', async () => {
    // Arrange
    const user = userEvent.setup();
    const searchSpy = jest.fn();
    await render(SearchBarComponent, {
      on: { search: searchSpy },
    });

    // Act
    const input = screen.getByRole('textbox', { name: /buscar/i });
    await user.type(input, 'componentes');
    await user.click(screen.getByRole('button', { name: /buscar/i }));

    // Assert
    expect(searchSpy).toHaveBeenCalledWith('componentes');
  });
```

> 💡 **Nota:** Usamos `userEvent.type` en lugar de `fireEvent.change`. `userEvent` simula la secuencia completa de eventos que un usuario real produce al teclear — más realista y más confiable.

### Paso 5 — Test de validación de error

```typescript
  test('muestra error cuando se hace submit sin texto', async () => {
    // Arrange
    const user = userEvent.setup();
    await render(SearchBarComponent);

    // Act — submit sin escribir nada
    await user.click(screen.getByRole('button', { name: /buscar/i }));

    // Assert — busca el mensaje de error por su rol de alerta
    expect(screen.getByRole('alert')).toHaveTextContent('Escribe algo para buscar');
  });
```

### Paso 6 — Ejecutar y verificar

1. En la terminal, ejecuta:
   ```bash
   npx vitest run
   ```
2. Deberías ver todos los tests pasando:
   ```
   ✓ src/app/search-bar/search-bar.component.test.ts (4 tests)
     ✓ renderiza el input y el botón de búsqueda
     ✓ permite escribir en el input
     ✓ emite el evento search al hacer submit con texto
     ✓ muestra error cuando se hace submit sin texto
   ```

3. Verifica que NO usas selectores de implementación:
   ```bash
   grep -r "getByTestId\|querySelector\|getByClassName" src/ --include="*.test.ts"
   ```
   Ese comando no debe encontrar nada.

## Qué puede salir mal

- **"Cannot find module '@testing-library/angular'"** → No instalaste la librería. Ejecuta `npm install -D @testing-library/angular` en la carpeta de tu proyecto.
- **"getByRole no encuentra el elemento"** → Tu elemento no tiene el rol accesible correcto. Verifica que el `<label>` está asociado al `<input>` con `for`/`id`, y que el `<button>` tiene texto visible. Ejecuta `screen.debug()` para ver el HTML que Testing Library renderiza.
- **"userEvent is not defined"** → Necesitas importarlo: `import userEvent from '@testing-library/user-event'` y asegurarte de que está instalado.
- **Los tests tardan más de 5 segundos** → Es probable que la configuración de Angular TestBed no esté optimizada. Verifica que usas `@analogjs/vite-plugin-angular` con Vitest en lugar del runner de Karma por defecto.

## Resultado esperado

Al terminar, tu componente `SearchBar` tiene 4 tests que verifican su comportamiento desde la perspectiva del usuario. Los tests buscan elementos por roles accesibles y simulan interacciones reales. Si refactorizas el HTML interno del componente (cambias clases, reordenas elementos), los tests siguen pasando — porque verifican comportamiento, no estructura.

**Criterios de aceptación:**
- [ ] Los tests siguen el patrón Arrange-Act-Assert (cada sección claramente separada)
- [ ] Cero uso de `getByTestId`, `querySelector` o `getByClassName` — solo `getByRole`, `getByLabelText`, `getByText`
- [ ] Se usa `userEvent` (no `fireEvent`) para simular interacciones
- [ ] Al menos 4 tests pasan: renderizado, input, submit exitoso, submit con error
