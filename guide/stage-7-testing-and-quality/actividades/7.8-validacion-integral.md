### Paso 1 — Verificar tests de componentes (7.1)

1. Ejecuta todos los tests:
   ```bash
   npx vitest run
   ```

2. Verifica que no se usan selectores de implementación:
   ```bash
   grep -r "getByTestId\|querySelector\|getByClassName" src/ --include="*.test.ts"
   ```
   Este comando no debe encontrar nada.

3. Verifica que se usa `userEvent` en lugar de `fireEvent`:
   ```bash
   grep -r "fireEvent" src/ --include="*.test.ts"
   ```
   Este comando no debe encontrar nada (o solo en comentarios explicativos).

### Paso 2 — Verificar MSW (7.2)

1. Verifica que los handlers MSW usan tipos TypeScript:
   ```bash
   npx tsc --noEmit
   ```
   Cero errores de tipos.

2. Verifica que `onUnhandledRequest: 'error'` está configurado en tu setup de tests.

3. Verifica que tienes handlers para success, error y retry.

### Paso 3 — Verificar E2E (7.3)

1. Ejecuta los tests E2E:
   ```bash
   npx playwright test
   ```

2. Verifica que el test del camino crítico completa en menos de 30 segundos.

3. Verifica que tienes al menos 2 page objects en `e2e/pages/`.

### Paso 4 — Verificar CI (7.5, 7.6)

1. Ve a GitHub → tu repositorio → Actions.

2. Verifica que el último pipeline tiene los jobs: `lint`, `unit-tests`, `e2e` (y opcionalmente `a11y`).

3. Verifica que los jobs tienen dependencias correctas (`needs`).

4. Verifica que al menos una ejecución pasada muestra un fallo de lint o accesibilidad detectado (evidencia de que el pipeline realmente bloquea errores).

### Paso 5 — Verificar prácticas avanzadas (7.7)

1. Verifica que los snapshot tests solo se usan para output pequeño:
   ```bash
   grep -r "toMatchSnapshot\|toMatchInlineSnapshot" src/ --include="*.test.ts"
   ```
   Cada snapshot debe ser de output de menos de 10 líneas.

2. Verifica que no hay tests flaky ejecutando la suite completa 3 veces:
   ```bash
   npx vitest run && npx vitest run && npx vitest run
   ```
   Las tres ejecuciones deben dar el mismo resultado.

### Paso 6 — Checklist final

Revisa cada criterio de aceptación de las actividades 7.1-7.7:

**7.1 — Testing Library:**
- [ ] Tests siguen patrón AAA
- [ ] Cero `getByTestId` o `querySelector`
- [ ] Se usa `userEvent`, no `fireEvent`
- [ ] Al menos 4 tests de componentes

**7.2 — MSW:**
- [ ] Handlers para success, error y retry
- [ ] Tests verifican 4 estados (loading, success, error, retry)
- [ ] Respuestas MSW tipadas con TypeScript
- [ ] `onUnhandledRequest: 'error'` configurado

**7.3 — E2E:**
- [ ] Camino crítico completa en < 30 segundos
- [ ] Page Object Model con al menos 2 page objects
- [ ] Locators accesibles (no CSS selectors)

**7.4 — Code Review:**
- [ ] Al menos 5 comentarios accionables en un PR
- [ ] Distinción `blocking:` vs `nit:`
- [ ] Lenguaje constructivo

**7.5 — CI:**
- [ ] Pipeline: lint -> unit -> E2E en orden
- [ ] `needs` configurado correctamente
- [ ] Error de lint comprobado que falla el pipeline

**7.6 — Accesibilidad en CI:**
- [ ] axe-core integrado en tests
- [ ] Violación intencional falla el build

**7.7 — Prácticas avanzadas:**
- [ ] Snapshots solo en output pequeño
- [ ] Test flaky identificado y corregido
- [ ] Mocks MSW pasan `npx tsc --noEmit`

## Qué puede salir mal

- **"Algunos tests que pasaban antes ahora fallan"** → Es posible que cambios recientes rompieran algo. Revisa qué cambió. Esto es exactamente el valor de tener tests — te avisan cuando algo se rompe.
- **"El pipeline de CI está en rojo pero todo pasa localmente"** → Diferencias de entorno. Verifica versiones de Node.js, configuración de timeouts, y si los browsers de Playwright están instalados en CI.
- **"No completé la Actividad 7.4 porque no tenía un PR"** → Crea un PR con los cambios de esta etapa y revísalo tú mismo. Practicar code review de tu propio código también es valioso.
