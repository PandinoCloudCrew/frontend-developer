## Por qué esta actividad

A esta altura ya sabes escribir tests unitarios, de componentes y E2E. Pero hay tres trampas comunes en las que caen incluso los equipos experimentados:

1. **Snapshot testing mal usado** — snapshots de componentes enteros que se rompen con cada cambio cosmético y que el equipo actualiza sin leer
2. **Flaky tests** — tests que a veces pasan y a veces fallan sin que nadie haya cambiado nada, destruyendo la confianza en el pipeline
3. **Mocks desincronizados** — mocks de API que devuelven datos con una forma diferente a lo que el servidor real retorna

Esta actividad te enseña cuándo usar snapshots (y cuándo no), cómo diagnosticar y corregir tests flaky, y cómo validar que tus mocks MSW coinciden con los contratos de la API real.

> **Pilar de diseño:** Esta actividad ejercita **Mantenibilidad** — tests que son falsos positivos (fallan sin razón) o falsos negativos (pasan pero no verifican nada real) son peores que no tener tests.

## Antes de empezar

Necesitas haber completado las **Actividades 7.1 y 7.2** — sabes testear componentes con Testing Library y mockear APIs con MSW.

**¿Qué es un snapshot test?** Es un test que guarda una "foto" del output de un componente (su HTML renderizado) y la compara con la versión guardada. Si el output cambia, el test falla. Suena útil, pero si la foto es de un componente entero con 200 líneas de HTML, cualquier cambio cosmético (agregar una clase CSS, reordenar un atributo) rompe el snapshot — y el desarrollador termina actualizándolo sin leerlo, haciendo el test inútil.

**¿Qué es un test flaky?** Es un test que falla intermitentemente — a veces pasa, a veces falla, sin que nadie haya cambiado el código. Las causas más comunes son: dependencia de timing (setTimeout, animaciones), dependencia de orden de ejecución entre tests, y datos compartidos entre tests que no se limpian.

**¿Qué es contract testing?** Es verificar que la "forma" de los datos que tu frontend espera coincide con lo que el backend realmente envía. Si tu mock MSW devuelve `{ nombre: "Laptop" }` pero el servidor real envía `{ name: "Laptop" }`, tus tests pasan pero la aplicación falla en producción.

### Paso 1 — Snapshot útil: output pequeño

Los snapshots funcionan bien para output pequeño y estable — por ejemplo, una función que genera un className o un fragmento de HTML de menos de 10 líneas.

1. Crea un test de snapshot para una función que genera CSS classes:
   ```typescript
   // src/app/utils/class-names.ts
   export function getStatusClasses(status: 'active' | 'inactive' | 'pending'): string {
     const base = 'badge';
     const variants: Record<string, string> = {
       active: 'badge--success',
       inactive: 'badge--muted',
       pending: 'badge--warning',
     };
     return `${base} ${variants[status]}`;
   }
   ```

2. Escribe el test con snapshot:
   ```typescript
   // src/app/utils/class-names.test.ts
   import { describe, test, expect } from 'vitest';
   import { getStatusClasses } from './class-names';

   describe('getStatusClasses', () => {
     test('genera las clases correctas para cada estado', () => {
       expect(getStatusClasses('active')).toMatchInlineSnapshot('"badge badge--success"');
       expect(getStatusClasses('inactive')).toMatchInlineSnapshot('"badge badge--muted"');
       expect(getStatusClasses('pending')).toMatchInlineSnapshot('"badge badge--warning"');
     });
   });
   ```

> 💡 **Nota:** Usamos `toMatchInlineSnapshot` — el snapshot se guarda en línea, en el mismo archivo de test. Para outputs pequeños esto es claro. Si el output cambia, ves inmediatamente en el diff qué cambió.

### Paso 2 — Demostrar un snapshot dañino

1. Escribe un snapshot de un componente entero (el anti-pattern):
   ```typescript
   test('❌ ANTI-PATTERN: snapshot de componente completo', async () => {
     const { container } = await render(SearchBarComponent);

     // Esto guarda TODO el HTML del componente — 20+ líneas
     expect(container.innerHTML).toMatchSnapshot();
   });
   ```

2. Ejecuta el test y mira el archivo de snapshot generado (`.snap`). Observa que tiene todo el HTML incluyendo atributos internos de Angular, clases CSS, IDs generados, etc.

3. Ahora cambia algo cosmético en el componente (agrega un `class` al `<form>`, o reordena un atributo). Ejecuta el test de nuevo — falla.

4. La pregunta clave: ¿este cambio rompió algo para el usuario? No. Pero el snapshot dice que sí. Esto es un **falso positivo** — el test falla sin que haya un bug real.

5. Elimina este test. Los snapshots de componentes completos generan ruido y hacen que el equipo pierda la confianza en los tests.

### Paso 3 — Crear y diagnosticar un test flaky

Para entender los tests flaky, vamos a crear uno a propósito:

1. Crea un test que depende de timing:
   ```typescript
   // src/app/utils/flaky-example.test.ts
   import { describe, test, expect } from 'vitest';

   describe('ejemplo de test flaky', () => {
     test('❌ FLAKY: depende de timing', async () => {
       let value = 'loading';

       // Simula una operación asíncrona impredecible
       setTimeout(() => {
         value = 'done';
       }, Math.random() * 100); // A veces tarda 5ms, a veces 95ms

       // Espera un tiempo fijo — a veces suficiente, a veces no
       await new Promise(resolve => setTimeout(resolve, 50));

       expect(value).toBe('done'); // Falla ~50% de las veces
     });
   });
   ```

2. Ejecuta el test varias veces:
   ```bash
   npx vitest run src/app/utils/flaky-example.test.ts --repeat 10
   ```
   Verás que a veces pasa y a veces falla.

### Paso 4 — Corregir la causa raíz

La solución no es "aumentar el timeout" ni "reintentar el test". La solución es eliminar la dependencia de timing:

```typescript
  test('✅ CORRECTO: no depende de timing', async () => {
    // En lugar de setTimeout con tiempo aleatorio, usa una Promise que resuelve cuando el valor está listo
    const value = await new Promise<string>(resolve => {
      // Simula la operación asíncrona
      setTimeout(() => resolve('done'), 10);
    });

    expect(value).toBe('done'); // Siempre pasa
  });
```

Las causas más comunes de tests flaky y sus soluciones:

| Causa | Solución |
|-------|----------|
| `setTimeout` con timing fijo | Usar `await` con Promises o `vi.useFakeTimers()` |
| Tests que comparten estado | Limpiar estado en `beforeEach`/`afterEach` |
| Orden de ejecución entre tests | Cada test debe ser independiente (principio FIRST: Isolated) |
| Animaciones CSS que no terminan | Desactivar animaciones en el entorno de test |

Elimina el test flaky de ejemplo una vez que entiendas el patrón.

### Paso 5 — Validar mocks MSW contra tipos TypeScript

Verifica que tus handlers MSW devuelven datos con la misma forma que tus tipos TypeScript:

1. Abre `src/mocks/handlers.ts` (de la Actividad 7.2) y verifica que cada handler tiene el tipo correcto:
   ```typescript
   import { http, HttpResponse } from 'msw';
   import { ProductsResponse } from '../app/models/product.model';

   export const handlers = [
     http.get('/api/products', () => {
       // El tipo ProductsResponse garantiza que la forma coincide
       const body: ProductsResponse = {
         products: [
           { id: 1, name: 'Laptop', price: 999, category: 'electronics' },
         ],
         total: 1,
       };
       return HttpResponse.json(body);
     }),
   ];
   ```

2. Prueba que TypeScript detecta inconsistencias. Cambia el tipo `Product` para agregar un campo nuevo:
   ```typescript
   export interface Product {
     id: number;
     name: string;
     price: number;
     category: string;
     inStock: boolean; // nuevo campo
   }
   ```

3. Ejecuta la verificación de tipos:
   ```bash
   npx tsc --noEmit
   ```
   TypeScript debe marcar un error en el handler porque falta `inStock` en el mock.

4. Revierte el cambio al tipo o actualiza el mock — lo importante es que viste cómo TypeScript detecta la desincronización.

## Qué puede salir mal

- **"El snapshot siempre falla después de actualizar Angular"** → Angular puede cambiar atributos internos entre versiones. Si tu snapshot incluye HTML interno de Angular, se romperá. Solución: solo haz snapshots de output que tú controlas (funciones puras, fragmentos pequeños de HTML).
- **"El test flaky pasa localmente pero falla en CI"** → CI es más lento que tu máquina local. Timeouts que "siempre funcionan" en tu laptop pueden no ser suficientes en un servidor de CI. Solución: elimina la dependencia de timing, no aumentes el timeout.
- **"tsc --noEmit no muestra errores en los handlers"** → Verifica que tus handlers usan tipos explícitos en las respuestas (`const body: ProductsResponse = ...`), no inferencia de tipos. Sin el tipo explícito, TypeScript no puede comparar.

Entiendes cuándo un snapshot es útil (output pequeño y estable) y cuándo es dañino (componentes enteros). Has experimentado con un test flaky, identificado su causa raíz y corregido el patrón. Tus mocks MSW usan tipos TypeScript que se validan con `npx tsc --noEmit`.
