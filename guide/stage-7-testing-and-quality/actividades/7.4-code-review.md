## Por qué esta actividad

Escribir buen código es una habilidad. Revisarlo es otra. En equipos profesionales, todo código pasa por un **code review** (revisión de código) antes de integrarse al proyecto. Un buen review detecta bugs, mejora la legibilidad y comparte conocimiento. Un mal review genera conflictos, frustración y pierde el tiempo de todos.

La diferencia entre un review útil y uno dañino está en cómo comunicas tus observaciones. "Esto está mal" no ayuda. "Podríamos extraer esta lógica a una función para reutilizarla en el componente X — ¿qué te parece?" sí ayuda.

> **Pilar de diseño:** Esta actividad ejercita **Mantenibilidad** — el code review es el mecanismo principal para mantener la calidad del código a lo largo del tiempo en un equipo.

## Antes de empezar

Necesitas haber completado las **Actividades 7.1-7.3** — tener experiencia escribiendo tests para poder identificar cuándo faltan en un PR.

Necesitas una cuenta de GitHub. Si no la tienes, créala en [github.com](https://github.com).

**¿Qué es un pull request (PR)?** Es una solicitud para integrar cambios de código a la rama principal del proyecto. Cuando terminas de trabajar en una funcionalidad, creas un PR para que tu equipo revise el código antes de integrarlo. Es el momento donde otro desarrollador lee tu código, sugiere mejoras y aprueba (o pide cambios).

**¿Qué es un code review?** Es el acto de leer el código de alguien más y dar feedback. No es buscar errores para sentirte superior — es un ejercicio colaborativo para mejorar la calidad del proyecto juntos.

### Paso 1 — Obtener un PR para revisar

Tienes dos opciones:

**Opción A — Revisar tu propio código:** Crea un PR con los cambios de las Actividades 7.1-7.3.
1. Crea una rama:
   ```bash
   git checkout -b feature/testing-stage-7
   ```
2. Agrega tus tests:
   ```bash
   git add src/ e2e/
   git commit -m "feat: add component tests and E2E for search flow"
   ```
3. Sube la rama y crea el PR:
   ```bash
   git push -u origin feature/testing-stage-7
   ```
4. En GitHub, crea el pull request hacia `main`

**Opción B — Revisar un PR público:** Ve a un proyecto open source que conozcas (por ejemplo, el repositorio de Angular) y busca un PR abierto con la etiqueta "good first issue" o "needs review".

### Paso 2 — Lectura general del PR

Antes de ver el código, entiende el contexto:

1. **Lee el título y la descripción del PR.** ¿Qué problema resuelve? ¿Está claro?
2. **Mira la lista de archivos cambiados.** ¿El tamaño del PR es razonable? (Un PR de +500 líneas es difícil de revisar bien)
3. **Identifica el tipo de cambio:** ¿Es una funcionalidad nueva, un fix, un refactor, o tests?

Anota tus primeras impresiones:
- ¿El PR hace una sola cosa o mezcla varios cambios?
- ¿Tiene tests? ¿Son suficientes?
- ¿La descripción explica el "por qué", no solo el "qué"?

### Paso 3 — Revisión línea por línea

Ahora ve al código. Para cada archivo, busca:

1. **Corrección:** ¿El código hace lo que dice que hace? ¿Hay bugs visibles?
2. **Legibilidad:** ¿Puedo entender este código sin que el autor me lo explique?
3. **Mantenibilidad:** ¿Puedo cambiar este código en 6 meses sin romper todo?
4. **Tests:** ¿Los tests cubren el camino feliz Y los casos de error?
5. **Accesibilidad:** ¿Los elementos HTML tienen roles y labels correctos?

### Paso 4 — Escribir comentarios accionables

Para cada observación, usa el formato adecuado:

**Comentarios `blocking:`** — Deben corregirse antes de aprobar el PR:
```
blocking: Este handler de error silencia la excepción con un `catch` vacío.
Si la API falla, el usuario no ve ningún mensaje de error.

Sugerencia: podríamos agregar un estado de error y mostrarlo en la UI,
similar a como lo hacemos en `ProductListComponent`.
```

**Comentarios `nit:`** — Sugerencias menores que no bloquean la aprobación:
```
nit: Podríamos renombrar `data` a `products` para mayor claridad.
No es bloqueante, pero mejora la legibilidad.
```

**Reglas para escribir comentarios:**
- Usa **"nosotros" o "podríamos"**, no "tú deberías"
- Explica el **por qué**, no solo el qué
- Si sugieres un cambio, muestra **cómo se vería** el código alternativo
- Si algo está bien, **dilo** — "Me gusta cómo extrajiste esta lógica a una función pura"

### Paso 5 — Completar el review

1. Verifica que tienes al menos **5 comentarios accionables**
2. Verifica que al menos uno es `blocking:` y al menos uno es `nit:`
3. Escribe un **resumen general** del review:
   ```
   ## Resumen

   El PR agrega tests sólidos para el flujo de búsqueda. El uso de
   Testing Library con roles accesibles es correcto.

   Tengo 2 comentarios blocking sobre manejo de errores y 3 nits
   sobre naming. Una vez resueltos los blocking, apruebo.
   ```
4. En GitHub, selecciona:
   - **Approve** si no hay comentarios `blocking:`
   - **Request changes** si hay al menos un `blocking:`

## Qué puede salir mal

- **"No sé qué comentar — el código se ve bien"** → Intenta buscar: ¿faltan tests para casos de error? ¿Los nombres de variables son claros? ¿Hay `any` en TypeScript? ¿El componente maneja el estado de loading? Si realmente todo está bien, déjalo con un comentario positivo: "Revisado, se ve bien. Me gusta cómo manejas el estado de error."
- **"Mis comentarios suenan agresivos"** → Lee cada comentario antes de publicarlo. Reemplaza "deberías" por "podríamos", "esto está mal" por "¿qué te parece si...?". Agrega contexto: no solo diga que algo es incorrecto, explica por qué y cómo se puede mejorar.
- **"El PR tiene 800 líneas y no sé por dónde empezar"** → Empieza por los tests — te dan contexto de qué se supone que hace el código. Luego ve a los componentes. Si el PR es muy grande, es válido comentar: "nit: Este PR cubre muchos cambios. ¿Podríamos dividirlo en PRs más pequeños para facilitar el review?"

## Resultado esperado

Has completado un code review de un PR con comentarios constructivos. Sabes distinguir entre sugerencias menores y problemas que bloquean la aprobación, y escribes feedback que el autor puede actuar sin sentirse atacado.

**Criterios de aceptación:**
- [ ] Al menos 5 comentarios accionables en el PR (cada uno con contexto y sugerencia)
- [ ] Se distingue `blocking:` de `nit:` en los comentarios
- [ ] El lenguaje es constructivo ("podríamos...", "nosotros..." — nunca "deberías...")
- [ ] El review tiene un resumen general que indica si se aprueba o se piden cambios
