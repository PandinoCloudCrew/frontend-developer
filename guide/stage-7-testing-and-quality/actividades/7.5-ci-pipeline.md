## Por qué esta actividad

Hasta ahora ejecutas los tests manualmente: abres la terminal, escribes `npm test`, miras los resultados. Eso funciona para ti solo — pero en un equipo, no puedes confiar en que todos ejecuten los tests antes de subir código. Un día alguien hace push sin testear, rompe el proyecto, y nadie se da cuenta hasta que el cliente reporta un bug.

Un **pipeline de CI** (Continuous Integration) ejecuta automáticamente lint, tests unitarios, tests de componentes y tests E2E cada vez que alguien sube código. Si algo falla, el merge se bloquea. No hay forma de romper el proyecto sin que el pipeline te lo diga.

> **Pilares de diseño:** Esta actividad ejercita **Mantenibilidad** (automatizas la verificación de calidad) y **Observabilidad** (el pipeline te muestra exactamente qué falló y por qué).

## Antes de empezar

Necesitas haber completado las **Actividades 7.1-7.3** — tener tests unitarios, de componentes y E2E funcionando localmente.

Necesitas un repositorio en GitHub. Si tu proyecto no está en GitHub, súbelo:
```bash
git remote add origin https://github.com/TU-USUARIO/TU-PROYECTO.git
git push -u origin main
```

**¿Qué es CI?** CI significa "Continuous Integration" (Integración Continua). Es una práctica donde cada vez que alguien sube código al repositorio, un servidor ejecuta automáticamente una serie de verificaciones (lint, tests, build). Si algo falla, el equipo se entera inmediatamente — no tres semanas después cuando un usuario reporta un bug.

**¿Qué es un pipeline?** Un pipeline es una secuencia de pasos que se ejecutan en orden. Imagina una cadena de montaje en una fábrica: primero se verifica la calidad de los materiales (lint), luego se ensamblan las piezas (tests unitarios), luego se prueba el producto completo (E2E). Si un paso falla, la cadena se detiene — no tiene sentido probar el producto completo si las piezas están mal.

**¿Qué es GitHub Actions?** Es el servicio de CI/CD de GitHub. Lo configuras con un archivo YAML (un formato de texto estructurado, como JSON pero más legible) y GitHub ejecuta los pasos cada vez que haces push o abres un pull request. Es gratuito para repositorios públicos.

**¿Qué es YAML?** Es un formato de archivo para configuración. Usa indentación (como Python) en lugar de llaves (como JSON). Ejemplo: en JSON escribes `{"name": "test"}`, en YAML escribes `name: test`. La indentación importa — si un paso está mal indentado, el pipeline falla.

### Paso 1 — Crear el archivo de workflow

1. En la raíz de tu proyecto, crea las carpetas necesarias:
   ```bash
   mkdir -p .github/workflows
   ```

2. Crea el archivo `.github/workflows/ci.yml`:
   ```yaml
   name: CI

   on:
     push:
       branches: [main]
     pull_request:
       branches: [main]

   jobs:
     lint:
       runs-on: ubuntu-latest
       steps:
         - uses: actions/checkout@v4
         - uses: actions/setup-node@v4
           with:
             node-version: 20
             cache: 'npm'
         - run: npm ci
         - run: npm run lint

     unit-tests:
       runs-on: ubuntu-latest
       needs: [lint]
       steps:
         - uses: actions/checkout@v4
         - uses: actions/setup-node@v4
           with:
             node-version: 20
             cache: 'npm'
         - run: npm ci
         - run: npx vitest run --coverage

     e2e:
       runs-on: ubuntu-latest
       needs: [unit-tests]
       steps:
         - uses: actions/checkout@v4
         - uses: actions/setup-node@v4
           with:
             node-version: 20
             cache: 'npm'
         - run: npm ci
         - run: npx playwright install --with-deps
         - run: npx playwright test
   ```

> 💡 **Nota:** Cada `job` tiene un `needs` que indica qué jobs deben completarse antes. `e2e` tiene `needs: [unit-tests]`, lo que significa que solo corre si los tests unitarios pasan. `unit-tests` tiene `needs: [lint]`, así que si el lint falla, nada más se ejecuta.

### Paso 2 — Configurar el job de lint

El job de lint ya está en el archivo anterior. Verifica que tu `package.json` tiene un script de lint:

```json
{
  "scripts": {
    "lint": "ng lint"
  }
}
```

Si usas Biome en lugar de ESLint:
```json
{
  "scripts": {
    "lint": "npx @biomejs/biome check src/"
  }
}
```

### Paso 3 — Configurar el job de tests unitarios

El job ya está configurado. Verifica que tu `package.json` tiene:
```json
{
  "scripts": {
    "test": "vitest run"
  }
}
```

La flag `--coverage` genera un reporte de cobertura. No es obligatorio pero es útil para ver qué porcentaje de tu código está cubierto por tests.

### Paso 4 — Configurar el job de E2E

El job de E2E necesita instalar los browsers de Playwright en el servidor de CI. La línea `npx playwright install --with-deps` hace eso.

Verifica que `playwright.config.ts` tiene la sección `webServer` para que Playwright arranque tu aplicación automáticamente:
```typescript
webServer: {
  command: 'ng serve',
  url: 'http://localhost:4200',
  reuseExistingServer: !process.env['CI'],
},
```

### Paso 5 — Probar que el pipeline funciona

1. Agrega los archivos al repositorio:
   ```bash
   git add .github/workflows/ci.yml
   git commit -m "ci: add CI pipeline with lint, unit tests and E2E"
   git push
   ```

2. Ve a GitHub → tu repositorio → pestaña **Actions**
3. Deberías ver el pipeline ejecutándose. Haz click para ver el detalle de cada job
4. Verifica que los 3 jobs (lint, unit-tests, e2e) pasan en orden

### Paso 6 — Verificar que un error falla el pipeline

Para confirmar que el pipeline realmente protege tu código:

1. Introduce un error de lint a propósito. Por ejemplo, en cualquier archivo `.ts`, agrega una variable sin usar:
   ```typescript
   const variableSinUsar = 'test';
   ```

2. Haz commit y push:
   ```bash
   git add -A
   git commit -m "test: intentional lint error to verify CI"
   git push
   ```

3. Ve a GitHub Actions y verifica que:
   - El job `lint` falla con el error de la variable sin usar
   - Los jobs `unit-tests` y `e2e` no se ejecutan (porque dependen de `lint`)

4. Revierte el cambio:
   ```bash
   git revert HEAD
   git push
   ```

## Qué puede salir mal

- **"npm ci failed"** → `npm ci` requiere que `package-lock.json` esté en el repositorio. Ejecuta `npm install` localmente, haz commit de `package-lock.json` y sube los cambios.
- **"El job de E2E falla con 'Browser was not installed'"** → Falta la línea `npx playwright install --with-deps`. Esta línea descarga Chrome, Firefox y los drivers necesarios en el servidor de CI.
- **"El pipeline tarda 15 minutos"** → Verifica que estás usando `cache: 'npm'` en el paso `actions/setup-node`. Esto reutiliza los `node_modules` entre ejecuciones. También puedes limitar los browsers de Playwright a solo Chrome con `npx playwright install chromium --with-deps`.
- **"El YAML tiene error de sintaxis"** → La indentación en YAML debe ser con espacios, nunca con tabs. Usa 2 espacios por nivel. Si un paso está fuera de alineación, todo el archivo falla.

## Resultado esperado

Tu repositorio en GitHub tiene un pipeline de CI que se ejecuta automáticamente en cada push y pull request. El pipeline verifica lint, tests unitarios, tests de componentes y tests E2E en orden. Si cualquier paso falla, los siguientes no se ejecutan y el merge se bloquea.

**Criterios de aceptación:**
- [ ] El pipeline ejecuta lint -> unit tests -> E2E en orden secuencial
- [ ] El job `e2e` tiene `needs: [unit-tests]` (solo corre si los tests unitarios pasan)
- [ ] Un error de lint falla el pipeline antes de ejecutar tests (verificado con push intencional)
- [ ] El pipeline completa en menos de 10 minutos con cache de `npm` habilitado
