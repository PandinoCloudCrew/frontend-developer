## Por qué esta actividad

Tus componentes no viven aislados — la mayoría obtiene datos de una API. ¿Cómo testeas un componente que hace `fetch` sin depender del servidor real? Si tu test llama al servidor de verdad, es lento, frágil (falla cuando el servidor se cae) y no puedes controlar las respuestas para testear errores.

**MSW (Mock Service Worker)** intercepta las peticiones HTTP a nivel de red y responde con datos que tú controlas. Tus componentes no saben que el servidor es falso — hacen `fetch` normalmente, pero MSW intercepta la petición y devuelve la respuesta que tú defines. Esto te permite testear los 4 estados clave: loading, success, error y retry.

> **Pilar de diseño:** Esta actividad ejercita **Mantenibilidad** — mocks que coinciden con los tipos TypeScript de tu API evitan que los tests pasen con datos incorrectos.

## Antes de empezar

Necesitas haber completado la **Actividad 7.1** — sabes escribir tests con Testing Library y usar `userEvent`.

**¿Qué es MSW?** MSW (Mock Service Worker) es una librería que intercepta peticiones HTTP a nivel de red. En lugar de reemplazar `fetch` con un mock (como `jest.fn()`), MSW deja que tu código use `fetch` normalmente — pero intercepta la petición antes de que salga y responde con datos que tú defines. Esto significa que testeas el flujo completo, incluyendo la serialización/deserialización de datos.

**¿Por qué no simplemente hacer `jest.mock('fetch')`?** Porque eso reemplaza la implementación interna. Si mañana cambias de `fetch` a `axios` o a `HttpClient` de Angular, todos tus mocks se rompen. MSW intercepta a nivel de red — no importa qué librería uses para hacer la petición.

### Paso 1 — Instalar MSW

1. En la terminal de VS Code, ejecuta:
   ```bash
   npm install -D msw
   ```

2. Verifica la instalación:
   ```bash
   npx msw --version
   ```

### Paso 2 — Definir los tipos de la API

Antes de crear mocks, define los tipos TypeScript de tu API. Esto garantiza que los mocks devuelven datos con la misma forma que el servidor real.

1. Crea (o verifica que existe) `src/app/models/product.model.ts`:
   ```typescript
   export interface Product {
     id: number;
     name: string;
     price: number;
     category: string;
   }

   export interface ProductsResponse {
     products: Product[];
     total: number;
   }
   ```

### Paso 3 — Crear handlers de MSW

1. Crea la carpeta `src/mocks/` y dentro crea `handlers.ts`:
   ```typescript
   import { http, HttpResponse } from 'msw';
   import { ProductsResponse } from '../app/models/product.model';

   export const handlers = [
     // Handler de éxito
     http.get('/api/products', () => {
       const body: ProductsResponse = {
         products: [
           { id: 1, name: 'Laptop', price: 999, category: 'electronics' },
           { id: 2, name: 'Mouse', price: 29, category: 'electronics' },
         ],
         total: 2,
       };
       return HttpResponse.json(body);
     }),
   ];
   ```

> 💡 **Nota:** La respuesta `body` tiene el tipo `ProductsResponse`. Si mañana agregas un campo al tipo y no actualizas el handler, TypeScript te avisa — tus mocks no se desincronizarán del servidor real.

### Paso 4 — Configurar el server de MSW

1. Crea `src/mocks/server.ts`:
   ```typescript
   import { setupServer } from 'msw/node';
   import { handlers } from './handlers';

   export const server = setupServer(...handlers);
   ```

2. Crea (o agrega a) tu archivo de setup de tests `src/setup-tests.ts`:
   ```typescript
   import { server } from './mocks/server';

   beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
   afterEach(() => server.resetHandlers());
   afterAll(() => server.close());
   ```

3. En `vite.config.ts`, agrega el archivo de setup:
   ```typescript
   test: {
     globals: true,
     environment: 'jsdom',
     include: ['src/**/*.test.ts'],
     setupFiles: ['src/setup-tests.ts'],
   },
   ```

> 💡 **Nota:** `onUnhandledRequest: 'error'` hace que el test falle si tu código hace una petición HTTP que no tiene handler — así descubres peticiones no mockeadas.

### Paso 5 — Test de éxito

1. Crea `src/app/services/product.service.test.ts`:
   ```typescript
   import { describe, test, expect } from 'vitest';
   import { render, screen } from '@testing-library/angular';
   import { ProductListComponent } from '../product-list/product-list.component';

   describe('ProductList con data fetching', () => {
     test('muestra los productos después de cargar', async () => {
       // Arrange — renderiza el componente (MSW intercepta el fetch automáticamente)
       await render(ProductListComponent);

       // Assert — espera a que los productos aparezcan
       expect(await screen.findByText('Laptop')).toBeTruthy();
       expect(screen.getByText('Mouse')).toBeTruthy();
     });

     test('muestra estado de loading mientras carga', async () => {
       // Arrange
       await render(ProductListComponent);

       // Assert — el loading aparece inmediatamente
       expect(screen.getByText(/cargando/i)).toBeTruthy();

       // Assert — después de cargar, el loading desaparece
       await screen.findByText('Laptop');
       expect(screen.queryByText(/cargando/i)).toBeNull();
     });
   });
   ```

> 💡 **Nota:** `screen.findByText` espera automáticamente (con timeout) a que el elemento aparezca. Úsalo para contenido asíncrono. `screen.queryByText` retorna `null` si no encuentra el elemento — útil para verificar que algo NO está en pantalla.

### Paso 6 — Tests de error y retry

Puedes sobrescribir handlers para tests específicos usando `server.use()`:

```typescript
import { http, HttpResponse } from 'msw';
import { server } from '../../mocks/server';

  test('muestra mensaje de error cuando la API falla', async () => {
    // Arrange — sobrescribe el handler para simular un error 500
    server.use(
      http.get('/api/products', () => {
        return new HttpResponse(null, { status: 500 });
      }),
    );

    await render(ProductListComponent);

    // Assert
    expect(await screen.findByRole('alert')).toHaveTextContent(
      /error al cargar/i,
    );
  });

  test('permite reintentar después de un error', async () => {
    // Arrange — primero falla, luego tiene éxito
    let requestCount = 0;
    server.use(
      http.get('/api/products', () => {
        requestCount++;
        if (requestCount === 1) {
          return new HttpResponse(null, { status: 500 });
        }
        return HttpResponse.json({
          products: [{ id: 1, name: 'Laptop', price: 999, category: 'electronics' }],
          total: 1,
        });
      }),
    );

    const user = (await import('@testing-library/user-event')).default.setup();
    await render(ProductListComponent);

    // Act — espera el error y haz click en reintentar
    const retryButton = await screen.findByRole('button', { name: /reintentar/i });
    await user.click(retryButton);

    // Assert — ahora muestra los datos
    expect(await screen.findByText('Laptop')).toBeTruthy();
  });
```

### Paso 7 — Ejecutar y verificar

1. Ejecuta los tests:
   ```bash
   npx vitest run
   ```

2. Verifica que todos los tests pasan y que los mocks usan los tipos correctos:
   ```bash
   npx tsc --noEmit
   ```
   Este comando verifica que los handlers MSW son type-safe — si la respuesta no coincide con `ProductsResponse`, TypeScript marca el error.

## Qué puede salir mal

- **"Request handler not found for GET /api/products"** → Tu handler usa una URL diferente a la que tu código pide. Verifica que la URL en `http.get('/api/products', ...)` coincide exactamente con la URL que tu servicio usa en `fetch` o `HttpClient`.
- **"TypeError: Cannot read properties of undefined"** → Tu componente espera un campo en la respuesta que tu handler MSW no incluye. Verifica que el handler devuelve todos los campos que tu tipo define.
- **El test pasa pero el componente no muestra loading** → Verifica que tu componente tiene un estado de loading visible. Si no lo tiene, agrégalo — es importante tanto para tests como para UX.
- **`server.use()` afecta otros tests** → Cada test debe usar `afterEach(() => server.resetHandlers())`. Esto ya debería estar en tu `setup-tests.ts`.

## Resultado esperado

Tu servicio de data fetching tiene tests que cubren los 4 estados: loading, success, error y retry. Los handlers MSW usan tipos TypeScript que coinciden con tu API. Si cambias la forma de la respuesta del servidor, TypeScript detecta la incompatibilidad en los mocks.

**Criterios de aceptación:**
- [ ] MSW handlers cubren success, error (status 500) y retry
- [ ] Los tests verifican los 4 estados: loading, success, error, retry
- [ ] Las respuestas MSW usan tipos TypeScript que coinciden con los modelos de la aplicación (pasa `npx tsc --noEmit`)
- [ ] `onUnhandledRequest: 'error'` está configurado para detectar peticiones no mockeadas
