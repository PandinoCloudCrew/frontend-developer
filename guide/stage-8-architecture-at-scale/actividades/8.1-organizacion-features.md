- [ ] Completada

**Duración:** ~60 min

## Por qué esta actividad

Cuando tu proyecto tiene 10 componentes, la estructura plana funciona: una carpeta `components/`, otra `services/`, otra `models/`. Pero cuando tiene 50 o 100, esa estructura se vuelve un laberinto. ¿Dónde está el componente de productos? ¿En `components/product-list` o en `components/product-card`? ¿El servicio que lo acompaña? En `services/product.service.ts`. ¿El tipo? En `models/product.model.ts`. Para tocar una sola funcionalidad, saltas entre 4 carpetas.

La **organización por features** agrupa todo lo relacionado a una funcionalidad en una sola carpeta. Si necesitas trabajar en "productos", todo está en `features/products/`. Si necesitas eliminar esa funcionalidad, borras la carpeta y listo — sin buscar archivos dispersos por todo el proyecto.

> **Pilar de diseño:** Esta actividad ejercita **Mantenibilidad** — una buena organización permite que un nuevo desarrollador encuentre y entienda el código relevante en minutos, no en horas.

## Antes de empezar

Necesitas haber completado la **Etapa 7** — tu proyecto tiene tests que verifican que todo funciona. Esto es crucial porque vas a mover archivos, y los tests te dirán si rompiste algo.

**¿Qué es una "feature"?** Es una funcionalidad que tiene sentido para el usuario. "Productos" es una feature — incluye la lista, el detalle, el buscador, el servicio de API y los tipos. "Carrito" es otra feature. "Autenticación" es otra. Una feature no es una capa técnica (como "componentes" o "servicios") sino un dominio funcional.

**¿Qué es la API pública de un feature?** Es el conjunto de cosas que otros features pueden importar. Normalmente es un archivo `index.ts` en la raíz del feature que exporta solo lo necesario. Todo lo demás es "privado" — otros features no deberían importar archivos internos directamente.

**¿Qué es una dependencia circular?** Es cuando el Feature A importa algo del Feature B, y el Feature B importa algo del Feature A. Esto crea un ciclo que puede causar bugs difíciles de diagnosticar (valores `undefined` inesperados) y hace imposible entender el flujo del código.

### Paso 1 — Analizar la estructura actual

1. En la terminal, observa la estructura actual de tu proyecto:
   ```bash
   find src/app -type f -name "*.ts" | head -30
   ```

2. Si ves algo como esto, tienes estructura plana:
   ```
   src/app/components/product-list/
   src/app/components/product-card/
   src/app/components/cart-summary/
   src/app/components/login-form/
   src/app/services/product.service.ts
   src/app/services/cart.service.ts
   src/app/services/auth.service.ts
   src/app/models/product.model.ts
   src/app/models/cart.model.ts
   ```

3. El problema: para trabajar en "productos", necesitas abrir archivos en `components/`, `services/` y `models/`. Todo está disperso.

### Paso 2 — Identificar y planificar features

1. Haz una lista de los features de tu aplicación. Ejemplo:
   - `products` — lista, detalle, búsqueda
   - `cart` — agregar, eliminar, resumen
   - `auth` — login, registro, perfil
   - `shared` — componentes reutilizables (botones, inputs, layouts)

2. Para cada feature, identifica qué archivos le pertenecen.

### Paso 3 — Crear la estructura por features

1. Crea la estructura de carpetas:
   ```bash
   mkdir -p src/app/features/products/components
   mkdir -p src/app/features/products/services
   mkdir -p src/app/features/products/models
   mkdir -p src/app/features/cart/components
   mkdir -p src/app/features/cart/services
   mkdir -p src/app/features/cart/models
   mkdir -p src/app/features/auth/components
   mkdir -p src/app/features/auth/services
   mkdir -p src/app/features/auth/models
   mkdir -p src/app/shared/components
   mkdir -p src/app/shared/utils
   ```

La estructura resultante será:
```
src/app/
  features/
    products/
      components/
        product-list/
        product-card/
      services/
        product.service.ts
      models/
        product.model.ts
      index.ts          ← API pública
    cart/
      components/
      services/
      models/
      index.ts
    auth/
      ...
  shared/
    components/
    utils/
    index.ts
```

### Paso 4 — Mover archivos al feature correspondiente

1. Mueve cada archivo a su feature. Usa `git mv` para preservar el historial:
   ```bash
   git mv src/app/components/product-list src/app/features/products/components/
   git mv src/app/components/product-card src/app/features/products/components/
   git mv src/app/services/product.service.ts src/app/features/products/services/
   git mv src/app/models/product.model.ts src/app/features/products/models/
   ```

2. Repite para cada feature.

3. Después de mover los archivos, actualiza los imports. En VS Code, puedes usar **Find and Replace** (`Ctrl+Shift+H` o `Cmd+Shift+H`) para buscar y reemplazar rutas:
   - Busca: `from '../services/product.service'`
   - Reemplaza: `from '../features/products/services/product.service'`

> 💡 **Nota:** Si usas VS Code con la extensión "Angular Language Service", al mover archivos con `git mv` la extensión puede actualizar imports automáticamente. Pero siempre verifica manualmente.

### Paso 5 — Crear la API pública de cada feature

1. En la raíz de cada feature, crea un `index.ts` que exporta solo lo que otros features necesitan:

   ```typescript
   // src/app/features/products/index.ts
   export { ProductListComponent } from './components/product-list/product-list.component';
   export { ProductCardComponent } from './components/product-card/product-card.component';
   export { Product, ProductsResponse } from './models/product.model';

   // NO exportes el servicio — es interno del feature
   // NO exportes componentes auxiliares que solo se usan dentro del feature
   ```

2. Ahora, cuando otro feature necesite algo de "products", importa desde la API pública:
   ```typescript
   // En el feature de cart:
   import { Product } from '../../features/products';
   // NO hacer: import { Product } from '../../features/products/models/product.model';
   ```

### Paso 6 — Verificar cero dependencias circulares

1. Instala madge:
   ```bash
   npm install -D madge
   ```

2. Ejecuta la detección de ciclos:
   ```bash
   npx madge --circular --extensions ts src/
   ```

3. Si hay ciclos, madge te muestra la cadena. Ejemplo:
   ```
   Circular dependency detected:
   src/app/features/products/services/product.service.ts →
   src/app/features/cart/services/cart.service.ts →
   src/app/features/products/models/product.model.ts
   ```

4. Para romper un ciclo, extrae el tipo compartido a `shared/`:
   ```bash
   mv src/app/features/products/models/product.model.ts src/app/shared/models/
   ```
   Y actualiza ambos features para importar desde `shared/`.

### Paso 7 — Ejecutar tests para verificar

1. Ejecuta todos los tests:
   ```bash
   npx vitest run
   ```

2. Si algún test falla, el error probablemente es un import roto. Busca la ruta incorrecta y actualízala.

3. Ejecuta la verificación de tipos:
   ```bash
   npx tsc --noEmit
   ```
   Cero errores.

## Qué puede salir mal

- **"Cannot find module '../services/product.service'"** → Moviste el archivo pero no actualizaste el import. Busca todos los imports del archivo antiguo con `grep -r "product.service" src/` y actualízalos.
- **"Circular dependency detected"** → Dos features se importan mutuamente. Extrae el tipo o la función compartida a `shared/`. Si dos features necesitan compartir mucho código, puede que en realidad sean un solo feature.
- **"¿Un componente pertenece a dos features?"** → Probablemente es un componente `shared`. Muévelo a `src/app/shared/components/`.
- **"Los tests pasan pero la app no compila"** → Ejecuta `npx tsc --noEmit` además de los tests. TypeScript detecta imports rotos que Vitest puede no detectar si el archivo no está directamente testeado.

## Resultado esperado

Tu proyecto está organizado por features. Cada feature tiene sus componentes, servicios y tipos en una sola carpeta. Existe una API pública (`index.ts`) que define qué exporta cada feature. No hay dependencias circulares.

**Criterios de aceptación:**
- [ ] Cero dependencias circulares entre features (`npx madge --circular --extensions ts src/` no reporta ciclos)
- [ ] Cada feature contiene sus componentes, servicios y tipos en una sola carpeta
- [ ] Cada feature tiene un `index.ts` que exporta solo su API pública
- [ ] Todos los tests pasan después de la reorganización (`npx vitest run` y `npx tsc --noEmit`)
