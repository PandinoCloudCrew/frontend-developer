## Por qué esta actividad

Cuando un usuario visita tu aplicación Angular, el navegador descarga un archivo JavaScript, lo ejecuta, y entonces renderiza la página. Esto se llama **CSR (Client-Side Rendering)** y tiene un problema: hasta que el JavaScript se descarga y ejecuta, el usuario ve una pantalla en blanco. Google tampoco puede indexar bien tu contenido porque el HTML inicial está vacío.

Hay alternativas: **SSR** (Server-Side Rendering) renderiza el HTML en el servidor antes de enviarlo al navegador — el usuario ve contenido inmediatamente. **SSG** (Static Site Generation) genera el HTML en tiempo de build — perfecto para contenido que no cambia frecuentemente. **ISR** (Incremental Static Regeneration) combina ambos: genera HTML estático pero lo actualiza periódicamente.

Ninguna estrategia es "la mejor" — cada una es correcta para un tipo de contenido. Elegir la incorrecta desperdicia recursos o perjudica la experiencia del usuario.

> **Pilares de diseño:** Esta actividad ejercita **Mantenibilidad** (elegir la estrategia correcta simplifica la arquitectura) y **Rendimiento** (la estrategia correcta reduce el TTI — Time to Interactive).

## Antes de empezar

Necesitas haber completado la **Actividad 8.1** — tu proyecto está organizado por features.

**¿Qué es renderizado?** Es el proceso de convertir tu código (TypeScript, HTML, CSS) en lo que el usuario ve en pantalla. Hay diferentes momentos en los que esto puede ocurrir:

| Estrategia | Cuándo se genera el HTML | Ideal para |
|-----------|--------------------------|------------|
| **CSR** (Client-Side Rendering) | En el navegador del usuario, después de descargar el JavaScript | Dashboards privados, aplicaciones internas |
| **SSR** (Server-Side Rendering) | En el servidor, en cada petición del usuario | Contenido personalizado, datos en tiempo real |
| **SSG** (Static Site Generation) | En tiempo de build, una vez | Blogs, documentación, landing pages |
| **ISR** (Incremental Static Regeneration) | En tiempo de build + re-genera periódicamente | E-commerce, catálogos que cambian cada hora |

**¿Qué es TTI?** TTI (Time to Interactive) es el tiempo que pasa desde que el usuario hace click en un enlace hasta que la página está completamente interactiva (puede hacer click en botones, escribir en inputs). Un TTI menor a 3 segundos es bueno; mayor a 5 segundos es malo.

**¿Qué es SEO?** SEO (Search Engine Optimization) es la capacidad de tu página para ser indexada por Google. Si tu HTML inicial está vacío (CSR puro), Google tiene dificultades para indexar el contenido. SSR y SSG resuelven esto porque el HTML ya tiene contenido cuando Google lo lee.

**¿Qué es Analog?** Es un meta-framework para Angular (similar a lo que Next.js es para React o Nuxt para Vue). Permite hacer SSR, SSG e ISR con Angular de forma sencilla. Usa Vite como herramienta de build, lo que lo hace más rápido que Angular Universal clásico.

### Paso 1 — Identificar 3 tipos de página

Elige 3 páginas de tu aplicación (o imagínalas si tu proyecto es pequeño):

1. **Página de blog/docs** — contenido que cambia raramente (cada semana o menos)
2. **Dashboard privado** — contenido personalizado por usuario, datos en tiempo real
3. **Listado de productos (e-commerce)** — contenido que cambia frecuentemente pero no es personalizado

### Paso 2 — Analizar requisitos de cada página

Para cada página, responde estas 4 preguntas:

| Pregunta | Blog | Dashboard | Listado |
|----------|------|-----------|---------|
| ¿Con qué frecuencia cambian los datos? | Semanal | Segundos | Horaria |
| ¿Necesita SEO? | Sí (Google debe indexar) | No (privado, requiere login) | Sí (usuarios buscan productos) |
| ¿Es personalizado por usuario? | No (igual para todos) | Sí (cada usuario ve sus datos) | No (mismo catálogo para todos) |
| ¿Cuál es el TTI aceptable? | < 2s (usuario impaciente) | < 3s (usuario cautivo) | < 2s (usuario compara) |

### Paso 3 — Elegir y justificar la estrategia

Basándote en el análisis:

- **Blog** → **SSG**: El contenido no cambia frecuentemente, necesita SEO, y no es personalizado. Generar HTML estático en build time es la opción más rápida (TTI ~ 0.5s, es solo HTML).

- **Dashboard** → **CSR** (o SSR si necesitas TTI rápido): Es personalizado y privado — no necesita SEO. CSR es suficiente. Si el TTI es crítico, puedes usar SSR para enviar el esqueleto del dashboard inmediatamente.

- **Listado de productos** → **ISR**: Necesita SEO (descarta CSR), cambia frecuentemente (descarta SSG puro), pero no es personalizado (no necesita SSR en cada petición). ISR genera HTML estático y lo re-genera cada X minutos.

### Paso 5 — Implementar SSR para contenido dinámico

1. Implementa una pagina con SSR:

::: code-group

```typescript [Angular]
// src/app/pages/dashboard.page.ts (Analog)
import { Component, inject, OnInit, signal } from '@angular/core';
import { HttpClient } from '@angular/common/http';

@Component({
  standalone: true,
  template: `
    <h1>Dashboard</h1>
    @if (loading()) {
      <p>Cargando tus datos...</p>
    } @else {
      <p>Bienvenido, {{ userName() }}</p>
    }
  `,
})
export default class DashboardPageComponent implements OnInit {
  private http = inject(HttpClient);
  userName = signal('');
  loading = signal(true);

  async ngOnInit(): Promise<void> {
    // En SSR, esta petición se ejecuta en el servidor
    this.http.get<{ name: string }>('/api/me').subscribe(user => {
      this.userName.set(user.name);
      this.loading.set(false);
    });
  }
}
```

<<< @/snippets/react/act-8.5-02.tsx [React]

:::

2. La diferencia con CSR: en CSR, el usuario descarga el JavaScript, luego ejecuta la petición HTTP desde el navegador, luego renderiza. En SSR, el servidor ejecuta la petición, renderiza el HTML, y envía HTML con datos al navegador — el usuario ve contenido inmediatamente.

### Paso 6 — Documentar la decisión

1. Crea un documento de decisión técnica (ADR — Architecture Decision Record). Crea `docs/adr/001-rendering-strategies.md`:

   ```markdown
   # ADR 001: Estrategias de renderizado por tipo de página

   ## Contexto
   La aplicación tiene 3 tipos de páginas con requisitos diferentes
   de SEO, frecuencia de actualización y personalización.

   ## Decisión

   | Página | Estrategia | Justificación |
   |--------|-----------|---------------|
   | Blog | SSG | Contenido estático, necesita SEO, TTI < 1s |
   | Dashboard | CSR | Personalizado, privado, no necesita SEO |
   | Listado | ISR (revalidar cada 30 min) | Necesita SEO, cambia frecuentemente, no personalizado |

   ## Consecuencias
   - Blog: build time aumenta con cada nuevo post (aceptable)
   - Dashboard: primera carga más lenta (aceptable, usuario cautivo)
   - Listado: datos pueden tener hasta 30 min de retraso (aceptable para catálogo)
   ```

## Qué puede salir mal

- **"¿Qué es ISR? Angular no lo soporta nativamente"** → ISR es un concepto popularizado por Next.js. En Angular, puedes lograrlo con Analog + `prerender` con revalidación, o usando un CDN con cache headers (`stale-while-revalidate`). La idea es la misma: servir HTML estático pero regenerarlo periódicamente.
- **"Mi aplicación completa es un dashboard — ¿necesito SSR?"** → No necesariamente. Si toda tu app requiere login y no necesita SEO, CSR puede ser suficiente. SSR agrega complejidad (necesitas un servidor Node.js). Úsalo cuando el beneficio lo justifique.
- **"SSR con Angular es lento"** → Verifica que no estás haciendo peticiones HTTP innecesarias en el servidor. Usa `TransferState` para evitar duplicar peticiones entre servidor y cliente.
- **"No sé qué TTI tiene mi aplicación actual"** → Abre DevTools → Lighthouse → Performance. El TTI aparece en los resultados. También puedes usar WebPageTest.org para medirlo desde diferentes ubicaciones.
