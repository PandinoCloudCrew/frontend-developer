## Por qué esta actividad

En la Actividad 8.1 organizaste código por features. Pero dentro de cada feature, ¿cómo separas la lógica de negocio de la UI? Si tu componente mezcla validaciones, llamadas a API, transformación de datos y renderizado, cambiar un framework (o simplemente refactorizar) requiere reescribir todo.

**Clean Architecture** separa tu código en capas con responsabilidades claras. La capa de dominio (las reglas de negocio) no sabe si estás usando Angular, React o una terminal. Esto hace que la lógica sea testeable sin UI, reutilizable entre proyectos, y sobreviva cambios de framework.

> **Pilar de diseño:** Esta actividad ejercita **Mantenibilidad** — separar la lógica de negocio del framework permite cambiar uno sin reescribir el otro.

## Antes de empezar

Necesitas haber completado la **Actividad 8.1** — tu proyecto está organizado por features.

**¿Qué es Clean Architecture?** Es un patrón de organización de código inventado por Robert C. Martin ("Uncle Bob") que separa el software en capas. La regla fundamental es: **las capas internas no conocen las capas externas**. La lógica de negocio (capa interna) no sabe si la UI es Angular, React o una terminal. La capa de UI (externa) conoce la lógica de negocio, pero no al revés.

**Las 4 capas en frontend:**

| Capa | Responsabilidad | Ejemplo |
|------|----------------|---------|
| **Presentation** | UI, componentes, templates | `ProductListComponent`, plantillas HTML |
| **Application** | Casos de uso, coordinación | `AddToCartUseCase` — coordina dominio + infraestructura |
| **Domain** | Reglas de negocio, entidades, validaciones | `calculateDiscount()`, `Product`, `isValidPrice()` |
| **Infrastructure** | APIs externas, almacenamiento, librerías de terceros | `ProductApiService`, `LocalStorageService` |

**Regla de dependencia:** Presentation -> Application -> Domain <- Infrastructure. El dominio NO importa nada de las otras capas.

### Paso 1 — Elegir una feature compleja

Elige una feature que tenga lógica de negocio real — no solo mostrar datos. Ejemplos:
- **Carrito de compras:** calcular totales, aplicar descuentos, validar stock
- **Facturación:** calcular impuestos, validar datos fiscales
- **Reservaciones:** verificar disponibilidad, calcular precios por fecha

Para este ejemplo usaremos un "carrito de compras".

### Paso 2 — Crear la estructura de 4 capas

1. Dentro de tu feature, crea las carpetas de las capas:
   ```bash
   mkdir -p src/app/features/cart/domain
   mkdir -p src/app/features/cart/application
   mkdir -p src/app/features/cart/infrastructure
   mkdir -p src/app/features/cart/presentation
   ```

2. La estructura resultante:
   ```
   src/app/features/cart/
     domain/          ← Reglas de negocio (puro TypeScript, cero Angular)
     application/     ← Casos de uso (coordinan dominio + infraestructura)
     infrastructure/  ← APIs, storage (Angular HttpClient, localStorage)
     presentation/    ← Componentes Angular (UI)
     index.ts         ← API pública del feature
   ```

### Paso 3 — Extraer la capa de dominio

La capa de dominio contiene las entidades y la lógica de negocio. **No importa Angular, ni HttpClient, ni ninguna librería externa.**

1. Crea `src/app/features/cart/domain/cart-item.ts`:
   ```typescript
   export interface CartItem {
     productId: number;
     name: string;
     unitPrice: number;
     quantity: number;
   }

   export function calculateItemTotal(item: CartItem): number {
     return item.unitPrice * item.quantity;
   }

   export function isValidQuantity(quantity: number): boolean {
     return Number.isInteger(quantity) && quantity > 0 && quantity <= 99;
   }
   ```

2. Crea `src/app/features/cart/domain/cart.ts`:
   ```typescript
   import { CartItem, calculateItemTotal } from './cart-item';

   export interface Cart {
     items: CartItem[];
     discountPercent: number;
   }

   export function calculateSubtotal(cart: Cart): number {
     return cart.items.reduce((sum, item) => sum + calculateItemTotal(item), 0);
   }

   export function calculateDiscount(cart: Cart): number {
     const subtotal = calculateSubtotal(cart);
     return subtotal * (cart.discountPercent / 100);
   }

   export function calculateTotal(cart: Cart): number {
     return calculateSubtotal(cart) - calculateDiscount(cart);
   }

   export function canCheckout(cart: Cart): boolean {
     return cart.items.length > 0 && calculateTotal(cart) > 0;
   }
   ```

> 💡 **Nota:** Observa que estas funciones son TypeScript puro. No importan `@angular/core`, no usan `inject()`, no necesitan un navegador para ejecutarse. Esto es intencional — la lógica de negocio no debe depender del framework.

### Paso 4 — Crear la capa de infraestructura

La capa de infraestructura maneja la comunicación con el mundo externo. Aquí SÍ usas Angular.

1. Define un puerto (interfaz) que el dominio espera. Crea `src/app/features/cart/domain/cart.port.ts`:
   ```typescript
   import { Cart } from './cart';

   export interface CartRepository {
     load(): Promise<Cart>;
     save(cart: Cart): Promise<void>;
   }
   ```

2. Implementa el puerto con Angular. Crea `src/app/features/cart/infrastructure/cart-api.repository.ts`:
   ```typescript
   import { Injectable, inject } from '@angular/core';
   import { HttpClient } from '@angular/common/http';
   import { firstValueFrom } from 'rxjs';
   import { Cart } from '../domain/cart';
   import { CartRepository } from '../domain/cart.port';

   @Injectable({ providedIn: 'root' })
   export class CartApiRepository implements CartRepository {
     private http = inject(HttpClient);

     async load(): Promise<Cart> {
       return firstValueFrom(this.http.get<Cart>('/api/cart'));
     }

     async save(cart: Cart): Promise<void> {
       await firstValueFrom(this.http.put('/api/cart', cart));
     }
   }
   ```

> 💡 **Nota:** La interfaz `CartRepository` vive en `domain/` porque el dominio define lo que necesita. La implementación vive en `infrastructure/` porque depende de Angular `HttpClient`. Si mañana cambias de API REST a GraphQL, solo cambias la implementación — el dominio no se toca.

### Paso 5 — Crear la capa de aplicación

La capa de aplicación coordina dominio e infraestructura. Los "casos de uso" viven aquí.

1. Crea `src/app/features/cart/application/add-to-cart.use-case.ts`:
   ```typescript
   import { Injectable, inject } from '@angular/core';
   import { CartApiRepository } from '../infrastructure/cart-api.repository';
   import { isValidQuantity } from '../domain/cart-item';
   import { CartItem } from '../domain/cart-item';

   @Injectable({ providedIn: 'root' })
   export class AddToCartUseCase {
     private cartRepo = inject(CartApiRepository);

     async execute(item: Omit<CartItem, 'quantity'>, quantity: number): Promise<void> {
       if (!isValidQuantity(quantity)) {
         throw new Error(`Cantidad inválida: ${quantity}. Debe ser entre 1 y 99.`);
       }

       const cart = await this.cartRepo.load();
       const existingItem = cart.items.find(i => i.productId === item.productId);

       if (existingItem) {
         existingItem.quantity += quantity;
       } else {
         cart.items.push({ ...item, quantity });
       }

       await this.cartRepo.save(cart);
     }
   }
   ```

### Paso 6 — Conectar en la capa de presentación

El componente Angular solo se encarga de la UI — delega toda la lógica al caso de uso:

1. Crea (o actualiza) `src/app/features/cart/presentation/cart-summary.component.ts`:
   ```typescript
   import { Component, inject, signal, OnInit } from '@angular/core';
   import { CartApiRepository } from '../infrastructure/cart-api.repository';
   import { calculateTotal, calculateSubtotal, Cart } from '../domain/cart';

   @Component({
     selector: 'app-cart-summary',
     standalone: true,
     template: `
       @if (cart(); as c) {
         <p>Subtotal: {{ subtotal() | currency }}</p>
         <p>Total: {{ total() | currency }}</p>
       }
     `,
   })
   export class CartSummaryComponent implements OnInit {
     private cartRepo = inject(CartApiRepository);
     cart = signal<Cart | null>(null);

     subtotal = () => this.cart() ? calculateSubtotal(this.cart()!) : 0;
     total = () => this.cart() ? calculateTotal(this.cart()!) : 0;

     async ngOnInit(): Promise<void> {
       this.cart.set(await this.cartRepo.load());
     }
   }
   ```

### Paso 7 — Testear el dominio sin UI

La prueba de que la separación funciona: los tests de dominio no necesitan Angular ni un navegador.

1. Crea `src/app/features/cart/domain/cart.test.ts`:
   ```typescript
   import { describe, test, expect } from 'vitest';
   import { calculateTotal, calculateSubtotal, canCheckout, Cart } from './cart';

   describe('Cart domain', () => {
     const cart: Cart = {
       items: [
         { productId: 1, name: 'Laptop', unitPrice: 1000, quantity: 1 },
         { productId: 2, name: 'Mouse', unitPrice: 25, quantity: 2 },
       ],
       discountPercent: 10,
     };

     test('calcula subtotal correctamente', () => {
       expect(calculateSubtotal(cart)).toBe(1050);
     });

     test('calcula total con descuento', () => {
       expect(calculateTotal(cart)).toBe(945); // 1050 - 10%
     });

     test('permite checkout con items', () => {
       expect(canCheckout(cart)).toBe(true);
     });

     test('no permite checkout con carrito vacío', () => {
       const emptyCart: Cart = { items: [], discountPercent: 0 };
       expect(canCheckout(emptyCart)).toBe(false);
     });
   });
   ```

2. Ejecuta solo los tests de dominio:
   ```bash
   npx vitest run src/app/features/cart/domain/
   ```
   Deben pasar sin necesitar `jsdom`, sin Angular, sin un navegador.

## Qué puede salir mal

- **"El dominio necesita importar HttpClient"** → Estás poniendo lógica de infraestructura en el dominio. Extrae la llamada HTTP a un servicio de infraestructura y pasa los datos al dominio como parámetros.
- **"¿Necesito 4 capas para una feature simple?"** → No. Clean Architecture tiene sentido para features con lógica de negocio compleja. Una página estática o un CRUD simple no lo necesita. Aplícalo donde el beneficio justifique la complejidad.
- **"Los tests de dominio importan cosas de Angular"** → Revisa los imports del archivo de dominio. Si ves `@angular/core`, `HttpClient`, o `inject`, esa lógica pertenece a otra capa.
- **"No sé qué va en Application vs Domain"** → Domain = reglas de negocio (cálculos, validaciones, entidades). Application = coordinación (orquestar dominio + infraestructura para completar un caso de uso).

## Resultado esperado

Una feature de tu proyecto está organizada en 4 capas de Clean Architecture. La capa de dominio es TypeScript puro sin dependencias de framework. Los tests de dominio se ejecutan sin renderizar UI ni necesitar un navegador.

**Criterios de aceptación:**
- [ ] La capa de dominio no importa `@angular/core`, `HttpClient`, ni ninguna librería de framework
- [ ] Los tests de dominio se ejecutan sin renderizar UI (no necesitan `jsdom` ni TestBed)
- [ ] La capa de infraestructura implementa una interfaz definida en el dominio (inversión de dependencias)
- [ ] `npx tsc --noEmit` pasa sin errores después de la reorganización
