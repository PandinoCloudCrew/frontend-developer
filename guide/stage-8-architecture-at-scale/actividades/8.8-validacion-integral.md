## Por qué esta actividad

Esta es la última etapa de la guía. Antes de considerarte listo para trabajar como frontend developer, necesitas confirmar que dominas los patrones de arquitectura a escala. No se trata de memorizar conceptos — se trata de poder tomar decisiones informadas: cuándo organizar por features, cuándo aplicar Clean Architecture, cuándo un design system tiene sentido, cuándo un monorepo es excesivo.

> **Pilar de diseño:** Esta actividad ejercita **Mantenibilidad** — la validación integral confirma que puedes construir y mantener aplicaciones que escalan con el equipo y con los requisitos.

Necesitas haber completado todas las actividades anteriores de esta etapa. Si alguna está pendiente, complétala primero.

Esta validación integral es tu última oportunidad de detectar brechas. Tómate el tiempo necesario para cada verificación.

### Paso 1 — Verificar organización por features (8.1)

1. Verifica cero dependencias circulares:
   ```bash
   npx madge --circular --extensions ts src/
   ```
   Debe reportar cero ciclos.

2. Verifica que cada feature tiene un `index.ts`:
   ```bash
   find src/app/features -name "index.ts" -type f
   ```
   Debe haber uno por feature.

3. Ejecuta todos los tests:
   ```bash
   npx vitest run
   ```

### Paso 2 — Verificar Clean Architecture (8.2)

1. Verifica que la capa de dominio no importa Angular:
   ```bash
   grep -r "@angular" src/app/features/*/domain/ --include="*.ts"
   ```
   Debe no encontrar resultados.

2. Ejecuta los tests de dominio sin `jsdom`:
   ```bash
   npx vitest run src/app/features/*/domain/
   ```
   Deben pasar sin necesitar un navegador.

### Paso 3 — Verificar design system (8.3)

1. Verifica que los componentes usan design tokens:
   ```bash
   grep -r "var(--" src/app/design-system/ --include="*.ts" --include="*.css" | head -10
   ```
   Debe mostrar usos de CSS custom properties.

2. Verifica que el design system exporta desde un `index.ts`:
   ```bash
   cat src/app/design-system/index.ts
   ```

### Paso 4 — Verificar type safety (8.4)

1. Ejecuta la verificación de tipos:
   ```bash
   npx tsc --noEmit
   ```
   Cero errores.

2. Verifica que los esquemas Zod existen:
   ```bash
   grep -r "z.object\|z.array\|z.string" src/ --include="*.ts" -l
   ```

### Paso 5 — Verificar estrategias de renderizado (8.5)

1. Verifica que existe un ADR de estrategias de renderizado:
   ```bash
   ls docs/adr/*rendering* 2>/dev/null || ls docs/adr/*render* 2>/dev/null
   ```

2. Verifica que la justificación cubre frecuencia de datos, SEO, personalización y TTI.

### Paso 6 — Verificar build (8.6)

1. Ejecuta el build de producción:
   ```bash
   ng build --configuration production
   ```

2. Verifica que hay chunks separados (más de solo `main.js`):
   ```bash
   ls dist/*/browser/chunk-* 2>/dev/null || ls dist/*/browser/*-*.js | wc -l
   ```
   Debe haber al menos 3 archivos JavaScript.

### Paso 7 — Verificar decisión de repositorio (8.7)

1. Verifica que existe un ADR de estrategia de repositorio:
   ```bash
   ls docs/adr/*repo* 2>/dev/null || ls docs/adr/*monorepo* 2>/dev/null
   ```

2. Revisa que la justificación menciona trade-offs concretos y se basa en el contexto del proyecto.

### Paso 8 — Checklist final

**8.1 — Organización por features:**
- [ ] Cero dependencias circulares
- [ ] Cada feature tiene sus componentes, servicios y tipos
- [ ] Cada feature tiene `index.ts` con API pública
- [ ] Tests pasan después de reorganización

**8.2 — Clean Architecture:**
- [ ] Domain layer no importa Angular
- [ ] Tests de dominio pasan sin UI
- [ ] Infrastructure implementa interfaces del dominio

**8.3 — Design System:**
- [ ] Al menos 5 componentes reutilizables
- [ ] Todos usan design tokens
- [ ] Cambiar token se propaga a todos los componentes

**8.4 — API Type-safe:**
- [ ] Esquemas Zod definen las respuestas de API
- [ ] Validación en runtime con `safeParse`
- [ ] `npx tsc --noEmit` pasa

**8.5 — Estrategias de renderizado:**
- [ ] 3 tipos de página analizados
- [ ] Estrategia correcta para cada tipo
- [ ] Decisión documentada en ADR

**8.6 — Build:**
- [ ] Chunks separados por feature
- [ ] Aliases de importación funcionan
- [ ] Variables de entorno configuradas

**8.7 — Monorepos/micro-frontends:**
- [ ] Decisión documentada en ADR
- [ ] Al menos 3 trade-offs por enfoque
- [ ] Justificación basada en contexto real

## Qué puede salir mal

- **"No completé todas las actividades previas"** → Vuelve a las que faltan. La validación integral no tiene sentido si hay brechas fundamentales.
- **"Algunos criterios no aplican a mi proyecto"** → Está bien. Si tu proyecto es pequeño, Clean Architecture o micro-frontends pueden no ser necesarios. Lo importante es que entiendes cuándo SÍ se necesitan y puedes justificar tu decisión.
- **"Los tests fallan después de tanta reorganización"** → Ejecuta `npx tsc --noEmit` primero para identificar imports rotos. Luego ejecuta los tests. La mayoría de los fallos después de reorganización son imports con rutas incorrectas.
