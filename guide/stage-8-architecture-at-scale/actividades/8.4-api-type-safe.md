# 🟡 Actividad 8.4 — Implementar capa de API type-safe

[Inicio](../../README.md) > [Etapa 8](../README.md) > Actividad 8.4

- [ ] Completada

**Duración:** ~60 min

## Por qué esta actividad

Tu frontend habla con un backend a través de una API. El backend envía un JSON y tu frontend lo consume. Pero ¿qué pasa si el backend cambia la forma de la respuesta (renombra un campo, agrega un campo obligatorio, cambia un `number` a `string`) y nadie le avisa al frontend? El código compila, los tests de mocks pasan (porque los mocks son viejos), y la aplicación se rompe en producción.

Una **API type-safe** garantiza que si el backend cambia algo, TypeScript te lo dice inmediatamente — antes de ejecutar el código, antes de hacer deploy, antes de que el usuario lo vea. Cambiar un tipo en el backend produce un error de compilación en el frontend.

> **Pilar de diseño:** Esta actividad ejercita **Mantenibilidad** — type safety end-to-end elimina una clase entera de bugs (desincronización frontend/backend) que son difíciles de detectar con tests tradicionales.

## Antes de empezar

Necesitas haber completado la **Actividad 8.2** — entiendes la separación entre capas de dominio e infraestructura.

**¿Qué es type safety end-to-end?** Es cuando los tipos TypeScript del frontend y del backend están conectados. Si cambias un tipo en un extremo, el otro extremo ve el error de tipos inmediatamente — no en producción, sino durante el desarrollo.

**¿Qué es Zod?** Es una librería de validación de esquemas para TypeScript. Define la forma esperada de los datos y verifica en runtime que los datos reales coinciden. A diferencia de las interfaces TypeScript (que se borran en la compilación), Zod verifica en runtime — detecta problemas cuando la API devuelve datos inesperados.

**¿Qué es tRPC?** Es un framework que conecta un backend TypeScript con un frontend TypeScript sin necesidad de generar código. El frontend importa los tipos directamente del backend. Es la opción más sencilla si controlas ambos extremos y ambos usan TypeScript.

**¿Qué es OpenAPI?** Es una especificación estándar para describir APIs REST. Puedes generar tipos TypeScript a partir de un documento OpenAPI. Es la mejor opción cuando el backend no es TypeScript o cuando no controlas el backend.

### Paso 1 — Instalar Zod

1. En la terminal de VS Code, ejecuta:
   ```bash
   npm install zod
   ```

2. Zod funciona con TypeScript `strict: true`. Verifica que tu `tsconfig.json` tiene:
   ```json
   {
     "compilerOptions": {
       "strict": true
     }
   }
   ```

### Paso 2 — Definir esquemas de validación

En lugar de solo definir interfaces (que se borran en compilación), define esquemas Zod que validan en runtime:

1. Crea `src/app/features/products/models/product.schema.ts`:
   ```typescript
   import { z } from 'zod';

   // Define el esquema — describe la forma esperada de los datos
   export const ProductSchema = z.object({
     id: z.number(),
     name: z.string().min(1),
     price: z.number().positive(),
     category: z.string(),
     inStock: z.boolean(),
   });

   // Infiere el tipo TypeScript a partir del esquema
   // Esto garantiza que el tipo y la validación siempre coinciden
   export type Product = z.infer<typeof ProductSchema>;

   export const ProductsResponseSchema = z.object({
     products: z.array(ProductSchema),
     total: z.number(),
   });

   export type ProductsResponse = z.infer<typeof ProductsResponseSchema>;
   ```

> 💡 **Nota:** `z.infer<typeof ProductSchema>` genera automáticamente el tipo TypeScript. No necesitas mantener el tipo y el esquema por separado — el esquema ES la fuente de verdad.

### Paso 3 — Validar respuestas de API en runtime

Crea una función que valida la respuesta antes de usarla:

1. Crea `src/app/shared/utils/api-validator.ts`:
   ```typescript
   import { z } from 'zod';

   export function validateResponse<T>(
     schema: z.ZodSchema<T>,
     data: unknown,
     endpoint: string,
   ): T {
     const result = schema.safeParse(data);

     if (!result.success) {
       console.error(
         `API response validation failed for ${endpoint}:`,
         result.error.format(),
       );
       throw new Error(
         `La respuesta de ${endpoint} no tiene la forma esperada. ` +
         `Campos con error: ${result.error.issues.map(i => i.path.join('.')).join(', ')}`,
       );
     }

     return result.data;
   }
   ```

### Paso 4 — Integrar en el servicio Angular

1. Actualiza tu servicio de API para validar las respuestas:
   ```typescript
   // src/app/features/products/infrastructure/product-api.service.ts
   import { Injectable, inject } from '@angular/core';
   import { HttpClient } from '@angular/common/http';
   import { firstValueFrom } from 'rxjs';
   import { ProductsResponseSchema, ProductsResponse } from '../models/product.schema';
   import { validateResponse } from '../../../shared/utils/api-validator';

   @Injectable({ providedIn: 'root' })
   export class ProductApiService {
     private http = inject(HttpClient);

     async getProducts(): Promise<ProductsResponse> {
       const data = await firstValueFrom(
         this.http.get<unknown>('/api/products'),
       );

       // Valida la respuesta en runtime — si la API devuelve algo inesperado, falla aquí
       return validateResponse(ProductsResponseSchema, data, '/api/products');
     }
   }
   ```

> 💡 **Nota:** Observa que el `http.get` usa `<unknown>` en lugar de `<ProductsResponse>`. Esto es intencional: no confiamos ciegamente en que la API devuelve lo correcto — lo validamos.

### Paso 5 — Provocar error de tipo

Para verificar que la validación funciona:

1. Simula una respuesta incorrecta. Si tienes un handler MSW (de la Actividad 7.2), modifícalo para devolver un campo con tipo incorrecto:
   ```typescript
   // En src/mocks/handlers.ts — cambia price de number a string
   http.get('/api/products', () => {
     return HttpResponse.json({
       products: [
         { id: 1, name: 'Laptop', price: '999', category: 'electronics', inStock: true },
         //                        ^^^^^ string en lugar de number
       ],
       total: 1,
     });
   }),
   ```

2. Ejecuta los tests:
   ```bash
   npx vitest run
   ```
   El test debe fallar con un mensaje claro: "La respuesta de /api/products no tiene la forma esperada. Campos con error: products.0.price"

3. Ahora ejecuta la verificación de tipos estática:
   ```bash
   npx tsc --noEmit
   ```
   TypeScript también debe marcar el error si el handler MSW usa el tipo `ProductsResponse`.

4. Revierte el cambio en el handler MSW.

### Paso 6 — Verificar type safety

1. Cambia el esquema para agregar un nuevo campo obligatorio:
   ```typescript
   // En product.schema.ts, agrega un campo:
   export const ProductSchema = z.object({
     id: z.number(),
     name: z.string().min(1),
     price: z.number().positive(),
     category: z.string(),
     inStock: z.boolean(),
     sku: z.string(), // nuevo campo obligatorio
   });
   ```

2. Ejecuta `npx tsc --noEmit`. Deberías ver errores en:
   - Los handlers MSW (no incluyen `sku`)
   - Los componentes que crean objetos `Product` sin `sku`
   - Los tests que usan datos de ejemplo sin `sku`

3. Esto es type safety end-to-end: un cambio en el esquema se propaga a todo el código que lo usa.

4. Revierte el cambio al esquema.

## Qué puede salir mal

- **"Cannot find module 'zod'"** → No instalaste Zod. Ejecuta `npm install zod`.
- **"La validación falla en desarrollo pero la API funciona bien"** → Tu esquema Zod puede ser más estricto que la API real. Usa `z.object({...}).passthrough()` si la API envía campos extras que no te interesan, o `z.partial()` para campos opcionales.
- **"¿Necesito Zod si ya tengo interfaces TypeScript?"** → Las interfaces se borran en compilación — no verifican nada en runtime. Si el backend envía `price: "999"` (string) en lugar de `price: 999` (number), tu interfaz `Product` no detecta el problema. Zod sí.
- **"El equipo del backend no usa TypeScript"** → Usa OpenAPI: pide al equipo de backend que genere un archivo OpenAPI (swagger.json) y genera tipos TypeScript con `npx openapi-typescript swagger.json -o src/api-types.ts`.

## Resultado esperado

Tu capa de API valida las respuestas del backend en runtime con Zod. Los esquemas Zod son la fuente de verdad para los tipos TypeScript. Si el backend cambia la forma de una respuesta, la validación de Zod falla en runtime y `npx tsc --noEmit` falla en compilación.

**Criterios de aceptación:**
- [ ] Los esquemas Zod definen la forma de las respuestas de API (no interfaces manuales separadas)
- [ ] Las respuestas de API se validan en runtime antes de usarlas (con `safeParse`)
- [ ] Cambiar un tipo en el esquema produce errores de TypeScript en los handlers MSW y los componentes (`npx tsc --noEmit`)
- [ ] Una respuesta de API con forma incorrecta falla en runtime con un mensaje descriptivo
