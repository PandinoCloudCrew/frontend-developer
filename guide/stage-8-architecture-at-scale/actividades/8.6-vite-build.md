## Por qué esta actividad

Cuando ejecutas `ng build`, Angular toma tu código TypeScript, tus templates y tu CSS, y los convierte en archivos JavaScript y CSS que el navegador puede entender. Este proceso se llama **build**. Pero ¿sabes qué produce? ¿Por qué el archivo principal pesa 400 KB? ¿Por qué la primera carga tarda 3 segundos?

Entender el build te permite optimizarlo: dividir el código en chunks por feature (lazy loading), configurar aliases para imports más limpios, y manejar variables de entorno sin exponer secretos. **Vite** es la herramienta de build que Angular usa internamente desde la versión 17 — es más rápida que Webpack y más fácil de configurar.

> **Pilar de diseño:** Esta actividad ejercita **Mantenibilidad** (un build organizado por features facilita el debugging) y **Rendimiento** (chunks separados permiten cargar solo el código necesario).

## Antes de empezar

Necesitas haber completado la **Actividad 8.1** — tu proyecto está organizado por features con lazy loading.

**¿Qué es un build?** Es el proceso de convertir tu código fuente (TypeScript, SCSS, templates HTML) en archivos que el navegador entiende (JavaScript, CSS). Durante el build, el código se compila, se minifica (se reduce su tamaño), se divide en chunks (archivos más pequeños), y se generan hashes para cache (para que el navegador sepa cuándo actualizar).

**¿Qué es un chunk?** Es un pedazo del código resultante del build. En lugar de tener un solo archivo JavaScript gigante (`main.js` de 2 MB), el build divide tu código en varios archivos más pequeños. Cuando el usuario navega a la sección de "productos", el navegador solo descarga el chunk de productos — no todo el código de la aplicación.

**¿Qué es Vite?** Es una herramienta de build creada por Evan You (creador de Vue.js). Es significativamente más rápida que Webpack porque usa ESModules nativos del navegador durante el desarrollo (no necesita bundlear todo) y Rollup para el build de producción. Angular adoptó Vite como builder predeterminado desde la versión 17.

**¿Qué es un alias?** Es un atajo para importar archivos. En lugar de escribir `import { Product } from '../../../features/products/models/product.model'`, configuras un alias `@products` y escribes `import { Product } from '@products'`.

### Paso 1 — Ejecutar build y analizar output

1. Ejecuta el build de producción:
   ```bash
   ng build --configuration production
   ```

2. Observa los archivos generados:
   ```bash
   ls -lh dist/tu-proyecto/browser/
   ```

3. Fíjate en:
   - `main-[hash].js` — el código principal de tu aplicación
   - `polyfills-[hash].js` — compatibilidad con navegadores viejos
   - `styles-[hash].css` — tu CSS compilado
   - Si ves un solo `main.js` de más de 200 KB, todo tu código está en un bundle — esto se puede mejorar

4. Para ver el tamaño detallado por feature:
   ```bash
   ng build --configuration production --stats-json
   ```
   Esto genera un `stats.json` que puedes analizar con herramientas visuales.

### Paso 2 — Configurar lazy loading por features

Lazy loading hace que cada feature se cargue solo cuando el usuario lo necesita. En Angular, se configura en las rutas:

1. Abre tu archivo de rutas (`src/app/app.routes.ts`) y configura lazy loading:
   ```typescript
   import { Routes } from '@angular/router';

   export const routes: Routes = [
     {
       path: 'products',
       loadComponent: () =>
         import('./features/products/presentation/product-list.component')
           .then(m => m.ProductListComponent),
     },
     {
       path: 'cart',
       loadComponent: () =>
         import('./features/cart/presentation/cart-summary.component')
           .then(m => m.CartSummaryComponent),
     },
     {
       path: 'auth',
       loadChildren: () =>
         import('./features/auth/auth.routes')
           .then(m => m.AUTH_ROUTES),
     },
   ];
   ```

> 💡 **Nota:** `loadComponent` y `loadChildren` usan `import()` dinámico. Vite detecta estos imports y genera un chunk separado para cada uno. El código de "productos" solo se descarga cuando el usuario navega a `/products`.

### Paso 3 — Configurar aliases de importación

1. Abre `tsconfig.json` y agrega aliases en `paths`:
   ```json
   {
     "compilerOptions": {
       "baseUrl": "src",
       "paths": {
         "@products/*": ["app/features/products/*"],
         "@cart/*": ["app/features/cart/*"],
         "@auth/*": ["app/features/auth/*"],
         "@shared/*": ["app/shared/*"],
         "@design-system": ["app/design-system/index.ts"]
       }
     }
   }
   ```

2. Ahora puedes importar con rutas más limpias:
   ```typescript
   // Antes:
   import { Product } from '../../../features/products/models/product.schema';
   import { DsButtonComponent } from '../../../design-system';

   // Después:
   import { Product } from '@products/models/product.schema';
   import { DsButtonComponent } from '@design-system';
   ```

3. Angular con Vite (v17+) resuelve los aliases de `tsconfig.json` automáticamente — no necesitas configuración adicional en Vite.

### Paso 4 — Configurar variables de entorno

1. Crea los archivos de entorno si no existen:
   ```bash
   mkdir -p src/environments
   ```

2. Crea `src/environments/environment.ts` (desarrollo):
   ```typescript
   export const environment = {
     production: false,
     apiUrl: 'http://localhost:3000/api',
     featureFlags: {
       newDashboard: true,
     },
   };
   ```

3. Crea `src/environments/environment.production.ts`:
   ```typescript
   export const environment = {
     production: true,
     apiUrl: 'https://api.tu-app.com',
     featureFlags: {
       newDashboard: false,
     },
   };
   ```

4. En `angular.json`, configura el reemplazo de archivos para producción:
   ```json
   "configurations": {
     "production": {
       "fileReplacements": [
         {
           "replace": "src/environments/environment.ts",
           "with": "src/environments/environment.production.ts"
         }
       ]
     }
   }
   ```

5. Usa las variables en tu código:
   ```typescript
   import { environment } from '../../environments/environment';

   const apiUrl = environment.apiUrl; // automáticamente cambia según el entorno
   ```

> 💡 **Nota:** Nunca pongas secretos (API keys, passwords) en archivos de environment — estos archivos se incluyen en el bundle y son visibles para cualquiera que abra DevTools. Los secretos deben estar en el backend.

### Paso 5 — Verificar chunks por feature

1. Ejecuta el build de producción:
   ```bash
   ng build --configuration production
   ```

2. Observa los archivos generados:
   ```bash
   ls -lh dist/tu-proyecto/browser/chunk-*.js
   ```

3. Deberías ver chunks separados con nombres o hashes. Para ver qué contiene cada chunk, puedes usar `source-map-explorer`:
   ```bash
   npm install -D source-map-explorer
   npx source-map-explorer dist/tu-proyecto/browser/main-*.js
   ```
   Esto abre un mapa visual que muestra qué código está en cada chunk.

4. Verifica que:
   - No hay un único `main.js` con todo el código
   - Cada feature tiene su propio chunk
   - El chunk principal (`main.js`) solo contiene el código del shell (router, layout global)

## Qué puede salir mal

- **"No veo chunks separados — todo está en main.js"** → Verifica que tus rutas usan `loadComponent` o `loadChildren` con `import()` dinámico. Si importas los componentes directamente (sin lazy loading), todo queda en el bundle principal.
- **"Los aliases no funcionan — 'Cannot find module @products/...'"** → Verifica que `baseUrl` en `tsconfig.json` es `"src"` y que los paths apuntan a rutas relativas a `src/`. Reinicia el servidor de desarrollo (`ng serve`) después de cambiar `tsconfig.json`.
- **"El build de producción tarda 5 minutos"** → Con Vite (Angular 17+), el build debería ser significativamente más rápido. Si usas Angular 16 o anterior, estás usando Webpack. Considera actualizar.
- **"source-map-explorer no encuentra source maps"** → Agrega `"sourceMap": true` en la configuración de build de producción en `angular.json` (temporalmente — no lo dejes en producción).

## Resultado esperado

Tu build de producción genera chunks separados por feature. Tienes aliases configurados para imports limpios y variables de entorno que cambian entre desarrollo y producción. Entiendes qué produce el build y puedes optimizarlo.

**Criterios de aceptación:**
- [ ] El build produce chunks separados por feature (al menos 2 chunks además de `main.js`)
- [ ] No es un único bundle monolítico — cada feature lazy-loaded tiene su propio chunk
- [ ] Los aliases de importación funcionan (`@products/...`, `@shared/...`)
- [ ] Las variables de entorno cambian entre desarrollo y producción sin modificar código
