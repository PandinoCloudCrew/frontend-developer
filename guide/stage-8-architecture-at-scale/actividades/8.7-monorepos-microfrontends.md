## Por qué esta actividad

Cuando tu proyecto crece de 1 aplicación con 3 developers a 5 aplicaciones con 30 developers, la organización del código se vuelve un problema estratégico. ¿Pones todo en un solo repositorio (monorepo)? ¿Cada equipo tiene su propio repositorio (polyrepo)? ¿Divides la interfaz en aplicaciones independientes que se combinan en el navegador (micro-frontends)?

Estas decisiones son difíciles de revertir y tienen consecuencias a largo plazo. Un monorepo mal gestionado se vuelve un monolito imposible. Micro-frontends mal implementados agregan complejidad sin beneficio. Esta actividad te ayuda a tomar la decisión correcta para tu contexto — no la decisión que tomó Netflix "porque son Netflix".

> **Pilar de diseño:** Esta actividad ejercita **Mantenibilidad** — elegir la estrategia de organización correcta determina la capacidad de tu equipo para trabajar en paralelo sin pisarse.

## Antes de empezar

Necesitas haber completado las **Actividades 8.1-8.6** — entiendes organización por features, design systems y el build.

**¿Qué es un monorepo?** Es un solo repositorio que contiene múltiples proyectos (aplicaciones y librerías). No es lo mismo que un monolito — un monolito es una sola aplicación donde todo está acoplado. Un monorepo tiene múltiples proyectos independientes que comparten el mismo repositorio pero se compilan y despliegan por separado. Google, Meta y Microsoft usan monorepos con miles de proyectos.

**¿Qué es un polyrepo?** Es la alternativa: cada proyecto tiene su propio repositorio. El equipo de "productos" tiene su repo, el equipo de "pagos" tiene otro, el design system tiene otro. Es más simple de entender pero dificulta compartir código.

**¿Qué son los micro-frontends?** Son una arquitectura donde la interfaz de usuario se compone de partes independientes, cada una desarrollada, testeada y desplegada por un equipo diferente. En el navegador, se combinan para parecer una sola aplicación. Piensa en un portal donde el header viene de un equipo, la búsqueda de otro y el catálogo de otro.

**¿Qué es Nx?** Es la herramienta más popular para gestionar monorepos en el ecosistema JavaScript/TypeScript. Nx detecta qué proyectos fueron afectados por un cambio y solo re-compila y re-testea esos proyectos (affected builds). Esto hace viable tener decenas de proyectos en un solo repositorio sin que el CI tarde horas.

### Paso 1 — Evaluar tu contexto actual

Responde estas preguntas sobre tu proyecto o un proyecto hipotético:

1. **¿Cuántos equipos trabajan en el frontend?**
   - 1 equipo → monorepo es suficiente, micro-frontends es excesivo
   - 2-4 equipos → monorepo con Nx es ideal
   - 5+ equipos → evaluar micro-frontends

2. **¿Comparten código entre aplicaciones?**
   - Sí (design system, utilidades, tipos) → monorepo facilita compartir
   - No (aplicaciones completamente independientes) → polyrepo puede ser suficiente

3. **¿Necesitan desplegar independientemente?**
   - No (todo se despliega junto) → monorepo simple
   - Sí (cada equipo despliega cuando quiere) → micro-frontends o monorepo con pipelines independientes

4. **¿Usan el mismo framework?**
   - Sí → monorepo con librerías compartidas
   - No (un equipo usa Angular, otro React) → micro-frontends

### Paso 2 — Analizar trade-offs de cada enfoque

Crea una tabla comparativa:

| Aspecto | Monorepo | Polyrepo | Micro-frontends |
|---------|----------|----------|-----------------|
| **Compartir código** | Fácil (mismo repo) | Difícil (publicar/consumir paquetes) | Moderado (contratos compartidos) |
| **Autonomía de equipos** | Moderada (comparten CI) | Alta (cada equipo es independiente) | Alta (deploy independiente) |
| **Consistencia** | Alta (misma versión de todo) | Baja (cada repo su versión) | Variable (depende de contratos) |
| **Complejidad de CI** | Moderada (affected builds con Nx) | Simple (pipeline por repo) | Alta (integración + pipelines individuales) |
| **Complejidad de setup** | Moderada (Nx, workspace) | Baja (un repo normal) | Alta (Module Federation, routing compartido) |
| **Refactoring cross-cutting** | Fácil (un solo PR) | Difícil (un PR por repo) | Muy difícil (contratos compartidos) |

### Paso 3 — Explorar un monorepo con Nx

Para entender cómo funciona un monorepo, experimenta con Nx:

1. Crea un workspace de Nx con Angular:
   ```bash
   npx create-nx-workspace@latest my-workspace --preset=angular-monorepo --appName=my-app --style=css
   cd my-workspace
   ```

2. Genera una librería compartida:
   ```bash
   npx nx generate @nx/angular:library shared-ui --directory=libs/shared-ui --standalone
   ```

3. Observa la estructura:
   ```
   my-workspace/
     apps/
       my-app/           ← tu aplicación principal
     libs/
       shared-ui/        ← librería compartida (design system)
     nx.json             ← configuración de Nx
   ```

4. Genera otra aplicación:
   ```bash
   npx nx generate @nx/angular:application admin-panel --directory=apps/admin-panel --standalone --style=css
   ```

5. Ahora ambas aplicaciones pueden importar de `shared-ui`:
   ```typescript
   import { SharedUiComponent } from '@my-workspace/shared-ui';
   ```

6. Prueba affected builds — solo re-compila lo necesario:
   ```bash
   npx nx affected --target=build
   ```

### Paso 4 — Evaluar micro-frontends

Los micro-frontends tienen sentido cuando:
- Tienes 5+ equipos que necesitan desplegar independientemente
- Los equipos usan diferentes frameworks (Angular + React)
- La aplicación es un "portal" que combina funcionalidades independientes

Los micro-frontends NO tienen sentido cuando:
- Eres un equipo de 1-4 personas
- Todos usan el mismo framework
- La aplicación tiene mucha interacción entre features
- Lo haces "porque Netflix/Amazon lo usa" (ellos tienen 1000+ developers)

Si decides explorar micro-frontends con Angular:
```bash
# Module Federation con Angular y Nx
npx nx generate @nx/angular:setup-mf my-app --mfType=host
npx nx generate @nx/angular:setup-mf remote-products --mfType=remote --host=my-app
```

> 💡 **Nota:** Module Federation es la implementación más común de micro-frontends. Permite cargar código de diferentes servidores en una sola aplicación. Pero agrega complejidad significativa — no lo uses si no lo necesitas.

### Paso 5 — Documentar la decisión

Crea un ADR (Architecture Decision Record) con tu decisión:

1. Crea `docs/adr/002-repo-strategy.md` (adapta a tu contexto real):

   ```markdown
   # ADR 002: Estrategia de repositorio

   ## Contexto
   El proyecto tiene [N] aplicaciones frontend, [M] desarrolladores,
   y comparten [design system / tipos / utilidades].

   ## Opciones evaluadas

   ### Opción A: Monorepo con Nx
   **Pros:**
   - Compartir código es trivial (import directo)
   - Refactoring cross-cutting en un solo PR
   - Affected builds reducen tiempo de CI

   **Contras:**
   - Setup inicial más complejo
   - CI requiere Nx para ser eficiente
   - Todos comparten la misma versión de Angular

   ### Opción B: Polyrepo
   **Pros:** [...]
   **Contras:** [...]

   ### Opción C: Micro-frontends
   **Pros:** [...]
   **Contras:** [...]

   ## Decisión
   [Tu decisión aquí, con justificación basada en tu contexto]

   ## Consecuencias
   [Qué implica esta decisión a largo plazo]
   ```

2. La decisión debe ser específica a tu contexto — no una respuesta genérica.

## Qué puede salir mal

- **"Nx es muy complicado — ¿realmente lo necesito?"** → Si tienes una sola aplicación y 1-3 developers, probablemente no. Nx agrega valor cuando tienes múltiples aplicaciones o librerías compartidas. Empieza simple y adopta Nx cuando la complejidad lo justifique.
- **"Mi jefe quiere micro-frontends porque leyó un artículo"** → Presenta los trade-offs concretos. Micro-frontends agregan complejidad significativa (routing compartido, estado compartido, consistencia de UI). Solo justifican esa complejidad cuando tienes equipos grandes y autónomos.
- **"¿Monorepo = monolito?"** → No. Un monolito es una aplicación donde todo está acoplado. Un monorepo es una estrategia de organización de repositorios. Puedes tener un monorepo con aplicaciones completamente independientes que se despliegan por separado.
- **"No sé cuántos equipos tendremos en el futuro"** → Empieza con lo más simple (monorepo o incluso un solo repo) y migra cuando el dolor lo justifique. No optimices para un futuro que puede no llegar.

## Resultado esperado

Has evaluado las opciones de organización de repositorios y micro-frontends para tu contexto. Tu decisión está documentada con trade-offs concretos y justificación basada en datos reales (tamaño del equipo, necesidades de deploy, código compartido), no en tendencias.

**Criterios de aceptación:**
- [ ] La decisión está documentada en un ADR con contexto, opciones y justificación
- [ ] Se listan al menos 3 trade-offs concretos por cada enfoque evaluado
- [ ] La decisión se basa en el contexto real del proyecto (tamaño de equipo, necesidades de deploy, código compartido)
- [ ] La justificación NO es "porque X empresa grande lo usa" — es específica a tu situación
