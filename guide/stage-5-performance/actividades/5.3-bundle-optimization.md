## Por que esta actividad

Tu aplicación puede tener un bundle de 500 KB o de 2 MB. La diferencia son segundos de carga — especialmente en redes moviles. Gran parte de ese tamaño viene de **dependencias de terceros** (librerias npm) que a veces ni siquiera usas completamente. Un bundle analyzer te muestra exactamente que ocupa espacio, para que puedas tomar decisiones informadas: eliminar lo innecesario, reemplazar librerias pesadas, o activar tree shaking.

## Antes de empezar

Necesitas tener completada la **Actividad 5.2** y una aplicación con dependencias npm instaladas.

Un **bundle** es el archivo JavaScript final que el navegador descarga. Contiene tu código + el código de todas las librerias que usas. Si instalaste `lodash` para usar una sola función (`_.debounce`), todo lodash (72 KB comprimido) esta en tu bundle.

**Tree shaking** es un proceso que tu herramienta de build hace automáticamente: elimina el código que importaste pero nunca usas. Pero solo funciona con imports nombrados (`import { debounce } from 'lodash-es'`), no con imports por defecto de librerias que no soportan ESModules.

Un **bundle analyzer** es una herramienta que genera un mapa visual de tu bundle — como un treemap — donde cada rectangulo es un archivo o libreria, y su tamaño representa cuanto espacio ocupa.

### Paso 1 — Instalar el bundle analyzer

Para Angular, usa `source-map-explorer`:

1. Abre la terminal en VS Code en la carpeta de tu proyecto
2. Instala la herramienta:
   ```bash
   npm install -D source-map-explorer
   ```
3. Agrega un script a `package.json`:
   ```json
   {
     "scripts": {
       "analyze": "ng build --source-map && source-map-explorer dist/*/browser/*.js"
     }
   }
   ```

> 💡 **Nota:** `--source-map` genera un archivo que mapea el bundle final a los archivos originales. El analyzer usa ese mapa para mostrarte que ocupa espacio.

### Paso 2 — Generar el reporte visual

1. Ejecuta el analisis:
   ```bash
   npm run analyze
   ```
2. Se abre una ventana del navegador con un treemap interactivo
3. Cada rectangulo representa un archivo o libreria:
   - Los rectangulos **grandes** son los que mas espacio ocupan
   - Pasa el mouse sobre cada uno para ver el tamaño exacto
   - Haz click para hacer zoom en una sección
4. Toma una captura de pantalla — la vas a comparar con el resultado final

### Paso 3 — Identificar las 3 dependencias mas grandes

1. En el treemap, busca los 3 rectangulos mas grandes dentro de `node_modules`
2. Documenta cada uno en un archivo `bundle-analisis.md`:

```text
# Analisis de Bundle

## Tamano total: XX KB (gzip)

## Top 3 dependencias mas grandes

1. **[nombre-libreria]** — XX KB
   - Se usa para: [que hace en tu app]
   - Se puede optimizar: [si/no y como]

2. **[nombre-libreria]** — XX KB
   - Se usa para: [que hace en tu app]
   - Se puede optimizar: [si/no y como]

3. **[nombre-libreria]** — XX KB
   - Se usa para: [que hace en tu app]
   - Se puede optimizar: [si/no y como]
```

3. Para cada dependencia, preguntate:
   - ¿Uso todas las funciones de esta libreria o solo una?
   - ¿Existe una alternativa mas liviana?
   - ¿Puedo implementar la funcionalidad yo mismo en pocas lineas?

### Paso 4 — Implementar una optimización

Aplica al menos una de estas estrategias:

**Estrategia A — Reemplazar un import pesado con uno específico:**
```typescript
// MAL: importa todo lodash (72 KB)
import _ from 'lodash';
const resultado = _.debounce(fn, 300);

// BIEN: importa solo la funcion (3 KB)
import debounce from 'lodash-es/debounce';
const resultado = debounce(fn, 300);
```

**Estrategia B — Reemplazar una libreria pesada con una alternativa:**
```typescript
// MAL: moment.js (67 KB + locales)
import moment from 'moment';
moment().format('YYYY-MM-DD');

// BIEN: date-fns (tree-shakeable, solo importas lo que usas)
import { format } from 'date-fns';
format(new Date(), 'yyyy-MM-dd');
```

**Estrategia C — Eliminar un import que no usas:**
1. Busca imports en tu código que nunca se usan
2. Tu linter (ESLint) deberia marcarlos — ejecuta:
   ```bash
   npx eslint src/ --rule '{"no-unused-vars": "error"}'
   ```
3. Elimina los imports no usados

**Estrategia D — Lazy load de una libreria pesada:**
```typescript
// MAL: chart.js se carga siempre (60 KB)
import Chart from 'chart.js/auto';

// BIEN: chart.js se carga solo cuando se necesita
async function crearGrafico(canvas: HTMLCanvasElement) {
  const { Chart } = await import('chart.js/auto');
  new Chart(canvas, { /* config */ });
}
```

### Paso 5 — Comparar antes vs despues

1. Ejecuta el analyzer de nuevo:
   ```bash
   npm run analyze
   ```
2. Compara el tamaño total con la captura de pantalla del Paso 2
3. Calcula el porcentaje de reduccion:
   ```
   Reduccion = ((tamano_antes - tamano_despues) / tamano_antes) * 100
   ```
4. Actualiza `bundle-analisis.md`:

```text
## Resultado

- Tamano antes: XX KB
- Tamano despues: YY KB
- Reduccion: ZZ%
- Optimizacion aplicada: [descripcion]
```

## Que puede salir mal

- **"El comando `npm run analyze` falla con 'no source maps found'"** → Asegurate de usar `--source-map` en el build. En Angular, verifica que `angular.json` no tiene `"sourceMap": false` en la configuración de produccion.
- **"Elimine un import y ahora la app no compila"** → El import SI se estaba usando. Revierte el cambio con `Ctrl+Z`. Antes de eliminar, busca el nombre de la función/clase importada en todo tu código.
- **"No logro reducir el 20%"** → Si tu app es pequena (< 200 KB), un 20% puede ser difícil. Intenta combinar varias estrategias: eliminar imports no usados + reemplazar una libreria pesada.

## Resultado esperado

Al terminar, tienes un reporte visual de tu bundle, conoces las 3 dependencias mas grandes, y has aplicado al menos una optimización medible. Tienes un archivo `bundle-analisis.md` con los numeros de antes y despues.

**Criterios de aceptacion:**
- [ ] Bundle reducido al menos 20% (o documentado por que no es posible si la app es muy pequena)
- [ ] Se identifican las 3 dependencias mas grandes con su tamaño
- [ ] Al menos una optimización implementada y verificada con el analyzer
