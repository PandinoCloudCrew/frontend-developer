## Por que esta actividad

Cuando un usuario abre tu aplicación, el navegador descarga **todo** el JavaScript de una sola vez — incluyendo el código de paginas que quiza nunca visite. Si tu app tiene 10 rutas, el usuario descarga el código de las 10 al entrar a la primera. Eso es como cargar un libro entero en memoria para leer solo la primera página. **Lazy loading** y **code splitting** resuelven esto: dividen tu código en pedazos (chunks) y solo descargan el necesario para la página actual.

## Antes de empezar

Necesitas tener completada la **Actividad 5.1** y una aplicación con al menos 2 rutas.

Un **bundle** es el archivo JavaScript final que el navegador descarga cuando un usuario abre tu aplicación. Las herramientas de build (Webpack, Vite, esbuild) toman todos tus archivos `.ts`/`.js` y los combinan en uno (o pocos) archivos. El problema: cuando tu app crece, ese archivo crece también — y el usuario tiene que esperar a que se descargue todo antes de ver algo.

**Code splitting** divide ese bundle en pedazos mas pequenos (chunks). La forma mas comun es dividir por ruta: el código de `/perfil` se descarga solo cuando el usuario navega a `/perfil`.

**Lazy loading de imagenes** es un atributo HTML (`loading="lazy"`) que le dice al navegador: "no descargues esta imagen hasta que el usuario haga scroll cerca de ella".

### Paso 1 — Medir el bundle actual

1. Abre la terminal en VS Code en la carpeta de tu proyecto
2. Ejecuta el build de produccion:
   ```bash
   ng build
   ```
   (Si no usas Angular: `npm run build`)
3. Observa la salida — Angular te muestra los tamanos de cada archivo:
   ```
   Initial chunk files | Names   | Raw size
   main.js             | main    | 245.00 kB
   styles.css          | styles  |  12.00 kB
   ```
4. Anota el tamaño de `main.js` — este es tu bundle actual. Todo esta en un solo archivo

### Paso 2 — Implementar code splitting por ruta

En Angular 19+, el code splitting se hace con `loadComponent` en las rutas:

1. Abre tu archivo de rutas (generalmente `src/app/app.routes.ts`)
2. Cambia las rutas para usar carga lazy:

```typescript
// src/app/app.routes.ts
import { Routes } from '@angular/router';

export const routes: Routes = [
  {
    path: '',
    loadComponent: () => import('./home/home.component')
      .then(m => m.HomeComponent),
  },
  {
    path: 'perfil',
    loadComponent: () => import('./perfil/perfil.component')
      .then(m => m.PerfilComponent),
  },
  {
    path: 'dashboard',
    loadComponent: () => import('./dashboard/dashboard.component')
      .then(m => m.DashboardComponent),
  },
];
```

3. **Importante:** elimina los `import` estaticos de estos componentes en la parte superior del archivo. Si tienes `import { PerfilComponent } from './perfil/perfil.component'`, eliminalo — el `import()` dinámico dentro de `loadComponent` lo reemplaza

> 💡 **Nota:** `import()` con parentesis (dinámico) es diferente de `import` sin parentesis (estatico). El dinámico le dice al bundler: "este código puede cargarse despues, ponlo en un chunk separado".

### Paso 3 — Lazy loading de imagenes

1. Abre los templates de tus componentes y busca todas las etiquetas `<img>`
2. A las imagenes que **no son visibles inmediatamente** (las que estan debajo del fold — el usuario tiene que hacer scroll para verlas), agregalas `loading="lazy"`:

```text
<!-- HTML: imagenes que no se ven al cargar la pagina -->
<img src="producto-3.webp" alt="Producto 3" width="300" height="200" loading="lazy">
<img src="producto-4.webp" alt="Producto 4" width="300" height="200" loading="lazy">
```

3. **No** agregues `loading="lazy"` a imagenes que el usuario ve inmediatamente (arriba del fold) — eso las retrasaria

### Paso 4 — Priorizar la imagen hero

La imagen hero (la imagen grande principal que el usuario ve al abrir la página) necesita tratamiento opuesto al lazy loading:

1. Encuentra tu imagen hero en el template
2. Asegurate de que **no** tiene `loading="lazy"`
3. Agrega `fetchpriority="high"` para que el navegador la descargue primero:

```text
<!-- HTML: la imagen principal de la pagina -->
<img src="hero-banner.webp"
     alt="Banner principal"
     width="1200"
     height="600"
     fetchpriority="high">
```

> 💡 **Nota:** en Angular, si usas la directiva `NgOptimizedImage`, esto se maneja con el atributo `priority`:
> ```text
> <!-- HTML: con NgOptimizedImage -->
> <img ngSrc="hero-banner.webp" width="1200" height="600" priority>
> ```

### Paso 5 — Verificar los chunks en el build

1. Ejecuta el build de produccion de nuevo:
   ```bash
   ng build
   ```
2. Ahora deberias ver multiples chunks en la salida:
   ```
   Initial chunk files   | Names       | Raw size
   main.js               | main        | 150.00 kB
   styles.css            | styles      |  12.00 kB

   Lazy chunk files      | Names       | Raw size
   chunk-PERFIL.js       | perfil      |  35.00 kB
   chunk-DASHBOARD.js    | dashboard   |  60.00 kB
   ```
3. Compara: `main.js` deberia ser mas pequeno que antes, y cada ruta tiene su propio chunk
4. Para verificar el lazy loading de imagenes:
   - Abre tu app en Chrome
   - Ve a DevTools → Network → filtra por **Img**
   - Recarga la página — solo deben cargarse las imagenes visibles
   - Haz scroll hacia abajo — las imagenes lazy deben aparecer en Network al hacerse visibles
5. Verifica la imagen hero:
   - En DevTools → Elements, busca tu imagen hero
   - Confirma que **no** tiene `loading="lazy"`
   - Confirma que tiene `fetchpriority="high"`

## Que puede salir mal

- **"Despues de agregar loadComponent, la ruta muestra una página en blanco"** → Verifica que el nombre del componente en `.then(m => m.NombreComponent)` coincide exactamente con el nombre exportado en el archivo del componente. Es case-sensitive.
- **"El build muestra el mismo tamaño de main.js"** → Probablemente aun tienes un `import` estatico del componente en algun lugar. Busca en todos tus archivos: si algun archivo importa el componente directamente (no con `import()`), el bundler lo incluye en main.js.
- **"No se cual imagen es la hero"** → Es la imagen mas grande que el usuario ve sin hacer scroll cuando abre la página. Abre tu app y mira: lo primero visible es lo que esta "above the fold".

## Resultado esperado

Al terminar, tu aplicación divide el JavaScript por ruta — cada ruta carga solo su código. Las imagenes que no son inmediatamente visibles se cargan bajo demanda, y la imagen hero tiene prioridad maxima.

**Criterios de aceptacion:**
- [ ] Cada ruta tiene su propio chunk JS (visible en la salida de `ng build`)
- [ ] La imagen hero NO tiene `loading="lazy"`
- [ ] La imagen hero tiene `fetchpriority="high"`
