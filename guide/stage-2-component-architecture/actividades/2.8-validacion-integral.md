## Por que esta actividad

Antes de avanzar a la Etapa 3, necesitas confirmar que dominas la arquitectura de componentes. Esta actividad ejecuta todos los criterios de aceptacion de la etapa y te ayuda a identificar y cerrar cualquier brecha. En un trabajo real, esto equivale a un "code review" de tu propio código antes de abrir un pull request.

| | |
|---|---|
| **Requiere** | Todas las actividades esenciales (2.0-2.4) completadas |
| **Aprenderas** | Ejecutar scripts de validación, interpretar resultados, corregir fallos restantes, verificar la calidad general de tus componentes |
| **Al completar** | Todos los criterios de aceptacion de la etapa pasan: props tipados, componentes menores a 150 lineas, cero fetch en componentes, Tabs con flechas, composicion funcional |

**Lectura:** Revisar los criterios de aceptacion de las Actividades 2.0-2.7.

## Antes de empezar

Necesitas haber completado al menos las **Actividades esenciales (2.0-2.4)**. Las recomendadas (2.5-2.6) y avanzadas (2.7) son opcionales para esta validación, pero si las completaste, también se verifican.

**¿Que es una validación integral?** Es una revision sistematica de todo lo que construiste en la etapa. En lugar de confiar en que "creo que funciona", ejecutas verificaciones concretas que te dicen con certeza si cumples los criterios o no.

### Paso 1 — Verificar compilacion limpia

1. En la terminal, dentro del directorio de tu proyecto Angular, ejecuta:
   ```bash
   ng build
   ```
2. El resultado debe ser: **cero errores de compilacion**
3. Si hay errores, lee cada mensaje. Angular te indica el archivo, la linea y el problema. Corrige cada error antes de continuar.

### Paso 2 — Verificar tamaño de componentes

1. En la terminal, ejecuta:
   ```bash
   wc -l src/app/**/*.component.ts
   ```
2. **Criterio:** Ningun archivo `.component.ts` debe exceder 150 lineas
3. Si algun componente excede el limite, revisa si puedes extraer lógica a un servicio o dividirlo en sub-componentes (como hiciste en la Actividad 2.3)

### Paso 3 — Verificar composicion

1. Abre el navegador con `ng serve`
2. Navega a la página donde estan los `ProductCard`
3. Verifica que:
   - `ButtonComponent` se usa dentro de `SearchBarComponent`
   - `ButtonComponent` se usa dentro de `ProductCardComponent`
   - Los eventos fluyen correctamente (clic en botón → consola muestra el evento)
4. Si la Actividad 2.5 esta completa, verifica que `FeaturedProductCard` puede reemplazar a `ProductCard` sin romper nada

### Paso 4 — Verificar Tabs con teclado

1. En el navegador, navega a la página con los Tabs
2. Haz clic en el primer tab para darle foco
3. Presiona flecha derecha → el segundo tab se activa
4. Presiona flecha derecha → el tercer tab se activa
5. Presiona flecha derecha → vuelve al primer tab (navegación circular)
6. Presiona flecha izquierda → vuelve al tercer tab
7. Verifica que el tab activo tiene un indicador visual (linea azul, texto en negrita)
8. Verifica que al usar Tab del teclado, el focus ring es visible

### Paso 5 — Verificar props tipados

1. Abre la terminal y ejecuta:
   ```bash
   npx tsc --noEmit --strict
   ```
   - `--noEmit` verifica tipos sin generar archivos
   - `--strict` activa todas las verificaciones de tipos
2. El resultado debe ser: **cero errores**
3. Si hay errores de tipo, corrigelos. Los mas comunes:
   - Falta de tipo en una variable (usar `any` implicitamente)
   - Propiedad que podria ser `undefined` pero no se maneja
   - Tipo incorrecto en un input/output

### Paso 6 — Verificar separacion de datos

1. Busca si algun componente hace fetch de datos directamente. En la terminal:
   ```bash
   grep -r "fetch\|HttpClient\|http\." src/app --include="*.component.ts"
   ```
2. El resultado debe estar **vacio** — ningun componente debe hacer fetch directamente
3. Los datos deben venir de servicios (como `UserService`), no de los componentes

### Paso 7 — Ejecutar tests

1. Si completaste la Actividad 2.6 (tests del servicio), ejecuta:
   ```bash
   ng test --watch=false
   ```
2. Todos los tests deben pasar
3. Si no completaste la Actividad 2.6, puedes saltar este paso

## Que puede salir mal

- **"ng build falla con errores que no habia visto con ng serve"** → `ng build` es mas estricto que `ng serve`. Lee cada error y corrigelo. Los mas comunes son imports faltantes y tipos incorrectos.
- **"wc -l muestra numeros diferentes a los que esperaba"** → Recuerda que `wc -l` cuenta todas las lineas, incluyendo lineas en blanco y comentarios. El limite de 150 es generoso — si estas cerca, revisa si hay lógica que podria vivir en un servicio.
- **"grep encuentra un HttpClient en un componente"** → Mueve esa lógica a un servicio. El componente debe recibir los datos como input o inyectar un servicio que se encargue del fetch.
