## Por que esta actividad

Antes de escribir código, necesitas aprender a **ver** una interfaz como un arbol de componentes. Cada rectangulo, cada sección, cada botón es potencialmente un componente. Si no sabes descomponer una UI, terminaras con componentes gigantes de 500 lineas que nadie quiere tocar. Esta habilidad de "pensar en componentes" es la base de todo framework moderno y la aplicaras en cada proyecto real.

## Antes de empezar

Necesitas haber completado la **Actividad 2.0** (proyecto Angular funcionando con `ng serve`).

**¿Que es descomponer una UI?** Es el proceso de mirar un diseño y dividirlo en piezas independientes. Cada pieza es un componente con una responsabilidad clara. Es como desarmar un LEGO: en lugar de ver una casa completa, ves las piezas individuales (puerta, ventana, techo) y como encajan.

**¿Que es el arbol de componentes?** Es un diagrama que muestra que componente contiene a que otro. El componente raiz (la página) contiene secciones, las secciones contienen tarjetas, las tarjetas contienen botones. Los datos fluyen hacia abajo (de padre a hijo via props) y los eventos fluyen hacia arriba (de hijo a padre via callbacks).

**¿Que son los props?** Son los datos que un componente padre le pasa a un componente hijo. Son la "API publica" del componente — lo único que el mundo exterior puede controlar. Todo lo demas es interno.

### Paso 1 — Observar el mockup

1. Imagina (o dibuja en papel) una **página de producto** tipica de un e-commerce. Tiene:
   - Un header con logo y barra de navegación
   - Una imagen del producto con galeria de thumbnails
   - Nombre del producto, precio, descripción
   - Un botón "Agregar al carrito"
   - Una sección de resenas con estrellas y comentarios
   - Un footer con links

2. Si prefieres algo visual, abre cualquier página de producto real (Amazon, MercadoLibre) y observala

### Paso 2 — Identificar los componentes

1. Crea un archivo `src/app/descomposicion.md` en tu proyecto Angular (o usa un editor de texto aparte)
2. Lista todos los componentes que identificas. Cada componente debe poder describirse en una oracion:

   ```markdown
   ## Componentes identificados

   - **ProductPage** — Contenedor de toda la pagina de producto
   - **Header** — Barra superior con logo y navegacion
   - **Logo** — Imagen del logo de la tienda
   - **NavBar** — Lista de links de navegacion
   - **ProductGallery** — Galeria de imagenes del producto
   - **ThumbnailList** — Fila de imagenes en miniatura
   - **ProductInfo** — Nombre, precio, descripcion del producto
   - **PriceTag** — Muestra el precio con formato
   - **AddToCartButton** — Boton para agregar al carrito
   - **ReviewSection** — Seccion de resenas
   - **ReviewCard** — Una resena individual
   - **StarRating** — Componente de estrellas (1-5)
   - **Footer** — Pie de pagina con links
   ```

3. **Regla clave:** si no puedes describir un componente en una sola oracion, probablemente es demasiado grande. Dividelo.

### Paso 3 — Documentar los props de cada componente

1. Para cada componente, escribe sus props como si fueran una interfaz TypeScript:

   ```typescript
   // ProductInfo: Muestra la informacion principal del producto
   interface ProductInfoProps {
     name: string;           // Nombre del producto
     price: number;          // Precio en moneda local
     description: string;    // Descripcion del producto
     inStock: boolean;       // Si esta disponible
   }

   // StarRating: Muestra una calificacion de 1-5 estrellas
   interface StarRatingProps {
     rating: number;         // Valor de 1 a 5
     maxStars?: number;      // Maximo de estrellas (default: 5)
   }

   // ReviewCard: Muestra una resena individual
   interface ReviewCardProps {
     author: string;         // Nombre del autor
     date: string;           // Fecha de la resena
     rating: number;         // Calificacion del autor
     comment: string;        // Texto de la resena
   }

   // AddToCartButton: Boton para agregar al carrito
   interface AddToCartButtonProps {
     productId: string;      // ID del producto
     disabled?: boolean;     // Si esta deshabilitado (default: false)
     onAdd: (id: string) => void;  // Callback cuando se hace clic
   }
   ```

2. **Verifica:** ningun componente deberia tener mas de 7-10 props. Si tiene mas, probablemente esta haciendo demasiado.

### Paso 4 — Dibujar el arbol de componentes

1. En tu documento, dibuja el arbol de componentes usando texto:

   ```
            ProductPage
           /     |      \
       Header  Main    Footer
       /   \     |
    Logo  NavBar |
                 |
         ┌──────┴──────┐
   ProductGallery  ProductInfo
        |              |       \
   ThumbnailList  PriceTag  AddToCartButton
                               |
                         ReviewSection
                              |
                         ReviewCard (x N)
                           |
                        StarRating
   ```

2. **Verifica:** tu arbol debe tener al menos 3 niveles de profundidad (por ejemplo: ProductPage → Main → ProductInfo → PriceTag)

### Paso 5 — Validar contra las reglas

Revisa tu descomposicion contra estas reglas:

1. **Una responsabilidad por componente:** cada componente hace una sola cosa. `ProductInfo` NO hace fetch de datos — solo los muestra
2. **Sin componentes "dios":** ningun componente tiene mas de 10 props
3. **Niveles consistentes:** cada componente trabaja con un solo nivel de abstraccion. `ProductPage` usa `Header`, `Main`, `Footer` — no mezcla `<div>` con `<Header>`
4. **Reutilizabilidad:** `StarRating` y `PriceTag` deberian funcionar en cualquier contexto, no solo en esta página

### Paso 6 — Crear la estructura en Angular

1. En la terminal de tu proyecto Angular, genera los componentes del primer nivel:
   ```bash
   ng g c product-page
   ng g c product-gallery
   ng g c product-info
   ng g c review-section
   ng g c review-card
   ng g c star-rating
   ```

2. Abre `src/app/product-page/product-page.component.ts` y observa que cada componente es standalone por defecto

3. No necesitas implementar la lógica todavia — solo verifica que los archivos se crearon correctamente. Abre cada `.component.ts` y confirma que tiene el decorador `@Component` con `standalone: true`

## Que puede salir mal

- **"No se me ocurren mas de 3 componentes"** → Piensa en cada sección visual como un componente. Mira las piezas repetidas: si hay varias resenas, cada resena es un componente. Si hay una lista de thumbnails, cada thumbnail es un componente. Busca las piezas que podrias reutilizar en otra página.
- **"Mis componentes tienen 15 props cada uno"** → El componente esta haciendo demasiado. Dividelo. Un componente con 15 props probablemente deberia ser 3 componentes con 5 props cada uno.
- **"No se si X es un componente o solo un elemento HTML"** → Preguntate: ¿esta pieza podria reutilizarse en otra parte? ¿Tiene su propia lógica o estado? Si la respuesta a cualquiera es si, es un componente. Un `<h1>` simple no es un componente, pero un `PriceTag` que formatea moneda si lo es.

## Resultado esperado

Tienes un documento (`descomposicion.md` o en papel) con:
- Una lista de al menos 8 componentes identificados
- Interfaces TypeScript para los props de cada componente
- Un arbol de componentes con al menos 3 niveles de profundidad
- Los componentes generados en tu proyecto Angular (archivos creados por `ng g c`)

**Criterios de aceptacion:**
- [ ] El arbol tiene al menos 3 niveles de profundidad
- [ ] Cada componente se describe en una sola oracion y tiene sus props documentados como interfaz TypeScript
- [ ] Ningun componente tiene mas de 10 props
- [ ] Los componentes estan generados en el proyecto Angular con `ng g c`

**Pilares de diseño que ejercita esta actividad:**
- **Mantenibilidad** — descomponer la UI en piezas pequenas y enfocadas facilita el cambio futuro
- **Accesibilidad** — al pensar en componentes semanticos (NavBar, Footer) se refuerza el uso de HTML semántico
