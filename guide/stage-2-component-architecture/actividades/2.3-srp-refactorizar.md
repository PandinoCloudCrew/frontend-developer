# 🟢 Actividad 2.3 — Aplicar SRP y refactorizar un componente dios

**Duracion:** ~60 min

## Por que esta actividad

En proyectos reales, es comun encontrar componentes que empezaron pequenos y fueron creciendo hasta convertirse en monstruos de 400+ lineas que hacen fetch, filtran, ordenan, paginan y renderizan todo en un mismo archivo. Estos "componentes dios" son fragiles: un cambio en la lógica de filtrado puede romper el renderizado. Aprender a aplicar el Single Responsibility Principle (SRP) y refactorizar estos componentes es una habilidad que usaras en cada trabajo real.

| | |
|---|---|
| **Requiere** | Actividad 2.2 completada (experiencia construyendo componentes con props tipados) |
| **Aprenderas** | Identificar violaciones de SRP, extraer lógica a servicios Angular, separar componentes de presentacion de lógica, refactorizar sin romper funcionalidad |
| **Al completar** | Has refactorizado un componente monolitico en multiples componentes y servicios, cada uno con una sola responsabilidad, y la salida es identica a la original |

## Antes de empezar

Necesitas haber completado la **Actividad 2.2** (componentes con props tipados).

**¿Que es el Single Responsibility Principle (SRP)?** Es el principio de que cada componente (o función, o servicio) debe tener **una sola razón para cambiar**. Si un componente maneja la obtencion de datos Y el filtrado Y la paginación Y el renderizado, tiene 4 razones para cambiar. Cualquier modificacion en una de esas areas puede romper las otras.

**¿Que es un servicio en Angular?** Es una clase que contiene lógica reutilizable (obtencion de datos, calculos, validaciones) que no pertenece a un componente específico. Se crea con `ng generate service nombre` y se inyecta en los componentes que lo necesitan. Angular usa **dependency injection** para esto: tu no creas el servicio manualmente, Angular lo crea y te lo entrega.

**¿Que es refactorizar?** Es cambiar la estructura del código sin cambiar su comportamiento externo. Antes y despues de refactorizar, la aplicación hace exactamente lo mismo — pero el código interno es mas limpio, mas legible y mas fácil de mantener.

### Paso 1 — Crear el componente dios

Vamos a crear deliberadamente un componente malo para luego refactorizarlo.

1. En la terminal:
   ::: code-group
   ```bash [Angular]
   ng g c user-dashboard
   ```
   ```bash [React]
   touch src/components/UserDashboard.tsx
   ```
   :::

2. Abre `src/app/user-dashboard/user-dashboard.component.ts` y reemplaza por:
   ::: code-group
   ```typescript [Angular]
   import { Component, signal, computed } from '@angular/core';
   import { CurrencyPipe } from '@angular/common';

   interface User {
     id: number;
     name: string;
     email: string;
     city: string;
     role: 'admin' | 'editor' | 'viewer';
     salary: number;
   }

   @Component({
     selector: 'app-user-dashboard',
     standalone: true,
     imports: [CurrencyPipe],
     templateUrl: './user-dashboard.component.html',
   })
   export class UserDashboardComponent {
     // Estado: datos
     users = signal<User[]>([
       { id: 1, name: 'Ana Garcia', email: 'ana@mail.com', city: 'Madrid', role: 'admin', salary: 55000 },
       { id: 2, name: 'Carlos Lopez', email: 'carlos@mail.com', city: 'Barcelona', role: 'editor', salary: 42000 },
       { id: 3, name: 'Diana Ruiz', email: 'diana@mail.com', city: 'Madrid', role: 'viewer', salary: 38000 },
       { id: 4, name: 'Eduardo Soto', email: 'edu@mail.com', city: 'Sevilla', role: 'editor', salary: 45000 },
       { id: 5, name: 'Fernanda Vega', email: 'fer@mail.com', city: 'Barcelona', role: 'admin', salary: 60000 },
       { id: 6, name: 'Gabriel Mora', email: 'gab@mail.com', city: 'Madrid', role: 'viewer', salary: 35000 },
     ]);

     // Estado: filtros
     searchTerm = signal('');
     selectedCity = signal('');
     selectedRole = signal('');
     sortField = signal<keyof User>('name');
     sortDirection = signal<'asc' | 'desc'>('asc');

     // Estado: paginacion
     currentPage = signal(1);
     pageSize = signal(3);

     // Computed: ciudades unicas para el filtro
     cities = computed(() => {
       const allCities = this.users().map(u => u.city);
       return [...new Set(allCities)].sort();
     });

     // Computed: filtrado + ordenamiento + paginacion
     filteredUsers = computed(() => {
       let result = this.users();

       if (this.searchTerm()) {
         const term = this.searchTerm().toLowerCase();
         result = result.filter(u =>
           u.name.toLowerCase().includes(term) ||
           u.email.toLowerCase().includes(term)
         );
       }

       if (this.selectedCity()) {
         result = result.filter(u => u.city === this.selectedCity());
       }

       if (this.selectedRole()) {
         result = result.filter(u => u.role === this.selectedRole());
       }

       result = [...result].sort((a, b) => {
         const field = this.sortField();
         const dir = this.sortDirection() === 'asc' ? 1 : -1;
         if (a[field] < b[field]) return -1 * dir;
         if (a[field] > b[field]) return 1 * dir;
         return 0;
       });

       return result;
     });

     paginatedUsers = computed(() => {
       const start = (this.currentPage() - 1) * this.pageSize();
       return this.filteredUsers().slice(start, start + this.pageSize());
     });

     totalPages = computed(() =>
       Math.ceil(this.filteredUsers().length / this.pageSize())
     );

     // Metodos
     onSearch(event: Event) {
       const target = event.target as HTMLInputElement;
       this.searchTerm.set(target.value);
       this.currentPage.set(1);
     }

     onCityChange(event: Event) {
       const target = event.target as HTMLSelectElement;
       this.selectedCity.set(target.value);
       this.currentPage.set(1);
     }

     onRoleChange(event: Event) {
       const target = event.target as HTMLSelectElement;
       this.selectedRole.set(target.value);
       this.currentPage.set(1);
     }

     onSort(field: keyof User) {
       if (this.sortField() === field) {
         this.sortDirection.set(this.sortDirection() === 'asc' ? 'desc' : 'asc');
       } else {
         this.sortField.set(field);
         this.sortDirection.set('asc');
       }
     }

     onPageChange(page: number) {
       this.currentPage.set(page);
     }
   }
   ```

   :::

3. Abre `src/app/user-dashboard/user-dashboard.component.html` y reemplaza por:
   ```text
   <!-- HTML: el componente dios - todo en un solo template -->
   <section class="dashboard">
     <h2>Panel de Usuarios</h2>

     <div class="filters">
       <input
         type="text"
         placeholder="Buscar por nombre o email..."
         (input)="onSearch($event)"
       />
       <select (change)="onCityChange($event)">
         <option value="">Todas las ciudades</option>
         @for (city of cities(); track city) {
           <option [value]="city">{{ city }}</option>
         }
       </select>
       <select (change)="onRoleChange($event)">
         <option value="">Todos los roles</option>
         <option value="admin">Admin</option>
         <option value="editor">Editor</option>
         <option value="viewer">Viewer</option>
       </select>
     </div>

     <table>
       <thead>
         <tr>
           <th (click)="onSort('name')">Nombre</th>
           <th (click)="onSort('email')">Email</th>
           <th (click)="onSort('city')">Ciudad</th>
           <th (click)="onSort('role')">Rol</th>
           <th (click)="onSort('salary')">Salario</th>
         </tr>
       </thead>
       <tbody>
         @for (user of paginatedUsers(); track user.id) {
           <tr>
             <td>{{ user.name }}</td>
             <td>{{ user.email }}</td>
             <td>{{ user.city }}</td>
             <td>{{ user.role }}</td>
             <td>{{ user.salary | currency }}</td>
           </tr>
         } @empty {
           <tr>
             <td colspan="5">No se encontraron usuarios</td>
           </tr>
         }
       </tbody>
     </table>

     <div class="pagination">
       @for (page of [].constructor(totalPages()); track $index) {
         <button
           [class.active]="currentPage() === $index + 1"
           (click)="onPageChange($index + 1)"
         >
           {{ $index + 1 }}
         </button>
       }
     </div>

     <p>
       Mostrando {{ paginatedUsers().length }} de {{ filteredUsers().length }} usuarios
       (pagina {{ currentPage() }} de {{ totalPages() }})
     </p>
   </section>
   ```

### Paso 2 — Identificar las responsabilidades

El componente tiene **4 responsabilidades mezcladas**:

1. **Datos** — contiene los usuarios (en produccion, esto vendria de una API)
2. **Filtrado y ordenamiento** — lógica de busqueda, filtros por ciudad/rol, ordenamiento
3. **Paginación** — lógica de paginas y navegación
4. **Renderizado** — la tabla HTML con sus estilos

Cada una de estas es una razón para cambiar. Vamos a separarlas.

       { id: 6, name: 'Gabriel Mora', email: 'gab@mail.com', city: 'Madrid', role: 'viewer', salary: 35000 },

### Paso 6 — Verificar que la salida es identica

1. Abre el navegador y verifica que todo funciona igual que antes: filtrado, ordenamiento, paginación
2. En la terminal, verifica el tamaño de cada archivo:
   ```bash
   wc -l src/app/user-dashboard/user-dashboard.component.ts
   wc -l src/app/user-filters/user-filters.component.ts
   wc -l src/app/user-table/user-table.component.ts
   wc -l src/app/pagination/pagination.component.ts
   wc -l src/app/services/user.service.ts
   ```
   Ningun archivo deberia superar 150 lineas.

## Que puede salir mal

- **"La tabla se ve diferente despues de refactorizar"** → Verifica que el template de `UserTableComponent` es identico a la sección de tabla del componente original. No cambies la estructura HTML, solo muevela.
- **"El servicio no me inyecta los datos"** → Asegurate de usar `inject(UserService)` en el componente. El servicio necesita tener `@Injectable({ providedIn: 'root' })`.
- **"Los filtros no funcionan"** → Verifica que los outputs del componente de filtros (`searchChanged`, `cityChanged`, `roleChanged`) estan conectados correctamente con `(searchChanged)="onSearchChange($event)"` en el dashboard.

## Resultado esperado

La aplicación se ve y funciona exactamente igual que antes, pero ahora el código esta organizado en piezas separadas: un servicio para los datos, un componente para filtros, uno para la tabla, uno para paginación, y el dashboard que los orquesta. Ningun archivo excede 150 lineas.

**Criterios de aceptacion:**
- [ ] Ningun componente excede 150 lineas (verificar con `wc -l`)
- [ ] Los datos vienen de un servicio (`UserService`), no estan hardcodeados en el componente
- [ ] Cada componente de presentacion (`UserFilters`, `UserTable`, `Pagination`) solo recibe datos via inputs y emite eventos via outputs
- [ ] La salida visual y funcional es identica a la versión original (antes de refactorizar)

**Pilares de diseño que ejercita esta actividad:**
- **Mantenibilidad** — SRP: cada pieza tiene una sola razón para cambiar, facilitando el mantenimiento a largo plazo
- **Resiliencia** — separar responsabilidades reduce el riesgo de romper funcionalidad no relacionada al hacer cambios
