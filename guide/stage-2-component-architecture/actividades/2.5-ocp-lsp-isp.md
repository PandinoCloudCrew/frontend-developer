## Por que esta actividad

En la Actividad 2.3 aplicaste SRP (Single Responsibility). Pero SOLID tiene 4 principios mas que previenen problemas reales: componentes que se rompen cuando agregas una variante (OCP), variantes que no son intercambiables (LSP), y APIs infladas que fuerzan a pasar datos innecesarios (ISP). Esta actividad te enseña a detectar estas violaciones en componentes que ya construiste y a corregirlas. Es la diferencia entre código que "funciona" y código que "funciona y se puede mantener".

|---|---|
| **Requiere** | Actividades 2.2-2.4 completadas (componentes construidos para revisar) |
| **Aprenderas** | Open/Closed Principle (extender via composicion), Liskov Substitution (variantes intercambiables), Interface Segregation (APIs minimas), detectar violaciones en código existente |

## Antes de empezar

Necesitas haber completado las **Actividades 2.2 a 2.4** (tener componentes construidos: Button, SearchBar, ProductCard, UserTable, Tabs).

**¿Que es OCP (Open/Closed Principle)?** Un componente debe poder extenderse con nuevo comportamiento sin modificar su código fuente. En la practica, esto significa usar composicion (`<ng-content>`, slots) en lugar de agregar `if/else` para cada variante nueva.

**¿Que es LSP (Liskov Substitution Principle)?** Si tienes un componente base y una variante especializada, la variante debe poder reemplazar al base en cualquier lugar sin romper nada. Si `FeaturedProductCard` se usa donde se usaba `ProductCard`, todo debe seguir funcionando.

**¿Que es ISP (Interface Segregation Principle)?** Un componente no debe obligar a sus consumidores a pasar datos que no necesitan. Si `ProductCard` tiene 15 props pero la mayoria de usos solo necesitan 3, la interfaz esta inflada.

### Paso 1 — Auditar OCP en tus componentes

1. Abre `src/app/button/button.component.ts`
2. Observa que tiene un input `variant` con `'primary' | 'secondary'`. Preguntate: ¿que pasa si ahora necesito un botón `'danger'` o `'ghost'`?
3. Con el diseño actual, tendrias que:
   - Agregar la nueva variante al union type
   - Agregar una nueva clase CSS
   - Potencialmente agregar lógica condicional en el template

4. Crea un archivo `src/app/auditoria-solid.md` y documenta:
   ```markdown
   ## Auditoria OCP

   ### ButtonComponent
   - **Violacion:** Agregar una nueva variante requiere modificar el componente
     (cambiar el union type, agregar CSS). Esto viola OCP.
   - **Impacto:** Cada nueva variante toca el componente base, lo que puede
     romper las variantes existentes.
   ```

### Paso 2 — Corregir la violacion con composicion

1. Modifica `src/app/button/button.component.ts` para que acepte content projection y clases externas:
   ```typescript
   import { Component, input, output } from '@angular/core';

   @Component({
     selector: 'app-button',
     standalone: true,
     template: `
       <button
         [class]="'btn ' + extraClass()"
         [disabled]="disabled()"
         (click)="handleClick()"
       >
         <ng-content />
       </button>
     `,
     styleUrl: './button.component.css',
   })
   export class ButtonComponent {
     extraClass = input<string>('btn-primary');
     disabled = input<boolean>(false);
     clicked = output<void>();

     handleClick() {
       if (!this.disabled()) {
         this.clicked.emit();
       }
     }
   }
   ```

2. Ahora los consumidores pueden crear variantes sin modificar `ButtonComponent`:
   ```text
   <!-- HTML: variantes sin modificar el componente base -->
   <app-button extraClass="btn-primary" (clicked)="save()">Guardar</app-button>
   <app-button extraClass="btn-danger" (clicked)="delete()">Eliminar</app-button>
   <app-button extraClass="btn-ghost" (clicked)="cancel()">Cancelar</app-button>
   ```

3. Agrega las clases CSS necesarias en `src/app/button/button.component.css`:
   ```css
   .btn {
     padding: 0.5rem 1rem;
     border: none;
     border-radius: 4px;
     cursor: pointer;
     font-size: 1rem;
   }

   .btn-primary {
     background-color: #2563eb;
     color: white;
   }

   .btn-secondary {
     background-color: #e5e7eb;
     color: #1f2937;
   }

   .btn-danger {
     background-color: #dc2626;
     color: white;
   }

   .btn-ghost {
     background-color: transparent;
     color: #2563eb;
     border: 1px solid #2563eb;
   }

   .btn:disabled {
     opacity: 0.5;
     cursor: not-allowed;
   }
   ```

> 💡 **Nota:** Ahora el componente usa `<ng-content />` en lugar de `{{ label() }}`. Esto permite al consumidor poner lo que quiera dentro: texto, iconos, o incluso otros componentes. El botón ya no necesita saber que va a contener.

### Paso 3 — Crear una variante sustituible (LSP)

1. Genera un componente para una tarjeta de producto destacada:
   ```bash
   ng g c featured-product-card
   ```

2. Abre `src/app/featured-product-card/featured-product-card.component.ts` y escribe:
   ```typescript
   import { Component, input, output } from '@angular/core';
   import { CurrencyPipe } from '@angular/common';
   import { ButtonComponent } from '../button/button.component';

   @Component({
     selector: 'app-featured-product-card',
     standalone: true,
     imports: [ButtonComponent, CurrencyPipe],
     templateUrl: './featured-product-card.component.html',
     styleUrl: './featured-product-card.component.css',
   })
   export class FeaturedProductCardComponent {
     // Mismos inputs que ProductCard — LSP
     name = input.required<string>();
     price = input.required<number>();
     description = input<string>('');
     imageUrl = input<string>('');
     addedToCart = output<string>();

     // Input adicional de la variante
     badge = input<string>('Destacado');

     onAddToCart() {
       this.addedToCart.emit(this.name());
     }
   }
   ```

3. Abre `src/app/featured-product-card/featured-product-card.component.html`:
   ```text
   <!-- HTML: tarjeta de producto destacada -->
   <article class="product-card featured">
     <span class="badge">{{ badge() }}</span>
     @if (imageUrl()) {
       <img [src]="imageUrl()" [alt]="name()" class="product-image" />
     }
     <div class="product-body">
       <h3>{{ name() }}</h3>
       <p class="price">{{ price() | currency }}</p>
       @if (description()) {
         <p class="description">{{ description() }}</p>
       }
       <app-button extraClass="btn-primary" (clicked)="onAddToCart()">
         Agregar al carrito
       </app-button>
     </div>
   </article>
   ```

4. Agrega estilos en `src/app/featured-product-card/featured-product-card.component.css`:
   ```css
   .product-card {
     border: 1px solid #e5e7eb;
     border-radius: 8px;
     overflow: hidden;
     max-width: 300px;
     position: relative;
   }

   .featured {
     border-color: #f59e0b;
     box-shadow: 0 0 0 2px #f59e0b33;
   }

   .badge {
     position: absolute;
     top: 0.5rem;
     right: 0.5rem;
     background: #f59e0b;
     color: white;
     padding: 0.25rem 0.75rem;
     border-radius: 4px;
     font-size: 0.75rem;
     font-weight: bold;
   }

   .product-image {
     width: 100%;
     height: 200px;
     object-fit: cover;
   }

   .product-body {
     padding: 1rem;
   }

   .price {
     font-size: 1.25rem;
     font-weight: bold;
     color: #059669;
   }

   .description {
     color: #6b7280;
     font-size: 0.875rem;
   }
   ```

5. **Prueba de sustituibilidad:** en `app.component.html`, reemplaza uno de los `<app-product-card>` por `<app-featured-product-card>` con los mismos props. Debe funcionar sin cambiar nada mas. Esa es la prueba de LSP.

### Paso 4 — Auditar ISP en las interfaces

1. Revisa cada componente y cuenta sus inputs:
   - `ButtonComponent` → 2 inputs (`extraClass`, `disabled`) — bien
   - `ProductCardComponent` → 4 inputs (`name`, `price`, `description`, `imageUrl`) — bien
   - `UserTableComponent` → 1 input (`users`) — bien
   - Si algun componente tuviera 10+ inputs, seria una violacion de ISP

2. Documenta en `src/app/auditoria-solid.md`:
   ```markdown
   ## Auditoria ISP

   - Ningun componente excede 10 props ✓
   - ButtonComponent: 2 inputs — minimo necesario
   - ProductCardComponent: 4 inputs — razonable
   - Todos los inputs opcionales tienen valores por defecto
   ```

### Paso 5 — Documentar los hallazgos

1. Completa tu archivo `src/app/auditoria-solid.md` con:
   - Las violaciones encontradas
   - Las correcciones aplicadas
   - Como la variante `FeaturedProductCard` es sustituible por `ProductCard`
   - El conteo de props de cada componente

## Que puede salir mal

- **"Al cambiar Button a usar `<ng-content>`, los componentes que usaban `label` se rompen"** → Correcto. Necesitas actualizar `SearchBar` y `ProductCard` para que pasen el texto como contenido del botón (`<app-button>Buscar</app-button>`) en lugar de como prop (`label="Buscar"`).
- **"FeaturedProductCard no compila porque no encuentra ButtonComponent"** → Asegurate de importar `ButtonComponent` en el array `imports` de `FeaturedProductCardComponent`.
- **"No se me ocurren violaciones de OCP"** → Piensa en que pasa cuando necesitas agregar una nueva variante. Si tienes que abrir y modificar el archivo del componente base, eso es una violacion de OCP.

## Resultado esperado

Tienes un documento `auditoria-solid.md` con las violaciones encontradas y corregidas. Tu `ButtonComponent` ahora acepta content projection (OCP). Tu `FeaturedProductCard` es sustituible donde se usa `ProductCard` (LSP). Ningun componente tiene mas de 10 props (ISP).

**Criterios de aceptacion:**
- [ ] Los componentes son extensibles via composicion: agregar una nueva variante de botón no requiere modificar `ButtonComponent` (OCP)
- [ ] `FeaturedProductCard` puede reemplazar a `ProductCard` sin romper la funcionalidad (LSP)
- [ ] Ningun componente tiene mas de 10 inputs (ISP)

**Pilares de diseño que ejercita esta actividad:**
- **Mantenibilidad** — SOLID reduce el acoplamiento y hace que los cambios sean localizados
- **Resiliencia** — variantes sustituibles reducen el riesgo de romper funcionalidad al extender componentes
