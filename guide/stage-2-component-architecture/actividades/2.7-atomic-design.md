## Por que esta actividad

Atomic Design es una metodologia popular para organizar componentes en jerarquias (atoms, molecules, organisms, templates, pages). Muchos equipos la adoptan, pero pocos entienden sus limitaciones. En esta actividad vas a clasificar todos los componentes que has construido usando Atomic Design y vas a descubrir donde la clasificacion se vuelve ambigua. Saber cuando Atomic Design ayuda y cuando estorba te ahorra debates improductivos en equipos reales.

## Antes de empezar

Necesitas haber completado las **Actividades 2.0 a 2.4** para tener suficientes componentes que clasificar.

**¿Que es Atomic Design?** Es una metodologia creada por Brad Frost que organiza componentes en 5 niveles:
- **Atoms** — los bloques mas basicos: un botón, un input, un icono, un label
- **Molecules** — grupos de atoms que funcionan juntos: una barra de busqueda (input + botón), un campo de formulario (label + input + error)
- **Organisms** — secciones complejas: una barra de navegación, una tarjeta de producto, un formulario completo
- **Templates** — layouts de página sin datos reales
- **Pages** — templates con datos reales de produccion

**¿Que es Feature-Sliced Design?** Es una alternativa que organiza el código por **dominio de negocio** (features) en lugar de por granularidad de UI. En lugar de `atoms/Button`, `molecules/SearchBar`, `organisms/ProductCard`, tendrias `features/product/components/ProductCard`, `features/cart/components/CartButton`. Cada feature contiene todo lo que necesita: componentes, servicios, modelos.

## Practica paso a paso

### Paso 1 — Clasificar tus componentes

1. Crea un archivo `src/app/atomic-design.md` en tu proyecto
2. Lista todos los componentes que has creado en la etapa y clasifica cada uno:

   ```markdown
   ## Clasificacion Atomic Design

   ### Atoms
   - ButtonComponent — elemento de interaccion basico
   - StarRating — visualizacion de calificacion (si lo creaste en 2.1)

   ### Molecules
   - SearchBarComponent — input + boton trabajando juntos
   - TextInputComponent — label + input con estado
   - SearchInputComponent — input con busqueda interna
   - TabComponent — un tab individual (parte de compound)
   - PaginationComponent — controles de pagina

   ### Organisms
   - ProductCardComponent — tarjeta completa de producto
   - FeaturedProductCardComponent — variante destacada
   - UserFiltersComponent — grupo de filtros
   - UserTableComponent — tabla de datos
   - TabGroupComponent — contenedor de tabs
   - UserDashboardComponent — panel completo

   ### Templates
   - (aun no hemos creado templates en esta etapa)

   ### Pages
   - AppComponent — la pagina raiz actual
   ```

### Paso 2 — Encontrar las ambiguedades

No todo encaja limpiamente. Documenta los casos ambiguos:

1. **¿PaginationComponent es molecule u organism?** Tiene multiples botones (atoms) y lógica de estado (página actual). Podria argumentarse ambos.
2. **¿UserDashboardComponent es organism, template o page?** Compone multiples organismos (filtros, tabla, paginación) y tiene lógica de negocio. ¿Es un organism complejo o ya es un template?
3. **¿TabGroupComponent es molecule u organism?** Contiene otros componentes pero su complejidad depende de cuantos tabs tenga.
4. **¿Donde van los servicios?** `UserFilterService`, `TabsStateService`, `UserService` no son componentes de UI. Atomic Design no tiene un nivel para lógica de negocio.

Agrega estas reflexiones a tu documento:

```markdown
## Ambiguedades encontradas

1. **PaginationComponent:** ¿molecule u organism? Tiene botones (atoms)
   pero tambien logica de navegacion. La clasificacion depende de la
   definicion que use el equipo.

2. **UserDashboardComponent:** ¿organism o template? Compone multiples
   organismos y tiene logica de coordinacion. Brad Frost diria que es
   un template, pero no tiene layout de pagina.

3. **Servicios sin clasificacion:** UserFilterService, UserService,
   TabsStateService no encajan en ningun nivel. Atomic Design solo
   cubre la capa de UI.

4. **TabGroupComponent como compound:** Los compound components no
   mapean bien a la jerarquia atomica porque su nivel depende del
   contexto de uso.
```

### Paso 3 — Evaluar Feature-Sliced Design

1. Piensa en como organizarias los mismos componentes por features:

   ```markdown
   ## Organizacion por features (alternativa)

   src/
     features/
       users/
         components/
           user-dashboard.component.ts
           user-filters.component.ts
           user-table.component.ts
         services/
           user.service.ts
           user-filter.service.ts
       products/
         components/
           product-card.component.ts
           featured-product-card.component.ts
       shared/
         components/
           button.component.ts
           search-bar.component.ts
           pagination.component.ts
           tabs/
             tab-group.component.ts
             tab.component.ts
             tab-panel.component.ts
         services/
           tabs-state.service.ts
   ```

2. Documenta las ventajas de cada enfoque:

   ```markdown
   ## Comparacion

   | Criterio | Atomic Design | Feature-Sliced |
   |----------|--------------|----------------|
   | Mejor para | Design systems, bibliotecas de componentes | Apps con logica de negocio |
   | Organizacion por | Granularidad de UI | Dominio de negocio |
   | Incluye servicios | No | Si |
   | Debates de clasificacion | Frecuentes (¿molecule u organism?) | Raros |
   | Co-locacion | Baja (archivos relacionados en carpetas diferentes) | Alta |
   ```

### Paso 4 — Escribir la conclusion

Agrega una conclusion a tu documento:

```markdown
## Conclusion

Atomic Design funciona bien para:
- Bibliotecas de componentes compartidas / design systems
- Proyectos donde la UI es la complejidad principal
- Equipos que necesitan un vocabulario comun para hablar de granularidad

Atomic Design NO funciona bien para:
- Aplicaciones con logica de negocio significativa (los servicios no encajan)
- Equipos que pierden tiempo debatiendo clasificaciones
- Proyectos donde los archivos relacionados necesitan estar juntos

Recomendacion: usar Atomic Design como modelo mental flexible para
pensar en granularidad, pero organizar el codigo por features en
aplicaciones reales.
```

## Que puede salir mal

- **"No se si mi componente es molecule u organism"** → Eso es exactamente el punto. La ambiguedad es una debilidad real de Atomic Design. Documentala como hallazgo.
- **"Me quedo sin componentes para clasificar"** → Incluye los componentes que documentaste en la Actividad 2.1 (los que identificaste en el mockup), aunque no los hayas implementado todos.
- **"No entiendo Feature-Sliced Design"** → La idea central es simple: agrupa los archivos por lo que hacen en el negocio (feature de usuarios, feature de productos) en lugar de por su tipo técnico (atoms, molecules).

## Resultado esperado

Tienes un documento `atomic-design.md` con la clasificacion de tus componentes, las ambiguedades encontradas, la comparacion con Feature-Sliced Design, y una conclusion fundamentada.

**Criterios de aceptacion:**
- [ ] Todos los componentes construidos estan clasificados en niveles atomicos (atoms, molecules, organisms)
- [ ] Se identifican al menos 2 casos ambiguos con explicacion de por que la clasificacion no es clara
- [ ] El documento propone cuando Atomic Design ayuda vs cuando estorba, con argumentos concretos

**Pilares de diseño que ejercita esta actividad:**
- **Mantenibilidad** — elegir la organizacion correcta de código facilita (o dificulta) el mantenimiento a largo plazo
- **Observabilidad** — una estructura clara del proyecto permite a los desarrolladores encontrar rapidamente donde vive cada pieza
