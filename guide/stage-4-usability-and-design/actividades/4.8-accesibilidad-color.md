## Por que esta actividad

El 8% de los hombres y el 0.5% de las mujeres tienen algun tipo de daltonismo. Si tu interfaz usa solo color para comunicar estados (rojo = error, verde = exito), estas personas no pueden distinguirlos. La regla WCAG 1.4.1 es clara: el color no puede ser el **único** medio visual para transmitir información.

Ademas, hay personas con trastornos vestibulares (vertigo, mareo) para quienes las animaciones son literalmente nauseabundas. La media query `prefers-reduced-motion` te permite respetar la preferencia del sistema operativo del usuario y desactivar o reducir animaciones cuando el usuario lo necesita.

Esta actividad combina dos aspectos de accesibilidad visual: (1) asegurar que todo estado tiene un indicador no-cromatico (texto, icono, forma) ademas del color, y (2) implementar soporte para movimiento reducido.

## Antes de empezar

Necesitas haber completado las **Actividades 4.1-4.4**. La lectura de Color para UI de la Actividad 4.1 es la misma — esta vez enfocate en la sección de accesibilidad y contraste.

Conceptos clave:

- **WCAG 1.4.1 — Uso del color**: "el color no se usa como el único medio visual para transmitir información, indicar una acción, solicitar una respuesta, o distinguir un elemento visual". Ejemplo: un campo con borde rojo en estado de error debe **también** tener un icono de advertencia o un texto que diga "Error".
- **Daltonismo** (deficiencia de vision del color): existen varios tipos. El mas comun es protanopia/deuteranopia (dificultad para distinguir rojo y verde). También existe tritanopia (dificultad con azul y amarillo). DevTools puede simular estas condiciones.
- **`prefers-reduced-motion`**: una media query que detecta si el usuario activo la opción "Reducir movimiento" en su sistema operativo. En macOS: Preferencias del Sistema → Accesibilidad → Pantalla → Reducir movimiento. En Windows: Configuración → Accesibilidad → Efectos visuales → Efectos de animación.

### Paso 1 — Auditar uso del color

1. Abre tu dashboard (Actividad 4.4) en el navegador
2. Haz una captura de pantalla mentalmente en blanco y negro. Preguntate:
   - ¿Las tarjetas de "exito" (verde), "advertencia" (amarillo) y "error" (rojo) se diferencian sin color?
   - ¿Los estados de la tabla ("Completada" vs "Pendiente") se distinguen sin color?
   - ¿El link activo del sidebar se distingue de los inactivos sin color?
3. Abre tu wizard (Actividad 4.2):
   - ¿Los campos con error se distinguen de los validos sin color?
   - ¿Los pasos completados se distinguen del paso actual sin color?

Documenta cada caso donde el color es el **único** diferenciador.

### Paso 2 — Agregar indicadores no-cromaticos

Para cada caso que encontraste, agrega un indicador adicional:

**Tarjetas semanticas del dashboard:**

```text
<!-- HTML: agregar iconos/texto a las tarjetas -->
<div class="card card--success">
  <h3>Ventas totales</h3>
  <p class="metric">$124,500</p>
  <p class="caption">
    <span aria-hidden="true">&#9650;</span> <!-- triangulo hacia arriba -->
    +12% vs mes anterior
  </p>
</div>

<div class="card card--error">
  <h3>Tickets sin resolver</h3>
  <p class="metric">47</p>
  <p class="caption">
    <span aria-hidden="true">&#9888;</span> <!-- triangulo de advertencia -->
    Requiere atencion
  </p>
</div>
```

**Estados en la tabla:**

```text
<!-- HTML: agregar indicadores a los estados -->
<td><span class="status status--complete">&#10003; Completada</span></td>
<td><span class="status status--pending">&#9679; Pendiente</span></td>
```

```css
/* Estados con indicador no-cromatico */
.status {
  display: inline-flex;
  align-items: center;
  gap: var(--space-1);
}

.status--complete {
  color: var(--color-success);
}

.status--pending {
  color: var(--color-warning);
}
```

**Campos con error en el wizard:**

```css
/* El campo de error tiene borde rojo + icono + texto */
.field.has-error input {
  border-color: var(--color-error);
  /* El texto de error (.field-error) ya es un indicador no-cromatico */
}

/* Reforzar el paso completado del wizard con un checkmark */
.step.completed::before {
  content: '\2713 '; /* checkmark Unicode */
}
```

### Paso 3 — Simular daltonismo

1. En Chrome: DevTools → menu de 3 puntos (arriba a la derecha del panel DevTools) → **More tools → Rendering**
2. Baja hasta **Emulate vision deficiencies**
3. Selecciona cada tipo y verifica tu interfaz:
   - **Protanopia** (no ve rojo): ¿puedes distinguir exito de error?
   - **Deuteranopia** (no ve verde): ¿puedes distinguir exito de error?
   - **Tritanopia** (no ve azul): ¿puedes distinguir info de advertencia?
   - **Achromatopsia** (no ve ningun color): ¿toda la información es comprensible?

4. Para cada tipo, si no puedes distinguir un estado, necesitas un indicador no-cromatico adicional (icono, texto, forma de borde diferente)

### Paso 4 — Implementar prefers-reduced-motion

1. Identifica todas las animaciones en tu CSS:
   - Skeleton pulse/shimmer (Actividad 4.6)
   - Transición del sidebar (Actividad 4.4)
   - Transición de la barra de progreso del wizard (Actividad 4.2)
   - Cualquier `transition` en botones o inputs

2. Agrega al final de tu CSS principal:

```css
/* ========== Movimiento reducido ========== */
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

> 💡 **Nota:** Usamos `0.01ms` en vez de `0s` porque algunos navegadores ignoran `0s`. Esta regla global desactiva efectivamente todas las animaciones y transiciones. Es un enfoque agresivo pero seguro. En una aplicación madura, podrias ser mas selectivo y mantener transiciones de opacidad (fade) que son menos problematicas que las de movimiento.

3. Para probar:
   - **Chrome DevTools:** Rendering → "Emulate CSS media feature prefers-reduced-motion" → reduce
   - **macOS:** Preferencias del Sistema → Accesibilidad → Pantalla → Reducir movimiento
   - **Windows:** Configuración → Accesibilidad → Efectos visuales → Efectos de animación → desactivar

### Paso 5 — Verificación final

1. Abre tu dashboard con simulacion de **protanopia** activa
2. Verifica que puedes distinguir:
   - Tarjetas de exito, advertencia y error
   - Estados de "Completada" y "Pendiente" en la tabla
   - Paso actual vs completado en el wizard
3. Activa **prefers-reduced-motion: reduce** en DevTools
4. Verifica que:
   - Los skeletons no pulsan/brillan
   - El sidebar no se desliza (aparece/desaparece instantaneamente)
   - La barra de progreso no transiciona (cambia instantaneamente)
5. Verifica que la aplicación sigue siendo **funcional** con ambas restricciones activas

## Que puede salir mal

- **"No encuentro 'Rendering' en DevTools"** → En Chrome, el panel Rendering no esta visible por defecto. Abre DevTools → presiona Ctrl+Shift+P (Command Palette) → escribe "rendering" → selecciona "Show Rendering".
- **"La simulacion de daltonismo no cambia nada"** → Asegurate de que estas usando colores (no solo grises). Si tu interfaz ya es monocromatica, la simulacion no muestra diferencia — pero eso no significa que sea accesible (necesitas los indicadores no-cromaticos igualmente).
- **"Las animaciones siguen funcionando con reduced-motion"** → Verifica que la regla `@media (prefers-reduced-motion: reduce)` esta al final del CSS (despues de las animaciones). Si esta antes, otras reglas la sobreescriben. El `!important` deberia prevenir esto, pero verifica el orden por si acaso.

## Resultado esperado

Tu dashboard y wizard son completamente comprensibles en simulacion de daltonismo: cada estado (exito, error, advertencia, pendiente, completado) tiene al menos un indicador que no depende del color (icono, texto, forma). Al activar `prefers-reduced-motion`, todas las animaciones se desactivan instantaneamente sin afectar la funcionalidad.

**Criterios de aceptacion:**
- [ ] Todo estado tiene un indicador no-cromatico (texto, icono, forma) ademas del color — verificado en simulacion de achromatopsia
- [ ] `prefers-reduced-motion: reduce` elimina todas las animaciones — verificado en DevTools
- [ ] La app es comprensible en simulacion de protanopia y deuteranopia — todos los estados se distinguen
