## Por que esta actividad

Un **dark pattern** es un truco de diseño que engana al usuario para que haga algo que no queria: suscribirse a un newsletter, aceptar cookies innecesarias, o no cancelar una suscripcion. Son el opuesto exacto de la usabilidad. A veces se introducen a proposito por presion del negocio; otras veces, los desarrolladores los crean sin darse cuenta.

Ejemplos comunes: "¿Seguro que quieres irte? Te vas a perder ofertas INCREIBLES" (confirm-shaming), un botón de "Aceptar todo" grande y colorido junto a "Gestionar preferencias" diminuto y gris (misdirection), o costos ocultos que aparecen en el ultimo paso del checkout.

Como desarrollador frontend, tu construyes estas interfaces. Conocer los dark patterns te permite (1) no crearlos por accidente y (2) argumentar contra ellos cuando alguien te pida implementarlos. Ademas, la regulacion europea (Digital Services Act) esta prohibiendo varios de estos patrones.

## Antes de empezar

Necesitas haber completado las **Actividades 4.1-4.4**. Vas a auditar tu wizard (Actividad 4.2) y tu dashboard (Actividad 4.4).

Los dark patterns mas comunes en frontend:

- **Confirm-shaming** (avergonzar para confirmar): "No, no quiero ahorrar dinero" como opción de cancelar. El texto culpa al usuario por no aceptar.
- **Misdirection** (desviar la atención): el botón que beneficia a la empresa es grande y colorido; el que beneficia al usuario es pequeno y gris.
- **Hidden costs** (costos ocultos): el precio final es diferente al mostrado porque se agregan impuestos, envio o cargos "de servicio" en el ultimo paso.
- **Roach motel** (motel cucaracha): es fácil entrar (suscribirse con un clic) pero difícil salir (cancelar requiere llamar por telefono).
- **Toast fatigue** (fatiga de notificaciones): mostrar toasts/snackbars para cada acción, incluso las triviales. El usuario aprende a ignorar todas las notificaciones, incluyendo las importantes.
- **Forced continuity** (continuidad forzada): el trial gratuito se convierte en pago sin aviso claro.

### Paso 1 — Preparar checklist de auditoria

1. Crea un archivo `ejercicio-4.7/auditoria-dark-patterns.md`
2. Escribe este checklist:

```text
# Auditoria de Dark Patterns

## Checklist

### Confirm-shaming
- [ ] Ningun texto de cancelacion/rechazo culpa o avergüenza al usuario
- [ ] Las opciones de "No, gracias" son neutras

### Misdirection
- [ ] Las acciones que benefician al usuario son tan prominentes como las que benefician al negocio
- [ ] El boton de "Cancelar" es visible y accesible (no escondido, no gris minusculo)

### Hidden costs
- [ ] El precio/resultado final es visible desde el inicio
- [ ] No hay cargos adicionales que aparezcan solo al final

### Roach motel
- [ ] Toda accion que el usuario puede iniciar, la puede revertir con igual facilidad
- [ ] El boton de "deshacer" o "cancelar" existe y funciona

### Toast fatigue
- [ ] Los toasts/snackbars solo se usan para resultados inciertos o asincronos
- [ ] No hay toast para acciones triviales (guardar en formulario, cambiar de tab)
- [ ] Las notificaciones importantes usan un mecanismo distinto (inline, no toast)

### Forced continuity
- [ ] Las suscripciones/registros tienen clausulas claras sobre renovacion
- [ ] El usuario puede salir del flujo en cualquier momento sin perder datos
```

### Paso 2 — Auditar el wizard

1. Abre tu wizard de la Actividad 4.2
2. Recorrelo como si fueras un usuario que no lo ha visto nunca:
   - ¿Puedes retroceder en cada paso? (Si no, es un roach motel)
   - ¿El botón "Crear cuenta" hace algo que no se explico al inicio? (hidden costs)
   - ¿Hay algun texto que presione al usuario para completar el registro? (confirm-shaming)
   - ¿El botón "Siguiente" es mucho mas prominente que "Anterior"? (Si — esto es aceptable porque avanzar es la acción primaria, pero "Anterior" debe ser visible y accesible)

3. Documenta tus hallazgos en `auditoria-dark-patterns.md`

### Paso 3 — Auditar el dashboard

1. Abre tu dashboard de la Actividad 4.4
2. Revisa:
   - ¿Si agregas toasts (para futuras funcionalidades), usarias uno para cada clic? Solo deben usarse para operaciones asincronas (exportar datos, enviar correo) cuyo resultado no es inmediato
   - ¿Las acciones destructivas (eliminar, resetear) tienen confirmacion? No deben tener confirm-shaming ("¿Seguro? Perderas TODO para siempre")

3. Implementa una practica buena: un dialogo de confirmacion neutro para acciones destructivas:

```text
<!-- HTML: ejemplo de dialogo de confirmacion neutro -->
<dialog id="confirm-dialog">
  <h2>Eliminar registro</h2>
  <p>Esta accion no se puede deshacer. ¿Deseas continuar?</p>
  <div class="dialog-actions">
    <button class="btn btn--secondary" id="dialog-cancel">Cancelar</button>
    <button class="btn btn--danger" id="dialog-confirm">Eliminar</button>
  </div>
</dialog>
```

```css
/* Dialogo de confirmacion neutro */
dialog {
  border: 1px solid var(--color-border);
  border-radius: 0.5rem;
  padding: var(--space-8);
  max-width: 24rem;
}

dialog::backdrop {
  background: rgba(0, 0, 0, 0.5);
}

.dialog-actions {
  display: flex;
  justify-content: flex-end;
  gap: var(--space-4);
  margin-block-start: var(--space-6);
}

.btn--danger {
  background-color: var(--color-error);
  color: white;
}
```

> 💡 **Nota:** El texto dice "Esta acción no se puede deshacer. ¿Deseas continuar?" — neutro y factual. No dice "¿SEGURO? Perderas TODA tu información PARA SIEMPRE" — eso es manipulación emocional.

### Paso 4 — Botones deshabilitados que explican por que

Un botón deshabilitado sin explicacion es frustrante — el usuario no sabe que hacer para habilitarlo. Implementa tooltips o texto explicativo:

1. En tu wizard, cuando el botón "Siguiente" esta deshabilitado:

```javascript
// Agregar a wizard.js — explicar por que el boton esta deshabilitado
function updateNextButton() {
  const isValid = validateCurrentStep();
  btnNext.disabled = !isValid;

  if (!isValid) {
    btnNext.setAttribute('title', 'Completa los campos obligatorios para continuar');
    btnNext.setAttribute('aria-describedby', 'next-hint');
  } else {
    btnNext.removeAttribute('title');
    btnNext.removeAttribute('aria-describedby');
  }
}
```

2. Agrega un texto visual debajo del botón:

```css
.btn:disabled {
  opacity: 0.5;
  cursor: not-allowed;
}

.btn:disabled + .hint {
  display: block;
  font-size: var(--font-size-sm);
  color: var(--color-text-muted);
  margin-block-start: var(--space-2);
}
```

### Paso 5 — Revision por pares

1. Pidele a otra persona (companero, amigo, familiar) que use tu wizard y tu dashboard
2. Observa sin intervenir:
   - ¿Intentan hacer algo que la interfaz no les permite?
   - ¿Se frustran en algun punto?
   - ¿Entienden que hace cada botón?
3. Preguntales al final:
   - "¿Sentiste que la interfaz te estaba empujando a hacer algo que no querias?"
   - "¿Hubo algun momento donde no sabias por que un botón estaba gris?"
4. Documenta las respuestas en tu auditoria

## Que puede salir mal

- **"No encuentro dark patterns en mi interfaz"** → Como desarrollador, tus dark patterns suelen ser accidentales: un botón deshabilitado sin explicacion, un toast para cada acción, o falta de un botón "deshacer". Pidele a alguien mas que use tu interfaz — lo que tu no ves, ellos lo experimentan.
- **"Mi companero dice que todo esta bien"** → Pidele que haga tareas especificas: "intenta cancelar el registro a la mitad", "intenta encontrar como volver al paso anterior". Las tareas especificas revelan problemas que la exploracion libre no muestra.
- **"No se como implementar el `<dialog>`"** → El elemento `<dialog>` es nativo de HTML. Se abre con `dialog.showModal()` y se cierra con `dialog.close()`. No necesitas librerias. Funciona en todos los navegadores modernos.

## Resultado esperado

Tienes un documento de auditoria que confirma que tu wizard y dashboard no contienen dark patterns. Los botones deshabilitados explican por que estan deshabilitados. Los toasts (si los hay) solo se usan para operaciones asincronas. Las acciones destructivas tienen un dialogo de confirmacion con texto neutro. Otra persona ha verificado la experiencia.

**Criterios de aceptacion:**
- [ ] Auditoria documentada con el checklist de 6 categorias de dark patterns
- [ ] Los toasts (si existen) se usan solo para resultados inciertos/asincronos
- [ ] Todo botón deshabilitado explica por que (tooltip o texto visible)
